# 架构选型与理由

> 说明：本文汇总本项目各核心组件"为什么选它"的选型思考，配合 [依赖组件与使用场景](../02-开发指南/依赖组件与使用场景.md) 与 [各服务面试题（含追问与答案）](../05-面试准备/各服务面试题（含追问与答案）.md) 使用。
> 技术栈全景：Java 17 + Spring Boot 3.0.2 + Spring Cloud Alibaba 2022.0.0（Nacos / Gateway / OpenFeign）+ Sa-Token + MySQL/MyBatis/Druid + Redis（BF / ZSET / Hash / Lua）+ RocketMQ + XXL-JOB + 美团 Leaf + Cassandra + Minio/OSS + Caffeine + ZooKeeper。

---

## 0. 选型总览表

| 组件 | 项目用途 | 一句话理由 |
|------|---------|-----------|
| Spring Cloud Alibaba | 微服务骨架（网关/注册/调用） | 国内微服务主流生态，Nacos 集注册+配置一体 |
| Spring Cloud Gateway | 统一入口 + 鉴权 | 基于 WebFlux 响应式、非阻塞、性能优于 Zuul 1 |
| Nacos | 注册中心 + 配置中心 | 一体两用、免运维，支持动态配置 |
| OpenFeign | 服务间 RPC 调用 | 声明式 HTTP 客户端，接口契约即调用 |
| Sa-Token | 登录鉴权 + 权限校验 | 轻量、天然适配网关（SaReactorFilter）、RBAC |
| RocketMQ | 异步解耦、削峰、计数链路 | Java 生态好、事务/延迟/顺序消息齐全、消费重试 |
| Redis | 缓存/计数/去重/限流/分布式锁 | 高性能、数据结构丰富、Lua 原子性 |
| MySQL + MyBatis + Druid | 主业务库 | 关系型保证事务，MyBatis SQL 可控，Druid 监控 |
| Cassandra | 笔记正文 KV 存储 | 无中心、线性扩展、写性能高，适合海量文本 |
| Caffeine | 本地缓存（用户/笔记详情） | W-TinyLFU 命中率高、性能强、Spring Boot 3 默认 |
| XXL-JOB | 定时任务（分片对齐） | 可视化、分片广播、任务日志，替代 Quartz |
| 美团 Leaf | 分布式 ID | 号段 + 雪花双模式，趋势递增 |
| ZooKeeper | 雪花 workerId 协调 | 临时顺序节点分配 + 时间戳校验防时钟回拨 |
| Minio / 阿里云 OSS | 对象存储（图片/视频） | 文件不进 DB，策略模式兼容私有化与云 |
| Jackson starter | 全局统一 JSON 序列化 | 全链路格式/时区/日期统一 |

## 1. 为什么选 Spring Cloud Alibaba 全家桶

**项目用在哪**：网关（Gateway）、注册/配置（Nacos）、服务调用（OpenFeign）、负载均衡等微服务基础设施。

**为什么选它**：
1. **Nacos 注册 + 配置一体化**：一个组件同时搞定服务注册发现和配置中心，免去单独部署 Eureka + Config + Bus 三件套，运维成本低。
2. **与 Spring Boot 3 / Spring Cloud 生态天然衔接**：项目是 Spring Boot 3.0.2 + Spring Cloud Alibaba 2022.0.0，官方对齐版本，坑少。
3. **国内落地成熟**：社区活跃、资料多、生产验证充分。
4. **Gateway 是响应式网关**：基于 WebFlux，**非阻塞 IO**，比 Zuul 1（Servlet 阻塞模型）吞吐高；本项目网关里还要跑 Sa-Token 鉴权（`SaReactorFilter`），必须用反应式框架才能挂上去。

**一句话记忆**：SCA 是"全家桶"——注册、配置、网关、调用一站齐，Nacos 一体两用最省心。

## 2. 为什么选 RocketMQ

**项目用在哪**：关注/点赞/收藏/发布等所有异步解耦、计数链路、data-align 增量清单（详见 [RocketMQ使用总结](../02-开发指南/RocketMQ使用总结.md)）。

**为什么选它**（对比 Kafka / RabbitMQ）：

| 维度 | RocketMQ | Kafka | RabbitMQ |
|------|----------|-------|----------|
| 语言/生态 | Java，和项目同栈 | Java 客户端但核心 Scala | Erlang，运维门槛高 |
| 功能完备性 | **事务消息、延迟消息、顺序消息全有** | 事务消息弱、无延迟消息 | 功能全但无事务消息 |
| 吞吐 | 单机十万级 | 百万级（最高） | 万级 |
| 消费重试 | **自带失败重试（默认 16 次）** | 需自研 | 有，但配置复杂 |
| 运维友好 | 控制台完善 | 需配套工具 | 一般 |
| 适用场景 | **业务消息（本项目）** | 大数据/日志流 | 简单解耦 |

**项目实际用法**：
- **异步提升吞吐**：高并发接口（发布笔记、点赞、关注）全部 `asyncSend` / `asyncSendOrderly` 异步发 MQ（[NoteServiceImpl.java:228](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L228)）。
- **顺序性**：关注链路用 `asyncSendOrderly(..., hashKey=userId)`，**同一用户的消息按序消费**，保证粉丝数变更不乱序（[RelationServiceImpl.java:162](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user-relation/xiaohashu-user-relation-biz/src/main/java/com/quanxiaoha/xiaohashu/user/relation/biz/service/impl/RelationServiceImpl.java#L162)）。
- **消费端可靠性**：消费失败自动重试 + 幂等兜底（唯一索引 / 双 Bloom，见 [项目复盘问答 问题十三](../04-问题排查与记录/项目复盘问答.md)）。

**一句话记忆**：要"业务消息"全套能力（事务、延迟、顺序、重试）且 Java 同栈——RocketMQ 比 Kafka 全、比 RabbitMQ 快且友好。

## 3. 为什么选 Redis

**项目用在哪**：验证码、用户 token、关注/粉丝 ZSET、计数 Hash、笔记缓存、Bloom 去重、分布式标志锁、Lua 原子脚本（详见 [Redis学习笔记](../02-开发指南/Redis学习笔记.md) 与 [Lua脚本使用总结](../02-开发指南/Lua脚本使用总结.md)）。

**为什么选它**：
1. **高性能**：单线程 + 内存 + 事件驱动，读写微秒级，扛得住高并发读写。
2. **数据结构丰富**：ZSET（关注列表/粉丝列表 + 排序）、Hash（计数器字段）、String（验证码/token）、BF（去重）、Lua（原子操作），一个中间件覆盖缓存、计数、去重、锁多种需求。
3. **原子性**：单线程执行命令天然原子，`setIfAbsent`（分布式锁）、Lua 脚本（关注判重）保证并发安全。
4. **可持久化 + 集群**：RDB/AOF 持久化，Cluster 分片扩容。

**为什么不直接用 DB 扛**：关系型数据库扛不住高频读写在内存里累计（计数接口每秒几十万次 increment），Redis 落内存、DB 落最终态，两者配合（count 服务 Redis 计数 → BufferTrigger 落库 → data-align 对账，见 [业务流程 18 节](../03-业务流程/业务流程.md)）。

**一句话记忆**：要"内存级速度 + 丰富数据结构 + 原子性"，Redis 是标准答案。

## 4. 为什么选 MySQL + MyBatis + Druid

**项目用在哪**：用户、笔记、关系、计数、auth 等主业务数据。

**为什么这么组合**：
- **MySQL**：关系型数据库，ACID 事务（注册、发布、关注落库都要事务）、成熟稳定、运维资料多，业务数据天然关系型（用户-笔记-点赞-收藏-关注）。
- **MyBatis**：SQL 手写可控、XML 动态 SQL（分片表名拼接、`insertOrUpdate` 幂等）、性能优化空间大；相比 JPA 黑盒，本项目大量"批量 insert + 唯一索引幂等"场景更适用。
- **Druid**：连接池 + 内置监控（SQL 统计、慢查询、连接数），生产排查方便。

**一句话记忆**：业务要事务用 MySQL，SQL 要可控用 MyBatis，监控要省心用 Druid。

## 5. 为什么选 Cassandra（笔记正文 KV）

**项目用在哪**：kv 服务的 `t_note_content`，按 `content_uuid` 存取笔记正文（大文本），数据访问层是 `NoteContentRepository extends CassandraRepository`。

**为什么选它**（对比 MySQL / HBase / MongoDB）：

| 维度 | Cassandra | MySQL | HBase | MongoDB |
|------|-----------|-------|-------|---------|
| 架构 | **无中心 P2P，无主从** | 主从 | 依赖 HDFS + ZK，重 | 副本集 |
| 扩展性 | **线性扩展，加节点即加容量** | 分库分表复杂 | 好但运维重 | 好 |
| 写性能 | **极高（LSM-Tree 顺序写）** | 有瓶颈 | 高 | 高 |
| 单点故障 | **无单点，自动故障转移** | 主库切换麻烦 | 组件多 | 一般 |
| 适合场景 | **海量非结构化文本** | 关系型事务 | 超大数据分析 | 文档型 |

**项目实际**：笔记正文是大文本且只按 `content_uuid` 精确存取，不需要 join、不需要事务——正是 Cassandra 的舒适区。UUID 由 note 服务本地生成（无中心分配，见 [项目复盘问答 问题十五](../04-问题排查与记录/项目复盘问答.md)）。

**一句话记忆**：海量文本 + 纯 KV 存取 + 要线性扩展 → 无中心高写入的 Cassandra。

## 6. 为什么选 Caffeine 而不是 Guava Cache

**项目用在哪**：[UserServiceImpl.java:83-87](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/service/impl/UserServiceImpl.java#L83-L87)（用户信息本地缓存）、[NoteServiceImpl.java:98-102](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L98-L102)（笔记详情本地缓存），都是 `initialCapacity(10000) + maximumSize(10000) + expireAfterWrite(1H)`。

**为什么选 Caffeine**：
1. **淘汰算法 W-TinyLFU vs LRU**：Caffeine 用"窗口 + 分段 LRU + 频率计数"，能记住高频对象、抗一次性扫描污染，**命中率更高**（热数据反复查的场景收益明显）。
2. **性能更强**：官方基准读写吞吐接近 `ConcurrentHashMap`，读场景约为 Guava Cache 的 2-3 倍。
3. **异步加载/刷新/淘汰**：`refreshAfterWrite` + 异步刷新，把耗时操作移出请求线程。
4. **可观测性**：`recordStats()` 提供命中率/加载耗时统计。
5. **Spring Boot 3 决定性因素**：Boot 2.7 起弃用、**Boot 3.x 已移除 Guava Cache 自动配置**，Caffeine 是 Spring Cache 默认本地缓存实现。
6. **维护活跃 + JSR-107**：Caffeine 持续更新并实现 JCache 规范；Guava 的 Cache 已进入维护模式。

**注意**：项目里 Guava 也用着——`RateLimiter` 做消费端限流（令牌桶，[FollowUnfollowMqConsumerRateLimitConfig](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user-relation/xiaohashu-user-relation-biz/src/main/java/com/quanxiaoha/xiaohashu/user/relation/biz/config/FollowUnfollowMqConsumerRateLimitConfig.java)）。是"缓存用 Caffeine、限流用 Guava"各取所长，不是二选一。

**一句话记忆**：Caffeine 淘汰更聪明、更快、Boot 3 唯一默认；Guava 的 RateLimiter 留下来做限流。

## 7. 为什么选 XXL-JOB（对比 Quartz）

**项目用在哪**：data-align 服务的 9 个任务（建表 / 7 个分片对齐 / 删表，详见 [XXL-JOB使用总结](../02-开发指南/XXL-JOB使用总结.md)）。

**为什么选它**：

| 维度 | XXL-JOB | Quartz |
|------|---------|--------|
| 控制台 | **自带可视化控制台**（任务管理/日志/报表） | 无，全靠代码 |
| 路由策略 | **10 种路由 + 分片广播** | 无分片概念 |
| 集群调度 | **调度中心独立部署**，执行器注册制 | 集群靠数据库锁，性能差 |
| 任务日志 | 在线查看调度日志 | 需自己落库 |
| 动态管理 | 控制台改 Cron / 启停，无需重启 | 改代码重启 |

**项目核心诉求就是"分片广播"**：7 个对齐任务靠 `getShardIndex/getShardTotal` 让每个实例处理自己的分片表——这是 Quartz 没有的能力。

**一句话记忆**：要"可视化 + 分片广播 + 任务日志"，XXL-JOB 是轻量分布式任务调度的标准答案。

## 8. 为什么选美团 Leaf（分布式 ID）

**项目用在哪**：分布式 ID 服务（[ID使用方式总结](ID使用方式总结.md)），业务表主键用**号段模式**（用户 ID、小哈书号），笔记 ID 用**雪花模式**。

**为什么不用 UUID / 自增主键**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| UUID | 本地生成零协调 | **无序**（索引页分裂/写放大）、**16 字节**（比 Long 大一倍）、不可读 |
| DB 自增 | 简单 | 单点、分库分表后不唯一、性能瓶颈 |
| **Leaf 号段** | 一次划 2000 个缓存内存、趋势递增、命中聚簇索引 | 依赖 DB（可接受） |
| **Leaf 雪花** | 无中心、纯内存生成、分布式 | 依赖时钟（ZK 上报校验防回拨） |

**为什么两种都要**（详见 [项目复盘问答 问题十四/十五](../04-问题排查与记录/项目复盘问答.md)）：
- **号段**：用户 ID、小哈书号——低频但需趋势递增（MySQL 主键友好）；
- **雪花**：笔记 ID——高并发、跨服务生成，不想每 2000 个就打一次 DB；
- 各 biz_tag 独立游标、各自唯一，互不干扰。

**一句话记忆**：要"全局唯一 + 趋势递增 + 不依赖中心"，Leaf 号段/雪花双模式全覆盖。

## 9. 为什么选 Sa-Token（对比 Spring Security）

**项目用在哪**：网关统一鉴权（`SaReactorFilter` + `SaRouter` 路由规则，[SaTokenConfigure.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-gateway/src/main/java/com/quanxiaoha/xiaohashu/gateway/auth/SaTokenConfigure.java)）+ 权限数据源（[StpInterfaceImpl.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-gateway/src/main/java/com/quanxiaoha/xiaohashu/gateway/auth/StpInterfaceImpl.java)）。

**为什么选它**：
1. **轻量**：一个注解/几行配置搞定登录鉴权，Spring Security 全家桶对网关这种"只做校验"的场景太重。
2. **天然适配响应式网关**：提供 `SaReactorFilter`，项目网关是 WebFlux 反应式，Spring Security 需要额外配 WebFlux 模块。
3. **API 简洁**：`StpUtil.checkLogin()` / `checkPermission()` 一眼看懂，`SaRouter.match().notMatch().check()` 链式路由规则清晰。
4. **扩展点简单**：实现 `StpInterface` 即可自定义权限来源（本项目从 Redis 拉角色→权限，见 [项目复盘问答 问题十一](../04-问题排查与记录/项目复盘问答.md)）。

**一句话记忆**：网关只做"校验"要轻要快，Sa-Token 一个类搞定，不用背 Spring Security 全家桶。

## 10. 为什么选 ZooKeeper（雪花 workerId 协调）

**项目用在哪**：雪花模式生成器注册 workerId（[SnowflakeZookeeperHolder](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-distributed-id-generator/xiaohashu-distributed-id-generator-biz/src/main/java/com/quanxiaoha/xiaohashu/distributed/id/generator/biz/core/snowflake/SnowflakeZookeeperHolder.java)）。

**为什么选它**：雪花算法要求**各实例 workerId 全局唯一**（同一毫秒不同实例不冲突）。ZK 用 `PERSISTENT_SEQUENTIAL` 临时顺序节点，**节点名后缀序号即 workerId**——天然唯一且自动分配；临时节点在实例下线时自动消失（不需要清理逻辑）；配合每 3 秒上报本机时间戳做**时钟回拨校验**。

**可靠性三层**（详见 [依赖组件与使用场景 分布式ID 章节](../02-开发指南/依赖组件与使用场景.md)）：ZK 分配 → 本地 `workerID.properties` 缓存 → ZK 全挂降级 `ZeroIDGen`。

**一句话记忆**：要"自动分配全局唯一的 workerId"，ZK 临时顺序节点是开箱即用的答案。

---

## 11. 为什么用 Minio / 阿里云 OSS（对象存储）

**项目用在哪**：oss 服务，用户头像/背景、笔记图片/视频，`FileStrategy` 策略接口 + `MinioFileStrategy` / `AliyunOSSFileStrategy` 两个实现 + `FileStrategyFactory` 按配置 `storage.type` 动态注册（`@RefreshScope` 支持运行期切换）。

**为什么文件不进 DB**：文件是二进制大对象，进 MySQL 会拖垮查询性能、撑爆库容量；对象存储提供容量扩展、URL 直读、CDN 支持。

**Minio vs 阿里云 OSS**：Minio 自部署（开源、S3 兼容、私有化/开发环境省钱）；OSS 云服务（免运维、高可用、按量付费）。策略模式让两者切换零成本。

**一句话记忆**：文件走对象存储不进库；Minio 省钱自部署、OSS 省心用云，策略模式两头通。

---

## 12. 为什么做统一 Jackson starter

**项目用在哪**：`xiaoha-spring-boot-starter-jackson` 提供全局唯一 `ObjectMapper`（`new ObjectMapper()` + JavaTimeModule + Asia/Shanghai 时区 + 忽略未知字段）和 `JsonUtils` 工具。

**为什么需要**（详见 [项目复盘问答 问题十二](../04-问题排查与记录/项目复盘问答.md)）：微服务下**所有跨进程传输都过序列化**（HTTP / Feign / Redis / MQ / 日志），如果各服务各配一套，日期格式、时区、字段策略不一致，联调必炸。抽成 starter 让全链路**一份配置、处处生效**。

**一句话记忆**：序列化是分布式系统的"隐形边界"，抽成 starter 统一格式是消除类问题的根治方案。

## 13. 选型原则总结

1. **按场景选，不追新**：KV 海量文本 → Cassandra；业务关系型 → MySQL；热数据 → Redis + Caffeine；都不是"越流行越好"。
2. **能合并的组件不分开**：Nacos 集注册+配置；ZK 只干 workerId 一件事；组件少、链路短、好排查。
3. **统一底座**：Jackson starter、统一 Response、统一异常，跨服务行为一致。
4. **快慢分离**：实时近似的 count（Redis）与次日精确的 data-align（DB 重算）分层，各自选型适配自己的"快/准"定位。
5. **最终一致优先**：MQ + 幂等 + 对齐兜底，允许短暂不一致，换取高吞吐与高可用。
