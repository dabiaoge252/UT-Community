## 1. 为什么操作类型要用枚举封装

### 1.1 背景

点赞/收藏/关注这类操作都有"正向"与"取消"两个动作，MQ 消息与接口中用 `Integer type` 表示：

| 枚举（各服务 enums 包） | 取值 | 说明 |
|---|---|---|
| `LikeUnlikeNoteTypeEnum`（note/count） | LIKE=1, UNLIKE=0 | 点赞 / 取消点赞 |
| `CollectUnCollectNoteTypeEnum`（note/count） | COLLECT=1, UN_COLLECT=0 | 收藏 / 取消收藏 |
| `FollowUnfollowTypeEnum`（user-relation） | FOLLOW=1, UNFOLLOW=0 | 关注 / 取关 |
| 其他示例 | `NoteTypeEnum`、`SexEnum`、`LoginTypeEnum` | 笔记类型、性别、登录方式等 |

例：生产端构建 DTO 时用枚举取值（[NoteServiceImpl.java:1191-1192](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L1191-L1192)）：

```java
.type(CollectUnCollectNoteTypeEnum.COLLECT.getCode()) // 收藏笔记
```

### 1.2 为什么用枚举

1. **消灭魔法数字，可读性高**：`LikeUnlikeNoteTypeEnum.LIKE.getCode()` 比裸的 `1` 语义清晰得多。
2. **类型安全**：编译期就能发现传错值（如 1/0 写反、手误写成 2），运行时不易出错。
3. **取值单一事实来源**：一处定义、全项目统一引用；note/count 等不同服务各自维护同名枚举但值保持一致，跨服务消息语义稳定。
4. **便于扩展**：未来新增"重新点赞/置顶"等类型，只改枚举一处。
5. **配合分支逻辑**：消费者/服务里 `switch (type)` 或与枚举 `getCode()` 比较，比散落的数字判断清晰。

### 1.3 注意点

- MQ 消息体里传输的仍是数字（`getCode()` 序列化后的 Integer），JSON 反序列化后拿到的是数字而非枚举；判断时用枚举 code 比较或映射回枚举，不要继续写魔法数字。
- 枚举用 Lombok `@Getter + @AllArgsConstructor` 简洁定义（[LikeUnlikeNoteTypeEnum.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/enums/LikeUnlikeNoteTypeEnum.java)）。

## 2. XXL-JOB 分片存储与分片对齐

### 2.1 XXL-JOB 的作用

XXL-JOB 是分布式任务调度平台，在本项目中承担：

- **统一管理定时任务**：注册、触发、停止、调度日志都在控制台完成；
- **分片广播（Sharding Broadcast）**：一次调度把任务分发给所有注册的执行器实例，每个实例拿到不同的 `shardIndex / shardTotal`（[FollowingCountShardingXxlJob.java:48-50](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/java/com/quanxiaoha/xiaohashu/data/align/job/FollowingCountShardingXxlJob.java#L48-L50)），各实例并行处理各自分片、互不冲突；
- 失败重试、告警、执行日志等运维能力。

### 2.2 数据对齐的目的是什么

**背景**：点赞、收藏、关注、发布都是高频操作。若每次操作都实时更新计数表（`t_user_count` / `t_note_count`），写放大严重，且高并发下计数容易漂移。

**方案（增量记录 + 次日重算对齐）**：

```text
当天：
  用户操作 → MQ → data-align 消费者
    → 只把"变更记录"写入 按日期+分片 的临时表（t_data_align_*_count_temp_yyyyMMdd_分片）
    → 不写最终计数，只记"谁/哪篇笔记今天变了"

次日：
  对齐任务（XXL-JOB 分片广播）读取临时表
    → 从源表（t_following、t_note_like 等）重新 count 出准确值
    → 回写计数表 t_user_count / t_note_count + 更新 Redis 计数缓存
    → 删除已处理的临时表记录
```

**目的**：保证计数**最终一致**——实时链路偶发丢失/偏差都不可怕，次日对齐会用源表重算修正。

### 2.3 分片存储（写侧）

- 临时表按 **日期 + 分片序号** 拆分（分片数 `table.shards`，默认 3，支持 Nacos 动态刷新，见 [TableConfig.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/java/com/quanxiaoha/xiaohashu/data/align/config/TableConfig.java)）；
- 消费者计算 `hashKey = id % tableShards`（id 是 noteId 或 用户ID），写入对应分片表（[TodayNoteLikeIncrementData2DBConsumer.java:88](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/java/com/quanxiaoha/xiaohashu/data/align/consumer/TodayNoteLikeIncrementData2DBConsumer.java#L88)）；
- 目的：单表数据量可控、可并行处理、可独立清理。

### 2.4 分片对齐（读侧）

- 对齐任务用 XXL-JOB **分片广播**：每个执行器实例处理自己 `shardIndex` 对应的分片表；
- 并行度 = 实例数 = 分片数（分片广播需配置路由策略为"分片广播"；若只有 1 个实例，`shardTotal=1` 只处理分片 0）。

## 3. 为什么 MQConstants 用接口实现

### 3.1 现状

各服务 `constant` 包下的 `MQConstants` 都是 **`public interface`**，内部全是 `String XXX = "..."`（Topic / Tag），例如 [note 的 MQConstants](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/constant/MQConstants.java)、[data-align 的 MQConstants](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/java/com/quanxiaoha/xiaohashu/data/align/constant/MQConstants.java)。

### 3.2 为什么用接口

1. **字段天然是常量**：接口中的字段默认 `public static final`，无需写修饰符，代码最简。
2. **不能实例化**：接口无法 `new`，天然符合"纯常量集合"的定位。
3. **集中管理、消除魔法字符串**：Topic/Tag 统一收敛到一个类，改一处全局生效，跨服务消费同一 Topic 时命名一致。
4. **编译期内联**：`static final` 字符串编译时直接内联到使用处，无运行时开销。
5. 可被 `implements` 或接口 `extends` 复用（本项目未用，但保留了扩展性）。

### 3.3 注意点

- 业界部分观点认为"常量接口"是反模式（接口语义是"能力契约"而非"常量容器"），更推荐 `final class + private 构造器`。本项目用接口实现更简洁，两种方式皆可，团队统一即可；若改用 class，务必加 `private` 构造器防止被实例化。

## 4. 数据对齐服务的布隆过滤器

### 4.1 作用

1. **幂等去重**：判断"该条增量变更当天是否已落库"，已落库则跳过——防 MQ 重复消费、防同一事件被多次写入临时表；
2. **挡在 DB 之前**：布隆过滤器判断"不存在"才落库，绝大多数重复事件在数据库之前就被拦下，减轻 DB 压力。

### 4.2 存储什么

基于 RedisBloom 模块的 `BF` 命令（Lua 脚本：不存在则 `BF.ADD` 空串占位 + `EXPIRE 20h`，再 `BF.EXISTS` 判断，见 [bloom_today_note_like_check.lua](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/resources/lua/bloom_today_note_like_check.lua)）。

- **key**：带日期，形如 `bloom:dataAlign:note:like:noteIds{date}`（构造方法见 [RedisKeyConstants.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/java/com/quanxiaoha/xiaohashu/data/align/constant/RedisKeyConstants.java)）；
- **value**：当天已处理对象的 ID（`noteId` / `noteCreatorId` / `userId`）。布隆过滤器只存**哈希指纹**，不存原始值、不能反查；
- 每个 Bloom 只存**一个维度**的 ID，粒度与"每日一张临时表"一致。

当前 Bloom 清单：

| 业务 | Bloom Key 前缀 | 存储内容 |
|---|---|---|
| 笔记点赞 | `bloom:dataAlign:note:like:noteIds{date}` / `...userIds{date}` | noteId / noteCreatorId（双 Bloom） |
| 笔记收藏 | `bloom:dataAlign:note:collect:noteIds{date}` / `...userIds{date}` | noteId / noteCreatorId（双 Bloom） |
| 笔记发布/删除 | `bloom:dataAlign:user:note:operators:{date}` | 发布者 userId |
| 用户关注 | `bloom:dataAlign:user:follows:{date}` | 源用户 userId |
| 用户粉丝 | `bloom:dataAlign:user:fans:{date}` | 目标用户 userId |

### 4.3 实现要点

- **先落库、后登记**：判断不存在才 insert，insert 成功后才 `BF.ADD`，保证"已登记 = 已落库"；
- **误判方向**：布隆过滤器误判只会"误判已存在"（假阳性），不会漏判；误判会导致该条增量跳过落库，极端情况下该维度少对齐一次，可接受；
- **双 Bloom 拆分**：点赞/收藏消费者按"笔记 ID + 发布者 ID"各用一个 Bloom（[TodayNoteLikeIncrementData2DBConsumer.java:66-124](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/java/com/quanxiaoha/xiaohashu/data/align/consumer/TodayNoteLikeIncrementData2DBConsumer.java#L66-L124)），笔记维度和发布者维度各自独立判断与落库，解决"同发布者多篇笔记撞唯一索引回滚"的问题（详见 04-问题排查与记录/开发问题记录.md 第 5 节）。
