## 1. 先说两句：为什么代码里全是英文缩写？

Java 后端项目里，开发者习惯用 `DTO`、`VO` 这类缩写给"装数据的类"命名，目的是**看一眼类名，就知道这个对象是干嘛用的、给谁用的**。

看不懂缩写没关系，先记住一句话：**它们本质上都只是"装数据的盒子"，区别只在于"这个盒子是给谁看的、要装到哪里去"**。下面逐个拆开讲。

---

## 2. DTO（数据传输对象）

### ① 一句话大白话（生活类比）

DTO 就是"**送资料用的信封**"：A 部门要把"手机号"交给 B 部门，就封一个信封（DTO），里面只装要传的几样东西，信封外面贴好地址，交给信使（Feign）送过去。信封里可以塞卡片，但**不能放"怎么送"的说明书**——DTO 里只放数据，不放逻辑。

### ② 正式定义

DTO（Data Transfer Object，**数据传输对象**）是用于在"层与层之间"或"服务与服务之间"传递数据的对象。它**只包含数据字段及其读写方法（getter/setter），不包含任何业务逻辑**。定义 DTO 的目的：只传递本次需要的数据，避免把整个数据库实体对象直接暴露出去。

### ③ 在本项目中的位置 / 示例

本项目是微服务架构，服务之间用 Feign 做远程调用（如 auth 服务调 user 服务的用户登录），**调用的入参和返回值都定义成 DTO 类**：

- **位置**：放在被调方服务的 **`*-api` 模块**下，按用途分两个包——`dto.req`（入参）和 `dto.resp`（出参）；调用方与服务提供方**共用同一份类**，保证字段两边对得上。
- **实例**：`xiaohashu-user-api` 里的 `RegisterUserReqDTO`（注册入参，含 phone 手机号）、`FindUserByPhoneReqDTO`（按手机号查用户入参）、`FindUserByPhoneRspDTO`（查用户出参，含 id、password）。
- **注意事项**：DTO 要能被 Jackson 序列化（通常加 `@Data` 等 Lombok 注解），因为 Feign 会把 DTO 转成 JSON 字符串在 HTTP 上传输，不能序列化就传不过去。

## 3. VO（视图对象）

### ① 一句话大白话（生活类比）

VO 就是"**给前台看的展示柜**"：后台仓库里存了很多货（数据库数据），不能把整个仓库直接搬给前台看，于是挑几样摆进一个展示柜（VO），**前台只能看到展示柜里摆出来的东西**——多余的字段（比如密码的盐）不会露出去。

### ② 正式定义

VO（View Object，**视图对象**）是用于表现层（展示层）的对象，用来封装"页面/前端要显示的数据"，在控制层（Controller）和视图层之间传递。它决定"**前端能看到哪些字段、字段叫什么名字**"，与数据库表结构**没有一一对应关系**。

### ③ 在本项目中的位置 / 示例

Controller 接收前端请求参数、或把数据返回给前端时，常定义成 VO：

- **位置**：放在各服务模块的 `model/vo` 包下。
- **实例**：`xiaohashu-auth` 里的 `UserLoginReqVO`（登录请求参数：phone、type、password、code 等）、`UpdatePasswordReqVO`（修改密码请求参数）；`xiaohashu-user-biz` 里的 `UpdateUserInfoReqVO`（修改用户信息请求参数）。
- **与 DTO 的分工**：面向"外部用户/前端"的数据用 VO；面向"服务之间内部传递"的数据用 DTO——一个朝外、一个朝内，别混用。

## 4. DO（数据对象）

### ① 一句话大白话（生活类比）

DO 就是"**和数据库表格一一对应的账本**"：数据库里有一张表（比如 `t_user` 用户表），代码里就有一个 DO 类（比如 `UserDO`），**表的每一列就是 DO 里的一个字段**。MyBatis 把"表里的行"和"DO 对象"互相转换——查出来的行变成 DO 对象，插进去的 DO 对象变成一行。

### ② 正式定义

DO（Data Object，**数据对象**）是**与数据库表结构一一对应**的持久化对象。它只用来"装载数据库一行数据"，字段名、类型基本和表字段一致，**不携带任何业务逻辑**，只负责在"数据库 ↔ Java 程序"之间搬运数据（ORM 映射的载体）。

### ③ 在本项目中的位置 / 示例

本项目用 MyBatis 操作 MySQL，每个 Mapper 对应的实体类就是 DO：

- **位置**：放在各服务 biz 模块的 `domain/dataobject` 包下（也有项目叫 `entity`、`po`、`model`，意思一样）。
- **实例**：`xiaohashu-user-biz` 里的 `UserDO`（用户表实体，字段有 id、phone、password、nickname、avatar 等）、`UserRoleDO`（用户角色关系表实体）；`xiaohashu-user-relation-biz` 里的 `FollowingDO`（关注表实体）、`FansDO`（粉丝表实体）；`xiaohashu-count-biz` 里的 `UserCountDO`（用户计数表实体）。
- **与 DTO / VO 的区别**：

| 类型 | 对应谁 | 一句话 |
|------|--------|--------|
| DO | 数据库表 | "账本"，表有几列它就有几个字段 |
| DTO | 服务之间 / 层之间 | "信封"，只装要传的字段 |
| VO | 前端页面 | "展示柜"，只摆给前端看的字段 |

- **转换链条**：查库时 DO 从数据库出来 → 转成 DTO 发给别的服务（RPC）→ 转成 VO 返回给前端。本项目代码里到处是 `DO → DTO → VO` 的 Builder 转换（如 `findByIds` 里 `UserDO` 转 `FindUserByIdRspDTO`）。

## 5. RPC（远程过程调用）

### ① 一句话大白话（生活类比）

RPC 就是"**打电话叫别的部门办事**"：你在 A 服务里，想让 B 服务帮忙查个用户，不用自己写一大堆 HTTP 连接代码，像调用**本地的普通方法**一样调用就行——底层框架（本项目是 OpenFeign）自动帮你把请求"打包、送过去、取回结果"。就像你打电话给前台："帮我查一下 10086 号用户"，电话线（Feign）自动连通对方部门。

### ② 正式定义

RPC（Remote Procedure Call，**远程过程调用**）是一种"调用远程服务的方法，就像调用本地方法一样"的通信方式。在微服务架构中，服务拆分成多个进程部署在不同机器上，A 服务要调用 B 服务的功能，就用 RPC 框架（OpenFeign、Dubbo、gRPC 等）发起网络调用，并完成**参数的序列化、传输、反序列化**，让开发者无感知底层网络细节。

### ③ 在本项目中的位置 / 示例

本项目服务间调用全部基于 **OpenFeign + Nacos** 实现 RPC：

- **接口契约**：每个服务暴露一个 `*-api` 模块，里面定义 Feign 接口（如 `UserFeignApi`、`RelationFeignApi`），调用方依赖该模块后，**像调用本地接口一样调用远程服务**。
- **服务发现**：Nacos 是"通讯录"，Feign 按服务名（如 `xiaohashu-user`）找到对方的 IP 端口，配合 LoadBalancer 做负载均衡。
- **实例**：`RelationServiceImpl.follow` 里 `userRpcService.findById(followUserId)`（调用 user 服务校验目标用户是否存在）；`findByIds` 里批量调用 `userRpcService.findByIds(userIds)` 查多个用户信息；`UserServiceImpl` 里调用分布式 ID 服务生成用户 ID。
- **相关概念**：RPC 的入参/出参一般用 **DTO**（见第 2 条），因为要序列化成 JSON 在网络上传输；**RPC 与 HTTP 接口的区别**——RPC 是"服务内部"的调用约定（走 Feign），HTTP 接口是"对外部前端"暴露的入口（走 Controller + Gateway 网关）。

## 6. Req / Rsp（请求 / 响应后缀）

### ① 一句话大白话（生活类比）

`Req`（Request）= "**进门用的申请表**"，`Rsp`（Response）= "**出门拿的结果单**"。凡是类名里带 `Req` 的，就是"调用接口时我要交给对方的东西"；带 `Rsp` 的，就是"对方处理完还给我的东西"。看到它们就能一秒判断：**这个类是入参还是出参**。

### ② 正式定义

- **Req（Request，请求）**：接口/方法的**入参**后缀。标注"这个对象是调用方发过来的数据"。
- **Rsp（Response，响应）**：接口/方法的**出参**后缀。标注"这个对象是处理完要返回的数据"。（有些人写成 `Resp`，一个意思，本项目统一用 `Rsp`。）

### ③ 在本项目中的位置 / 示例

- **服务间（DTO）**：放在 `*-api` 模块的 `dto.req` / `dto.resp` 两个包下——入参类叫 `XxxReqDTO`，出参类叫 `XxxRspDTO`。例：`RegisterUserReqDTO`（注册入参）、`FindUserByIdRspDTO`（查用户出参）。
- **前端（VO）**：放在 biz 模块 `model/vo` 包下——入参类叫 `XxxReqVO`，出参类叫 `XxxRspVO`。例：`FollowUserReqVO`（关注入参：followUserId）、`FindFollowingUserRspVO`（关注列表出参）。

## 7. 2DB（MQ 落库后缀）

### ① 一句话大白话（生活类比）

`2DB` = "**to Database（去数据库）**"。看到 Topic 名字带 `2DB`，就知道这条 MQ 消息的使命是"**把数据写进 MySQL**"，相当于快递单上写着"最终派送目的地：数据库"。

### ② 正式定义

`2DB` 是项目里 **RocketMQ Topic 命名的固定后缀**，表示该消息由消费者处理时**负责落库（写入数据库）**。它是一条"二级消息"：上游只把变更发给"计数 Topic"（先更新 Redis），再由消费者转发一条带 `2DB` 后缀的 Topic 给"落库消费者"（最终把计数同步到 MySQL）。

### ③ 在本项目中的位置 / 示例

计数服务（`xiaohashu-count`）的 [MQConstants](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-count/xiaohashu-count-biz/src/main/java/com/quanxiaoha/xiaohashu/count/biz/constant/MQConstants.java) 里 4 个 Topic 成对出现：

| 一级 Topic（先更新 Redis） | 二级 Topic（落库） | 谁消费 |
|--------------------------|-------------------|--------|
| `CountFansTopic` | `CountFans2DBTopic` | `CountFans2DBConsumer`（`insertOrUpdateFansTotalByUserId`） |
| `CountFollowingTopic` | `CountFollowing2DBTopic` | `CountFollowing2DBConsumer` |
| `CountNoteLikeTopic` | `CountNoteLike2DBTopic` | `CountNoteLike2DBConsumer` |
| `CountNoteCollectTopic` | `CountNoteCollect2DBTopic` | `CountNoteCollect2DBConsumer` |

> 设计意图：**Redis 快写 + 落库慢写分离**。点赞/关注的瞬间，先把计数加进 Redis（毫秒级返回），数据库的写入走 MQ 异步慢慢做，避免每次操作都同步写库拖慢接口。

## 8. 一句话速查：DTO / VO / DO 怎么选

> 纠结"该建什么对象"时，对号入座即可：

| 场景 | 用哪个 | 一句话 |
|------|--------|--------|
| 数据库一行数据 ↔ Java | **DO** | 跟表结构一一对应，只做搬运 |
| 服务 A 调服务 B（Feign）的入参 | **ReqDTO** | 跨服务，只装要传的字段 |
| 服务 A 调服务 B（Feign）的出参 | **RspDTO** | 跨服务，返回给对方的字段 |
| 前端调后端接口的入参 | **ReqVO** | 面向外部，只收前端该传的字段 |
| 后端返回给前端的出参 | **RspVO** | 面向外部，只露前端该看的字段 |

**记住 3 个原则**：
1. **看方向**：入参是 `Req`，出参是 `Rsp`；
2. **看边界**：跨服务/跨层用 `DTO`，对前端/对外用 `VO`，对数据库用 `DO`；
3. **别乱混**：不要把 DO 直接返回给前端（密码字段会泄露），也不要把 VO 当 DO 存库（少了字段会丢数据）。
