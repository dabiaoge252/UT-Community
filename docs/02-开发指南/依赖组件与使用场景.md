## 先读 30 秒：什么是组件和依赖

写 Java 项目就像**搭积木**：连数据库、发 HTTP 请求、做缓存、生成唯一 ID……这些功能，全世界早就有大佬写好现成的"积木块"了，我们管这些积木块叫**组件**（也叫依赖、三方库、框架）。项目只要在 `pom.xml`（Maven 的"购物清单"）里声明"我要买哪块积木"，再把官方文档翻一翻，就能直接用，完全不用从零造轮子。

本清单里几个高频词，先混个脸熟：

| 名词 | 大白话 |
|------|--------|
| `pom.xml` | Maven 项目的"购物清单"，`<dependency>` 就是清单上的一项 |
| **Starter** | Spring 生态的"套餐"：引入一个 starter，配套组件和自动配置一起到位 |
| **BOM** | 版本"管家"：统一管理一堆组件的版本号，你就不用一个个写版本了 |
| **微服务** | 把一个大系统拆成多个小服务（auth、user、note……），各管一块，互相通过 HTTP 调用 |

> 看表技巧：后面 14 类组件表格里，**"本项目使用位置"列是重点**——它告诉你真实代码在哪，想深入了解时直接点链接跳过去看。

## 一、核心框架

> **这是啥**：这三兄弟是整套项目的"地基操作系统"。**Spring Boot** 是毛坯房——让一个 Java 程序快速变成"能对外提供服务"的应用（内嵌服务器、自动配置）；**Spring Cloud** 是装修方案——提供微服务标配的网关、负载均衡、服务调用等能力；**Spring Cloud Alibaba** 是阿里巴巴出的进口家具——里面的 Nacos 等组件是国人用起来最顺手的。
> **为什么需要它**：没有它们，你要自己写服务器、写配置加载、写服务发现，上万行代码才能把项目跑起来；有了它们，一个注解、一个 starter 就搞定。

| 组件 | 功能 | 适用场景 | 本项目使用位置 |
|------|------|---------|----------------|
| **Spring Boot 3.0.2** | 自动配置、内嵌容器、起步依赖，快速搭建独立应用 | 所有 Spring 应用的基座 | 所有服务的启动类（`@SpringBootApplication`） |
| **Spring Cloud 2022.0.0** | 微服务基础设施（网关、负载均衡、调用等） | 分布式微服务架构 | 父 pom 统一引入 BOM |
| **Spring Cloud Alibaba 2022.0.0.0** | 阿里系微服务组件（Nacos 等） | 微服务注册发现 / 配置管理 | 父 pom 统一引入 BOM |

## 二、注册与配置中心

> **这是啥**：Nacos 身兼两职。**注册中心** = 服务的"通讯录"：每个服务启动时在 Nacos 上登记自己的名字和地址，别的服务想调用时按名字一查就找到，不用写死 IP；**配置中心** = 项目的"中央遥控器"：配置文件集中放 Nacos 上，改了不用重启服务就能生效（动态刷新）。
> **为什么需要它**：微服务几十个，调用方如果写死 IP，一扩容、一迁移就全乱套；配置写死在各服务里，改一处要重启一大片。`spring-cloud-starter-bootstrap` 是配套的"开机先连配置中心"开关，没它 Nacos Config 加载不了。

| 组件 | 功能 | 适用场景 | 本项目使用位置 |
|------|------|---------|----------------|
| **Nacos Discovery**（`spring-cloud-starter-alibaba-nacos-discovery`） | 服务注册与发现，调用方按服务名找到实例 | 微服务之间相互调用 | auth、gateway、user-biz、oss-biz、kv-biz、distributed-id-generator-biz 全部引入 |
| **Nacos Config**（`spring-cloud-starter-alibaba-nacos-config`） | 配置中心，配置统一管理、动态刷新 | 多服务共享配置、运行时改配置 | auth（`@NacosValue` 动态读取限流阈值）、oss-biz |
| **spring-cloud-starter-bootstrap** | 开启 `bootstrap.yml` 加载机制，让应用启动时先连配置中心 | Nacos Config 场景下的必配项 | 所有引入 Nacos 的服务 |
| ~~nacos-config-spring-boot-starter~~（`com.alibaba.boot`） | 旧版 Nacos 配置中心 starter | 老项目兼容 | 仅保留在父 pom `dependencyManagement`，auth 中已注释停用 |

## 三、网关与远程调用

> **这是啥**：**Spring Cloud Gateway** = 整个系统的"小区大门保安"，所有外部请求先进大门，保安检查（登录了没、有没有权限）再放行到里面的服务；**OpenFeign** = 服务之间的"对讲机"，本服务想调用另一个服务，写个接口方法就能像打本地电话一样调用，底层自动帮你发 HTTP 请求；**LoadBalancer** 是"指挥员"，多个实例时帮你在其中选一个（负载均衡）；**feign-form** 是给对讲机加的"快递功能"，让 Feign 能传文件。
> **为什么需要它们**：没有网关，每个服务都要自己做登录校验、容易各自为政；没有 Feign，服务间调用要手写一大坨 HTTP 连接代码。

| 组件 | 功能 | 适用场景 | 本项目使用位置 |
|------|------|---------|----------------|
| **Spring Cloud Gateway**（`spring-cloud-starter-gateway`） | 响应式 API 网关：路由转发、统一鉴权、限流 | 微服务统一入口 | [xiaohashu-gateway](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-gateway)（路由 + Sa-Token 登录/权限校验 + userId 透传） |
| **OpenFeign**（`spring-cloud-starter-openfeign`） | 声明式 HTTP 客户端，像调本地方法一样调远程接口 | 服务间 RPC 调用 | `UserFeignApi`、`FileFeignApi`、`KeyValueFeignApi`、`DistributedIdGeneratorFeignApi`，配合 `@EnableFeignClients` 开启 |
| **Spring Cloud LoadBalancer**（`spring-cloud-starter-loadbalancer`） | 客户端负载均衡，Feign/网关按服务名选择实例 | 多实例服务调用 | 所有 api 模块 + gateway 引入 |
| **feign-form / feign-form-spring** | 让 Feign 支持 `multipart/form-data` 文件上传 | Feign 传文件 | oss-api 的 `FeignFormConfig`（`SpringFormEncoder`），配合 `FileFeignApi` 上传 |

## <a id="ch4"></a>四、认证鉴权

> **这是啥**：**Sa-Token** = 登录发"门禁卡"（token）的系统。用户登录成功发一张卡，之后每次请求都出示这张卡，网关一验卡就知道"你是谁、有没有权限进这个门"；**Sa-Token 整合 Redis** 是把"发卡记录"存在 Redis 里，多台机器（网关、auth 服务）都能查到同一张卡，实现分布式会话共享；**Sa-Token 网关版** 是专门给响应式网关（WebFlux）用的版本；**Spring Security Crypto** 只是借用了 Spring Security 家的一个加密算法（BCrypt）给密码"加盐腌制"后存库，防止数据库泄露后密码明文暴露。
> **为什么需要它**：互联网应用不能让人随便登录、随便访问别人数据，必须有一套"发卡 + 验卡"机制；密码也不能明文存，否则数据库一泄露全完。

| 组件 | 功能 | 适用场景 | 本项目使用位置 |
|------|------|---------|----------------|
| **Sa-Token**（`sa-token-spring-boot3-starter`） | 轻量级认证鉴权框架：登录、token 签发、权限校验 | 单体/微服务登录鉴权 | auth 服务 `StpUtil.login()` 签发 token |
| **Sa-Token 整合 Redis**（`sa-token-redis-jackson`） | 会话信息存 Redis，token 可跨服务共享 | 分布式会话共享 | auth、gateway 引入，网关无状态校验登录态 |
| **Sa-Token 网关版**（`sa-token-reactor-spring-boot3-starter`） | 响应式环境下的 Sa-Token（支持 WebFlux） | Spring Cloud Gateway 鉴权 | gateway 的 `SaTokenConfigure`（`SaReactorFilter`） |
| **Spring Security Crypto**（`spring-security-crypto`） | 仅提供 BCrypt 密码加密算法（不含完整 Security） | 密码加密存储 | auth 的 `PasswordEncoderConfig`（`BCryptPasswordEncoder`） |

## 五、数据存储与访问

> **这是啥**：不同类型的数据仓库，各存各擅长的东西——**MySQL** 是严谨的"档案柜"（关系型数据库），数据规规矩矩按表格存，强一致、支持事务，适合用户、角色这些核心数据；**Redis** 是"便签条"（键值缓存），存在内存里读写飞快，适合验证码、缓存、计数；**Cassandra** 是"大仓库"（分布式 NoSQL），能扛海量写入，适合笔记正文这种大文本；**MyBatis** 是"翻译官"，把 Java 方法翻译成 SQL 去查库（MyBatis Generator 是它的"自动翻译生成器"，按表结构自动生成代码）；**Druid** 是连接 MySQL 的"水池"（数据库连接池），管着连接的复用和监控，避免每次都新建连接。
> **为什么需要它们**：数据是项目的命根子。什么样的数据用什么样的仓库最合适——核心业务数据要强一致（MySQL），热点数据要快（Redis/本地缓存），海量文本要扛得住写入（Cassandra）。

| 组件 | 功能 | 适用场景 | 本项目使用位置 |
|------|------|---------|----------------|
| **MySQL + MyBatis**（`mybatis-spring-boot-starter` + `mysql-connector-java`） | 关系型数据库访问（ORM + SQL） | 强一致、事务型业务数据 | user-biz（用户/角色/权限表）、leaf 库（号段表） |
| **MyBatis Generator**（`mybatis-generator-maven-plugin`） | 根据表结构自动生成 DO / Mapper | 快速生成数据层代码 | user-biz 的 `generatorConfig.xml` |
| **Druid**（`druid-spring-boot-3-starter` / `druid`） | 数据库连接池 + 监控 | 高并发数据库连接管理 | user-biz（Spring 集成版）、distributed-id-generator-biz（原生版 `DruidDataSource`） |
| **Redis**（`spring-boot-starter-data-redis` + `commons-pool2`） | 键值缓存、验证码、会话、原子计数 | 缓存热点数据、分布式状态 | auth（验证码）、user-biz（角色权限、ID 自增遗留）、gateway（角色/权限缓存） |
| **Cassandra**（`spring-boot-starter-data-cassandra`） | 分布式 NoSQL，高可用、易水平扩展 | 大文本、海量写入、弱事务数据 | kv-biz 存储"笔记内容"（`NoteContentDO` + `NoteContentRepository`） |

### 数据存储补充：Redis Bitmap 与布隆过滤器（Bloom Filter）

> **Bitmap（位图）** = "一张只画黑白格子的纸"。每个位置只能存 0 或 1，一个键就能表示几亿个状态，内存却极小。典型场景：签到（今天签没签）、在线状态、登录天数统计。**本项目目前没有直接用 Bitmap**（"是否点赞过"用布隆过滤器实现），但它是面试高频题：`SETBIT` 写入某一位、`GETBIT` 读取某一位、`BITCOUNT` 统计 1 的个数、`BITOP` 做位运算（与/或）。

> **布隆过滤器（Bloom Filter）** = "会误报、不会漏报的筛子"。用来快速判断"某个元素**一定不在** / **大概率在**"某个大集合里：说**不存在就一定不存在**，说**存在只是可能存在**（有误判率）。它不存原始数据、只存哈希后的位，所以**内存占用极小**，代价是**有误判** + **不能删除元素**。
> **本项目用它干嘛**：判断"某用户是否点赞/收藏过某篇笔记"，给点赞/取消点赞、收藏/取消收藏接口做**幂等判重**。用 RedisBloom 模块的 `BF.EXISTS` / `BF.ADD` 命令，并且**包在 Lua 脚本里**执行（判重 + 写入原子完成，防止并发重复点赞导致计数多 +1）。

| Redis 命令 / 结构 | 作用 | 本项目用法 |
|------|-----------|-----------|
| `BF.EXISTS key item` | 判断元素是否（可能）存在：1 存在 / 0 不存在 | `bloom_note_like_check.lua` 判重（点赞/取消点赞） |
| `BF.ADD key item` | 把元素加入布隆过滤器 | 点赞/收藏时写入 |
| `EXISTS key` | 判断布隆过滤器本身是否存在（不存在返回 -1，Java 端从 DB 全量重建） | 脚本开头兜底 |
| `EXPIRE key seconds` | 给布隆过滤器设过期时间（防止无限膨胀） | `bloom_add_note_like_and_expire.lua` 设"保底 1 天 + 随机秒" |
| Bitmap：`SETBIT` / `GETBIT` / `BITCOUNT` / `BITOP` | 位图读写 / 统计 / 运算 | ❌ 未使用（可作扩展） |

**项目真实代码**（[bloom_note_like_check.lua](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/resources/lua/bloom_note_like_check.lua)）：

```lua
local key = KEYS[1]      -- 用户点赞笔记的布隆过滤器 Key
local noteId = ARGV[1]   -- 笔记 ID

-- 1. 布隆过滤器不存在（Redis 重启或已过期），返回 -1，Java 端先从 DB 全量同步重建
local exists = redis.call('EXISTS', key)
if exists == 0 then
    return -1
end

-- 2. 判断该笔记是否点赞过（1 表示已点赞，0 表示未点赞）
local isLiked = redis.call('BF.EXISTS', key, noteId)
if isLiked == 1 then
    return 1
end

-- 3. 未点赞 → 加入布隆过滤器，返回 0
redis.call('BF.ADD', key, noteId)
return 0
```

Java 端调用（[NoteServiceImpl.likeNote](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L639-L760)）：脚本返回 1（已点赞）/ 0（点赞成功）/ -1（过滤器不存在，需先同步重建），再按分支走——已点赞抛"重复点赞"异常，-1 则先 `bloom_batch_add_note_like_and_expire.lua` 全量重建再重新判重。

**布隆过滤器的典型用途**（本项目体现前两个）：
1. **缓存穿透防护**：查询前先问"这个 ID 一定不存在吗"，一定不存在直接返回，避免恶意请求打穿缓存打到数据库；
2. **幂等判重**：点赞/收藏接口先查"是否点过"，点过就不重复处理（本项目场景）；
3. **超大集合快速判断**：判断手机号/黑名单是否在亿级名单里，内存友好。

**布隆过滤器 vs Bitmap**：Bitmap 精确、一位一位存，能准确知道每个位置的状态；布隆过滤器用"多个哈希位 + 数组"组合判断，会误判但极省内存、能存海量元素。判断"某元素是否在大集合里"用布隆过滤器；判断"某个具体位置的状态"用 Bitmap。

## 六、分布式 ID 生成

> **这是啥**：**美团 Leaf** = 一台"全局唯一编号机"，保证所有服务生成的 ID（用户 ID、笔记 ID 等）都不重复。它有两种出号方式：**号段模式** = "批发号段"，一次从数据库领一批号（比如 1~1000）放内存慢慢发，用完再去领，省得每次生成都查库；**雪花模式** = 用"时间戳 + 机器号（workerId）+ 序号"拼出一个唯一号，纯计算不用查库，更快。**ZooKeeper + Curator** 是"排队叫号机"，负责给每台机器分一个全局唯一的 workerId；**perf4j** 是个小"秒表"，统计号段更新耗时；**commons-io** 就是普通的 IO 工具库（这里用来把 workerId 落盘）。
> **为什么需要它**：多台机器同时生成 ID，如果各生成各的（比如各用自增），一定会撞号；而数据库自增太慢，扛不住高并发，所以需要一台"专门发号的机器"。

| 组件 | 功能 | 适用场景 | 本项目使用位置 |
|------|------|---------|----------------|
| **美团 Leaf**（自研封装） | 分布式唯一 ID：号段模式（DB 预取 + 双 Segment）+ 雪花模式 | 全局唯一、高性能 ID | `xiaohashu-distributed-id-generator` 服务，user-biz 注册时生成用户 ID / 工大社区号 |
| **ZooKeeper + Curator**（`zookeeper` + `curator-recipes`） | 雪花模式协调器：为每个节点分配全局唯一 workerId | 雪花算法多节点部署 | `SnowflakeZookeeperHolder`（通过 ZK 申请 workerId） |
| **perf4j** | 轻量性能统计工具 | 统计方法耗时（用于监控号段更新性能） | `SegmentIDGenImpl` 中 `Slf4JStopWatch` |
| **commons-io** | IO 工具库 | 文件/流操作 | distributed-id-generator-biz |

### ZooKeeper + Curator 详解（雪花 workerId 协调器）

> **这是什么**：**ZooKeeper（ZK）** = 分布式协调服务，可以理解成"分布式系统的公告栏 + 通讯录"——多台机器要协调一致（谁当领导、谁用几号、谁在线），都在这里登记和查看。**Curator** 是 ZK 官方推荐的高级客户端（把复杂的 API 封装得简单好用，还带重试策略），本项目用 `zookeeper` + `curator-recipes` 两个依赖。

> **为什么需要它**：雪花算法 64 位 ID 由"时间戳 + workerId + 序列号"拼成，**workerId（机器号）必须全局唯一**，否则多台机器生成相同时间戳 + 相同序列号时会撞号。多节点部署时谁给每台机器发一个不重复的 workerId？——交给 ZK。

#### ZK 核心概念（面试必背）

| 概念 | 大白话 | 说明 |
|------|--------|------|
| **数据模型** | 树形目录 | 数据以"节点（znode）"组织成树，路径如 `/snowflake/{leaf.name}/forever/ip:port-000000001` |
| **持久节点**（PERSISTENT） | 公告栏贴的纸 | 客户端断开也一直在，直到手动删除 |
| **持久顺序节点**（PERSISTENT_SEQUENTIAL） | 排号机 | 创建时自动在名字末尾追加递增序号 `-000000001`，**天然不重复**（本项目用它分配 workerId） |
| **临时节点**（EPHEMERAL） | 在线状态牌 | 客户端会话断开自动消失，适合服务注册/心跳探活 |
| **Watcher 监听** | 盯着公告栏 | 客户端对节点注册监听，节点变化时收到通知（本项目没用到，靠定时上报） |
| **典型场景** | — | 服务注册发现、配置中心、分布式锁、Leader 选举、workerId 分配 |

#### 本项目怎么用 ZK（SnowflakeZookeeperHolder）

[SnowflakeZookeeperHolder.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-distributed-id-generator/xiaohashu-distributed-id-generator-biz/src/main/java/com/quanxiaoha/xiaohashu/distributed/id/generator/biz/core/snowflake/SnowflakeZookeeperHolder.java#L48-L107) 完整流程：

1. **连接 ZK**：用 Curator 建立连接，带重试策略（`RetryUntilElapsed`）+ 连接/会话超时配置；
2. **首次启动**：根节点 `/snowflake/{leaf.name}/forever` 不存在 → 用 `PERSISTENT_SEQUENTIAL` 模式创建自己的节点 `ip:port-000000000`（[createNode](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-distributed-id-generator/xiaohashu-distributed-id-generator-biz/src/main/java/com/quanxiaoha/xiaohashu/distributed/id/generator/biz/core/snowflake/SnowflakeZookeeperHolder.java#L144-L151)）——**节点名后缀序号就是 workerId**（第一台 0、第二台 1……顺序节点保证不重复）；
3. **节点数据 = 本机信息**：`Endpoint`（ip、port、当前时间戳）转 JSON 存在节点里（[buildData](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-distributed-id-generator/xiaohashu-distributed-id-generator-biz/src/main/java/com/quanxiaoha/xiaohashu/distributed/id/generator/biz/core/snowflake/SnowflakeZookeeperHolder.java#L170-L175)），并**每 3 秒定时上报**一次本机时间戳（`updateNewData` → `setData`）；
4. **重启复用**：先查 `forever` 下有没有自己的节点 → 有就**复用原 workerId**，并 `checkInitTimeStamp` 校验"**本机当前时间不能早于节点里记录的上次时间**"（防时钟回拨）；没有就新建节点拿新 workerId；
5. **本地兜底**：workerId 同时落盘到本地 `workerID.properties`（`updateLocalWorkerID`）——**ZK 挂掉时读本地文件恢复 workerId 保证能启动**；ZK 不可用且无本地文件 → init 失败 → 降级 `ZeroIDGen`（零生成器，牺牲唯一性保可用）。

> 整个链路的"可靠性三层"：**ZK 分配 workerId（首选）→ 本地文件缓存 workerId（ZK 挂了兜底）→ ZeroIDGen 降级（都不行保启动）**。

#### ZK vs Nacos（本项目同时用了，面试常问）

| | ZooKeeper | Nacos |
|--|-----------|-------|
| 本项目角色 | 雪花 workerId 分配（**协调器**） | 注册中心 + 配置中心 |
| 一致性 | CP（强一致） | 注册 AP / 配置 CP，可切换 |
| 特点 | 数据树 + 顺序/临时节点，通用协调能力 | 更聚焦"注册发现 + 动态配置"，支持 `@RefreshScope` 热刷新 |

> 一句话：**Nacos 管"服务在哪、配置怎么变"，ZK 管"谁分到几号 workerId"**，各司其职。

## 十一、异步并发编排（CompletableFuture，JDK 自带）

> **这是啥**：JDK 自带的"多线程拼装师"。一个接口要同时查两样东西（比如查作者信息 + 查笔记正文），串行做要 100ms + 80ms = 180ms；用 CompletableFuture 把两件事丢给两个线程**并行**做，总耗时只有最慢的那个 ≈ 100ms。
> **为什么需要它**：接口慢 = 用户体验差、数据库连接被长时间占用。把互不依赖的操作并行执行，是提接口速最立竿见影的手段之一。注意它不是第三方组件，是 `java.util.concurrent` 自带的。

> `CompletableFuture` 是 JDK `java.util.concurrent` 自带的异步编程工具（非第三方依赖），用于**异步执行任务**并**编排多个异步结果**（并行、串行、聚合）。项目中用于并发发起多个 RPC 调用，缩短接口耗时。

### 11.1 作用（为什么用它）

- **并行化**：把相互独立的耗时操作（如两个 RPC 调用）同时执行，接口总耗时从"串行之和"降为"最慢的那个"；
- **编排组合**：支持 `allOf`（全部完成）、`anyOf`（任一完成）、`thenApply`（完成后转换）等组合能力；
- **替代手动并发**：相比 `new Thread` + `CountDownLatch`，代码更简洁、可读、可组合。

### 11.2 常用方法（含本项目实际用到的）

| 方法 | 作用 | 是否本项目用到 |
|------|------|--------------|
| `supplyAsync(Supplier, Executor)` | 提交一个**有返回值**的异步任务到指定线程池 | ✅ 并行发起"查用户"“查笔记内容”两个 RPC |
| `completedFuture(value)` | 返回一个**已完成**的结果对象（常用于占位） | ✅ 笔记无内容时给内容 Future 赋初始值 null |
| `allOf(CompletableFuture...)` | 等待**所有**给定 Future 全部完成 | ✅ 等用户信息 + 笔记内容都返回后再组装 |
| `thenApply(Function)` | 完成后对结果做**转换**，返回新的 CompletableFuture | ✅ 组装 `FindNoteDetailRspVO` |
| `join()` | 阻塞获取结果，**不抛受检异常** | ✅ 在 thenApply 里取两个 RPC 的结果 |
| `get()` | 阻塞获取结果，**抛受检异常**（需 try-catch/throws） | ✅ 获取最终组装结果（方法用 `@SneakyThrows` 简化） |
| `runAsync(Runnable, Executor)` | 提交**无返回值**的异步任务 | ❌（写缓存用的是线程池 `submit`） |
| `thenAccept(Consumer)` | 完成后**消费**结果，无返回值 | ❌ |
| `thenCompose(Function)` | 任务**串联**（前一个结果作为后一个输入） | ❌ |
| `exceptionally` / `whenComplete` | **异常兜底** / 完成回调 | ❌（当前未做，建议补充） |
| `anyOf(...)` | 任一 Future 完成即返回 | ❌ |

### 11.3 本项目中的使用（NoteServiceImpl.findNoteDetail）

**背景**：查询笔记详情时需要两个相互独立的 RPC——
- `userRpcService.findById(creatorId)`（查作者信息）
- `keyValueRpcService.findNoteContent(contentUuid)`（查正文，KV 存储）

原实现是**串行**（先查用户，再查内容），改造成 CompletableFuture **并行**后，两个 RPC 同时在 `taskExecutor` 线程池执行，`allOf` 等两者都完成后再 `thenApply` 组装 VO，接口耗时 ≈ 两个 RPC 中最慢的一个，而不是两者之和。

```java
// ① 并行发起两个 RPC（都提交到自定义线程池）
CompletableFuture<FindUserByIdRspDTO> userResultFuture = CompletableFuture
        .supplyAsync(() -> userRpcService.findById(creatorId), threadPoolTaskExecutor);
CompletableFuture<String> contentResultFuture = CompletableFuture.completedFuture(null);
if (Objects.equals(noteDO.getIsContentEmpty(), Boolean.FALSE)) {
    contentResultFuture = CompletableFuture
            .supplyAsync(() -> keyValueRpcService.findNoteContent(noteDO.getContentUuid()), threadPoolTaskExecutor);
}

// ② 等两个都完成后再组装
CompletableFuture<FindNoteDetailRspVO> resultFuture = CompletableFuture
        .allOf(userResultFuture, contentResultFuture)
        .thenApply(s -> {
            FindUserByIdRspDTO user = userResultFuture.join();
            String content = finalContentResultFuture.join();
            return FindNoteDetailRspVO.builder()...build();
        });

// ③ 获取最终结果（get() 抛受检异常，方法用 @SneakyThrows 处理）
FindNoteDetailRspVO findNoteDetailRspVO = resultFuture.get();
```

### 11.4 使用注意点

1. **务必传自定义线程池**：`supplyAsync` 不传 Executor 会用 `ForkJoinPool.commonPool()`，容易被其他任务占用/阻塞；项目统一传入 `taskExecutor`（ThreadPoolTaskExecutor）。
2. **`get()` 抛受检异常**：`InterruptedException` / `ExecutionException`，项目用 `@SneakyThrows` 简化，生产建议 try-catch 兜底。
3. **异步链中的异常不会自动抛出**：异常被包装进 CompletableFuture，只有 `get()/join()` 时才抛；建议配合 `exceptionally`/`whenComplete` 做兜底，避免静默失败。
4. **`allOf` 只保证"都完成"，不传递结果**：需要结果时在回调里分别 `join()` 取。
5. **闭包捕获变量**：`thenApply` 里引用的局部变量要有效 final（项目用 `finalContentResultFuture` 中转保证）。

### 11.5 异步选型：什么时候用线程池（ThreadPoolTaskExecutor），什么时候用 MQ

> 面试/开发高频纠结：想把一个"耗时操作"异步掉，到底用线程池还是消息队列？一句话：**线程池是"自己家里找帮手"，MQ 是"把活儿派给别的部门"**。项目里两者都在用，判断标准看 4 条：

| 判断维度 | 用线程池（ThreadPoolTaskExecutor / CompletableFuture） | 用消息队列（RocketMQ） |
|---------|------------------------------------------------------|----------------------|
| **要不要跨服务** | ❌ 只在**当前服务进程内**异步（如写缓存、并行 RPC） | ✅ 需要**别的服务**来处理（如通知 count 服务计数） |
| **能不能丢消息** | ⚠️ 线程池里的任务失败/服务重启会**丢**，无重试机制 | ✅ 消息持久化 + 重试，**可靠投递** |
| **要不要削峰/缓冲** | ❌ 无缓冲，任务堆积在内存队列 | ✅ 天然削峰填谷，消费端按自己速度慢慢处理 |
| **要不要顺序/延迟/广播** | ❌ 无这些能力 | ✅ 支持顺序消费、延时消息、广播、Tag 过滤 |

**怎么选（速查口诀）**：
- **"自己进程内、丢了无所谓、做完就算"** → 线程池（异步写缓存回填、并行查数据）。本项目例子：`UserServiceImpl.findById` 查完 DB 后 `threadPoolTaskExecutor.submit(...)` 异步回填 Redis 缓存；`NoteServiceImpl.findNoteDetail` 用 CompletableFuture 并行调两个 RPC。
- **"要跨服务、要可靠、要削峰、要最终一致"** → MQ。本项目例子：关注/取关、点赞/取消点赞 —— 接口内只写 Redis + 发一条 MQ 就返回，落库交给消费者异步做（失败可重试、峰值被令牌桶削掉）。

> 两者常**串在一起用**：主线程发 MQ → 消费者（MQ 侧）收到后，又用线程池做内部异步（比如 `FollowUnfollowConsumer` 消费后落库，`CountFansConsumer` 消费后 `BufferTrigger` 聚合）——线程池管"进程内"，MQ 管"进程间"。

## 十二、本地缓存（Caffeine）

> **这是啥**：**Caffeine** = 进程内的"小冰箱"，数据存在当前应用自己的内存里，读写是纳秒级；而 Redis 虽然也快，但每次都要走一遍网络。项目把它当作"本地缓存 → Redis → 数据库"三级缓存的第一级，能命中的话连网络都不用出。
> **为什么需要它**：同一个数据被查 100 次，每次都去查 Redis / 数据库太浪费；放进内存，命中就直接返回，快一个量级。代价是它只在本机生效、还可能存旧数据，所以必须靠后面的 Redis/DB 兜底（下面注意点有讲）。

> Caffeine 是一个高性能的 Java **本地（进程内）缓存**库，被称为"内存缓存之王"。项目把它作为**二级缓存的第一级**（本地缓存 → Redis → 数据库），进一步减少 RPC 与 Redis 访问。

### 12.1 作用（为什么用它）

- **比 Redis 更快**：数据存在 JVM 堆内，无网络 IO，`get` 是纳秒~微秒级；
- **自动淘汰**：支持按**容量**（`maximumSize`）、按**时间**（写入/访问后过期）、按**引用**等策略自动清理，避免内存无限增长；
- **进程内共享**：同一服务实例内所有线程共享一份缓存。

### 12.2 常用方法与配置（含本项目实际用到的）

| 方法 / 配置 | 作用 | 是否本项目用到 |
|------------|------|--------------|
| `Caffeine.newBuilder()` | 创建缓存构造器 | ✅ |
| `.initialCapacity(n)` | 设置初始容量（预分配，减少扩容） | ✅ 10000 |
| `.maximumSize(n)` | 设置最大容量，超限按 LRU 淘汰 | ✅ 10000 |
| `.expireAfterWrite(1, TimeUnit.HOURS)` | 写入后固定时长过期 | ✅ 1 小时 |
| `.build()` | 构建缓存实例 `Cache<K, V>` | ✅ |
| `getIfPresent(key)` | 查询，命中返回 value，未命中返回 null | ✅ 两级缓存第一级查询 |
| `put(key, value)` | 写入缓存 | ✅ 异步回填 |
| `get(key, mappingFunction)` | 未命中时用函数加载并写入（最常用，本项目未用） | ❌ |
| `invalidate(key)` / `invalidateAll()` | 主动删除缓存（数据变更时失效） | ❌（当前未做，见注意点） |
| `.expireAfterAccess(n)` / `.refreshAfterWrite(n)` | 访问后过期 / 写后定时刷新 | ❌ |

### 12.3 本项目中的使用

在两个服务里都定义了 `LOCAL_CACHE`，构成"**本地缓存 → Redis → DB**"三级读取链路（DB 分支异步回填 Redis，Redis 命中时异步回填本地缓存）：

**① user-biz（UserServiceImpl）—— 直接缓存对象**

```java
// Cache<Long, FindUserByIdRspDTO>，key 为用户 ID，value 为 DTO 对象
private static final Cache<Long, FindUserByIdRspDTO> LOCAL_CACHE = Caffeine.newBuilder()
        .initialCapacity(10000)
        .maximumSize(10000)
        .expireAfterWrite(1, TimeUnit.HOURS)
        .build();

// 查询：命中本地缓存直接返回
FindUserByIdRspDTO dto = LOCAL_CACHE.getIfPresent(userId);
// 写入：Redis 命中后异步回填本地缓存
threadPoolTaskExecutor.submit(() -> LOCAL_CACHE.put(userId, findUserByIdRspDTO));
```

**② note-biz（NoteServiceImpl）—— 缓存 JSON 字符串**

```java
// Cache<Long, String>，key 为笔记 ID，value 为序列化后的 JSON 字符串
private static final Cache<Long, String> LOCAL_CACHE = Caffeine.newBuilder()
        .initialCapacity(10000)
        .maximumSize(10000)
        .expireAfterWrite(1, TimeUnit.HOURS)
        .build();

// 查询：命中后反序列化返回，并做可见性校验
String json = LOCAL_CACHE.getIfPresent(noteId);
if (StringUtils.isNotBlank(json)) {
    FindNoteDetailRspVO vo = JsonUtils.parseObject(json, FindNoteDetailRspVO.class);
    checkNoteVisibleFromVO(userId, vo);   // 缓存命中也要做业务校验
    return Response.success(vo);
}
```

> 两种取值风格的取舍：note-biz 存 **JSON 字符串**（与 Redis 里的值一致，读写序列化逻辑统一）；user-biz 存**对象**（省去反序列化，性能更好，但需保证对象不被外部修改）。

### 12.4 使用注意点

1. **本地缓存只在本实例内生效**：多实例部署时每个节点各有一份，数据可能不一致 → 必须配合 Redis/DB 这类共享存储做兜底，本项目即"本地 → Redis → DB"三级结构。
2. **缓存命中也不能跳过业务校验**：note-biz 在本地缓存命中后仍执行 `checkNoteVisibleFromVO`（可见性校验），避免把私有笔记缓存结果错发给他人。
3. **写缓存放在异步线程回填**：主线程读 DB/Redis 直接返回，异步写缓存不阻塞接口。
4. **数据变更时要主动失效**：目前发布/更新/删除笔记**没有调用 `invalidate()`**，可能导致缓存中的旧数据；后续业务（如改笔记）需在写操作后主动删缓存，否则 1 小时过期前读到旧数据。
5. **容量要评估**：`maximumSize(10000)` 是数量上限，若 value 是很大的 JSON 字符串，实际内存占用可能超预期。

## 十三、消息队列（RocketMQ）

> **这是啥**：**RocketMQ** = "快递柜"。A 系统把消息丢进柜子就完事，B 系统有空再来取。三大好处：**异步**（发完消息接口立刻返回，不用等对方慢慢处理完）、**解耦**（生产者不关心谁消费、几个消费者，以后加新消费者不用改生产者代码）、**削峰**（瞬间消息再多，消费端按自己的速度慢慢处理，不把数据库打爆）。
> **为什么需要它**：以"关注用户"为例——如果同步落库，用户要干等；改成"先写 Redis、发一条 MQ 就返回"，落库交给消费者异步做，接口秒回。详细的零基础教程见《RocketMQ使用总结.md》。

| 组件 | 功能 | 适用场景 | 本项目使用位置 |
|------|------|---------|----------------|
| **RocketMQ**（`rocketmq-spring-boot-starter` 2.2.3） | 分布式消息中间件：异步解耦、流量削峰、广播通知、延时消息 | 关注/取关异步落库、删缓存通知、延迟双删 | note-biz（删本地缓存广播 + 延时删 Redis）、user-relation-biz（关注/取关 MQ + 令牌桶削峰） |

> 详细知识、常用方法、构建流程见《RocketMQ使用总结.md》。

**常用方法与本项目用法**

| 方法 / 注解 | 作用 | 本项目用法 |
|------------|------|-----------|
| `RocketMQTemplate.syncSend(topic, payload)` | 同步发送（阻塞等回执） | note 更新笔记后广播删各实例本地缓存 |
| `RocketMQTemplate.asyncSend(topic, message, callback)` | 异步发送 + 回调，不阻塞业务线程 | user-relation 关注消息、note 延时消息 |
| `asyncSend(..., timeout, delayLevel)` | 发送**延时消息**（delayLevel 取预设档位） | 延迟双删（level=1 即 1s） |
| 发送带 Tag：`topic:tag` | 主题下细分消息类型 | 关注消息 Tag=`Follow` |
| `@RocketMQMessageListener(consumerGroup, topic, messageModel)` | 声明消费者 | 3 个消费者（集群/广播/延时） |
| `RocketMQListener<T>.onMessage(msg)` | 消费处理 | `FollowUnfollowConsumer` 等 |

**快速回顾**：广播模式（BROADCASTING）每实例都消费 → 删各实例本地缓存；集群模式（CLUSTERING）组内竞争 → 关注落库只执行一次；延时消息只能选 18 个预设级别。

## <a id="ch14"></a>十四、限流（Guava RateLimiter 令牌桶）

> **这是啥**：**Guava RateLimiter** = "收费站/放行杆"，每秒只放 N 辆车（请求/消息）通过，没有"通行证"就得等着。原理是**令牌桶**：桶里每秒自动放 N 个令牌，请求先拿一个令牌才能执行，拿不到就阻塞等待。
> **为什么需要它**：消息堆积时，消费者如果瞬间狂写数据库，数据库会被打爆；加个限流让消费匀速进行，这就是"削峰"。注意它存在本机内存里，多实例各自独立限流、不共享。

| 组件 | 功能 | 适用场景 | 本项目使用位置 |
|------|------|---------|----------------|
| **Guava RateLimiter**（`guava` 33.0.0） | 单机令牌桶限流：固定速率放令牌，请求取令牌 | MQ 消费者流量削峰 | user-relation-biz `FollowUnfollowMqConsumerRateLimitConfig`（@RefreshScope 动态调速）+ `FollowUnfollowConsumer.acquire()` |

**常用方法与本项目用法**

| 方法 | 作用 | 本项目用法 |
|------|------|-----------|
| `RateLimiter.create(permitsPerSecond)` | 创建令牌桶（每秒令牌数） | 配置类动态创建（速率来自 Nacos） |
| `acquire()` | 阻塞获取令牌（拿不到就等待） | 消费者 `onMessage` 开头削峰 |
| `tryAcquire()` | 非阻塞尝试，失败立即返回 | ❌ |

**注意**：单机内存限流，多实例各自独立不共享；配合 `@RefreshScope` 可在 Nacos 改速率后重建令牌桶。

## 十五、Redis Pipeline（管道批量写）

> **这是啥**：**Redis Pipeline（管道）** = "快递批量打包"。平时执行一条 `set` 命令，就要在"你 → Redis → 你"之间来回跑一趟（一次网络往返 RTT）；而 Pipeline 把 **N 条命令打包进一个包裹**，一次送过去，Redis 收到后**一条条顺序执行**，再一次性把结果带回来——**只跑一趟网络，却干完了 N 件事**。
> **为什么需要它**：批量写缓存时，如果一条条 `set`，N 条就要 N 次网络往返，耗时随条数线性上涨；用 Pipeline 一次往返搞定，吞吐量大幅提升。典型场景：**批量查询用户信息后，把结果批量回填到 Redis 缓存**（本项目 `UserServiceImpl.findByIds` 就是这么做的，一次循环 set 几十上百个 key，绝不能逐个 set）。

| 组件 | 功能 | 适用场景 | 本项目使用位置 |
|------|------|---------|----------------|
| **Spring Data Redis**（`RedisTemplate.executePipelined`） | 把多条命令打包成一次网络请求批量执行，减少 RTT（网络往返次数） | 需要"批量写 Redis"（批量 set / incr / zadd 等） | user-biz `UserServiceImpl.findByIds`（批量查用户后异步回填缓存） |

**常用方法与本项目用法**

| 方法 | 作用 | 本项目用法 |
|------|------|-----------|
| `redisTemplate.executePipelined(SessionCallback)` | 执行管道：回调里提交的所有 Redis 操作，一次性打包发送 | `findByIds` 中循环 `set` 用户信息 + 过期时间 |
| `SessionCallback.execute(RedisOperations operations)` | 管道回调体：在里面用 `operations` 提交一批命令 | 回调里 `operations.opsForValue().set(key, value, expireSeconds, TimeUnit.SECONDS)` |

**项目真实代码**（[UserServiceImpl.findByIds](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/service/impl/UserServiceImpl.java#L434-L460)）：

```java
threadPoolTaskExecutor.submit(() -> {
    // DTO 集合转 Map，方便按用户 ID 取值
    Map<Long, FindUserByIdRspDTO> map = finalFindUserByIdRspDTOS.stream()
            .collect(Collectors.toMap(FindUserByIdRspDTO::getId, p -> p));

    // 执行 pipeline 操作：回调里所有 set 命令打包成一次网络请求
    redisTemplate.executePipelined(new SessionCallback<>() {
        @Override
        public Object execute(RedisOperations operations) {
            for (UserDO userDO : userDOS) {
                Long userId = userDO.getId();
                String userInfoRedisKey = RedisKeyConstants.buildUserInfoKey(userId);
                String value = JsonUtils.toJsonString(map.get(userId));
                // 过期时间：保底1天 + 随机秒数（打散过期时间，防缓存雪崩）
                long expireSeconds = 60*60*24 + RandomUtil.randomInt(60*60*24);
                operations.opsForValue().set(userInfoRedisKey, value, expireSeconds, TimeUnit.SECONDS);
            }
            return null; // 返回值在这里没用到
        }
    });
});
```

**注意：Pipeline ≠ Lua**。Pipeline 只负责"减少网络往返"，**不保证原子性**（执行过程中可能有别的客户端的命令插队）；Lua 脚本才保证"整段脚本原子执行"。所以项目里：**批量写缓存**用 Pipeline（不要求原子、只求快），**关注关系"判重 + 上限校验 + 写入"**用 Lua（必须原子，见第 5 章 Lua 总结）。

## 十六、BufferTrigger（快手批量聚合）

> **这是啥**：**BufferTrigger** = "食堂的餐盘收集车"。厨师（MQ 消费者）收到一盘菜（一条消息）**不立刻端走**，而是先放进收集车（buffer 缓冲队列），等**凑够一车**（batchSize）或**到了点**（linger 时间到）再一起端走批量处理。它是快手开源的一个"**缓冲 + 批量触发**"组件，坐标 `com.github.phantomthief:buffer-trigger`。
> **为什么需要它**：粉丝数是"高频小消息"——很多人可能同时在关注/取关同一个大 V，一条消息就更新一次 Redis 会产生大量无效请求；用 BufferTrigger 把 1 秒内的消息聚合成一批，**按目标用户合并成净变化量后一次性更新**，Redis 请求次数大幅减少。

| 组件 | 功能 | 适用场景 | 本项目使用位置 |
|------|------|---------|----------------|
| **buffer-trigger**（`com.github.phantomthief:buffer-trigger`） | 缓冲聚合：把高频小消息积攒成批，按"数量或时间"触发批量消费 | MQ 高频计数消息聚合（粉丝数统计） | count-biz `CountFansConsumer`（bufferSize 50000 / batchSize 1000 / linger 1s） |

**常用方法与本项目用法**

| 方法 | 作用 | 本项目用法 |
|------|------|-----------|
| `BufferTrigger.batchBlocking()` | 创建"批量阻塞型"触发器（积满或到点才消费） | 粉丝计数消费者 |
| `.bufferSize(n)` | 缓冲队列最大容量（积压上限） | 50000 |
| `.batchSize(n)` | 一批最多聚合 n 条 | 1000 |
| `.linger(Duration)` | 最多等待多久触发一次 | `Duration.ofSeconds(1)`（1 秒） |
| `.setConsumerEx(list -> ...)` | 设置批量消费者（入参是聚合后的 List） | `consumeMessage`：分组统计 + 更新 Redis + 转发落库 MQ |
| `.build()` | 构建触发器对象 | |
| `enqueue(item)` | 往缓冲队列放一条消息（不立即处理） | `onMessage` 里只入队 |

**项目真实代码**（[CountFansConsumer](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-count/xiaohashu-count-biz/src/main/java/com/quanxiaoha/xiaohashu/count/biz/consumer/CountFansConsumer.java#L46-L58)）：

```java
// 构建 BufferTrigger：积满 1000 条 或 每满 1 秒，触发一次批量消费
private BufferTrigger<String> bufferTrigger = BufferTrigger.<String>batchBlocking()
        .bufferSize(50000)              // 缓存队列最大容量
        .batchSize(1000)                // 一批最多聚合 1000 条
        .linger(Duration.ofSeconds(1))  // 多久聚合一次
        .setConsumerEx(this::consumeMessage) // 聚合完交给 consumeMessage 批量处理
        .build();

@Override
public void onMessage(String body) {
    bufferTrigger.enqueue(body); // 先入队列，不立即消费（攒批）
}
```

**要点**：
- **为什么粉丝数聚合、关注数不聚合？** 关注数是"我关注别人"，一个人短时间内关注不了几个，频率低，单条直接处理（见 `CountFollowingConsumer`）；粉丝数是"别人关注我"，大 V 可能瞬间被成千上万人关注，必须聚合。
- **聚合后怎么算？** 按 `targetUserId` 分组，把同一目标的一批 `FOLLOW(+1)/UNFOLLOW(-1)` 合并成**最终净变化量**（比如 +5-2=+3），一次 `opsForHash().increment` 完成，再异步发 MQ 落库——这就是"减请求、减写库"。

## <a id="ch17"></a>快速定位：一个功能用到了哪些组件

> **这是啥**：一张"菜谱"——想做某个功能（比如用户登录），照着这一行的组件链条一步步串起来就能实现。写新功能、排错时先查它，能快速知道要动哪些服务、哪些依赖。

| 业务功能 | 涉及组件 |
|---------|---------|
| 用户登录（验证码/密码） | Hutool（生成验证码）→ Redis（存验证码）→ 阿里云短信（发送）→ Sa-Token（签发 token）→ BCrypt（密码加密）→ Feign（调用户服务） |
| 服务间接口调用 | Nacos（服务发现）→ OpenFeign + LoadBalancer（RPC 调用）→ biz-context（userId 透传） |
| 统一入口鉴权 | Gateway（路由）→ Sa-Token Reactor（鉴权）→ Redis（角色/权限缓存） |
| 用户注册 | Feign（调分布式 ID 服务生成 ID）→ MyBatis + MySQL + Druid（落库）→ Redis（角色写入） |
| 用户信息查询（findById） | Caffeine（本地缓存）→ Redis（二级缓存）→ MySQL（DB 兜底） |
| 文件上传 | OSS/Minio（对象存储）→ feign-form（Feign 传文件）→ JAXB（OSS SDK 依赖） |
| 笔记内容存储 | Cassandra（KV 存储） |
| 笔记详情查询 | CompletableFuture（并行 RPC）→ user 服务 + KV 服务 → Caffeine（本地缓存）→ Redis（二级缓存） |
| 关注用户 | Redis ZSET + Lua（判重/上限）→ RocketMQ（异步落库）→ Guava RateLimiter（削峰）→ MySQL（关注/粉丝表） |
| 取关用户 | Lua（校验+删除 ZSET，无缓存则 DB 全量同步兜底）→ RocketMQ `asyncSendOrderly`（按用户顺序落库）→ 删除粉丝 ZSET |
