## 1. 前言：为什么做这个项目

**项目定位**：一个仿小红书风格的**笔记分享社区**微服务项目——用户可以发布图文/视频笔记，浏览笔记详情，点赞、收藏、关注他人，并实时查看粉丝数、关注数、获赞数等计数。

**和"以增删改查为主"的项目不同，这个项目更偏向"知识深度与真实业务的结合"**：

- 有**高并发读**场景（笔记详情）→ 引出多级缓存（Caffeine + Redis + DB）、缓存穿透/击穿/雪崩的治理；
- 有**高频写**场景（点赞/收藏/关注）→ 引出"先写缓存 + 异步 MQ 落库 + 批量聚合削峰"；
- 有**计数最终一致性**难题 → 引出独立的**数据对齐服务**（日增量临时表 + XXL-JOB 分片广播 + 双布隆过滤器）；
- 有**分布式**基础设施 → Nacos、Gateway、OpenFeign、Sa-Token、美团 Leaf、Cassandra、RocketMQ、XXL-JOB 全套落地。

**怎么读这份笔记**：先看第 2 节全景图，再按业务模块顺序读；每节的"演进 / 踩坑"是面试高分区；第 3 节的面试题先自测，答案在文末。

## 2. 内容介绍：项目全景

### 2.1 模块地图

```
xiaohashu (根聚合工程)
├── xiaoha-framework/      # 自研基础设施：common 通用类库 + 3 个 Spring Boot Starter
├── xiaohashu-gateway/     # 网关：路由 + Sa-Token 鉴权 + userId 透传
├── xiaohashu-auth/        # 认证：验证码/密码登录、token 签发
├── xiaohashu-user/        # 用户：注册、信息、角色权限
├── xiaohashu-note/        # 笔记：发布/查询/更新/删除/置顶/可见性
├── xiaohashu-user-relation/ # 关注/粉丝
├── xiaohashu-count/       # 计数：粉丝/关注/点赞/收藏计数
├── xiaohashu-data-align/  # 数据对齐：日增量落库 + XXL-JOB 分片对齐
├── xiaohashu-distributed-id-generator/ # 美团 Leaf 分布式 ID
├── xiaohashu-kv/          # Cassandra 键值存储（笔记正文）
└── xiaohashu-oss/         # 对象存储（Minio / 阿里云 OSS）
```

### 2.2 一次完整请求链路

```
前端 → Gateway（路由 + 鉴权 + 把 userId 写入请求头）
     → auth 登录（校验验证码/密码 → Sa-Token 签发 token）
     → user 服务（Feign 调用，注册/查询）
     → note 服务（Caffeine → Redis → DB 三级缓存查详情；发布走 分布式ID + KV 存正文）
     → 操作（点赞/收藏/关注）→ 发 RocketMQ
     → count 服务（BufferTrigger 聚合 → Redis Hash → 落库）
     → data-align 服务（双 Bloom 去重 → 写日增量临时表 → 次日 XXL-JOB 分片对齐）
```

### 2.3 技术栈速览

Java 17 + Spring Boot 3.0.2 + Spring Cloud Alibaba 2022.0.0（Nacos / Gateway / OpenFeign）+ Sa-Token + MySQL/MyBatis/Druid + Redis（BF / ZSET / Hash / Lua）+ RocketMQ + XXL-JOB + 美团 Leaf + Cassandra + Minio/OSS。

## 4. 登录注册（auth）

### 4.1 核心思路

支持**验证码登录**与**密码登录**两种方式，新用户验证码登录即自动注册。登录成功后由 Sa-Token 签发 token 作为登录凭证，验证码存 Redis（3 分钟过期）。

> 演进点（对应黑马的 Session → Redis 演进）：本项目**直接使用 Redis 存验证码 + Sa-Token token**，天然解决多实例 Session 共享问题。

### 4.2 关键代码

[AuthServiceImpl.loginAndRegister](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-auth/src/main/java/com/quanxiaoha/xiaohashu/auth/service/impl/AuthServiceImpl.java) 核心流程：

```java
// 验证码登录：校验 code → RPC user.registerUser（不存在即注册）→ StpUtil.login 签发 token
// 密码登录：RPC findUserByPhone → BCrypt.matches 校验 → StpUtil.login
```

### 4.3 底层原理

- **Sa-Token**：登录后 `StpUtil.login(userId)` 生成 token，网关侧通过 Redis 校验登录态；
- **BCrypt**：密码加密存储，校验时 `matches`，不可逆；
- **验证码发送**：`VerificationCodeServiceImpl` 生成 6 位随机码，写入 Redis（3 分钟过期），异步调用阿里云短信，带发送频率限制。

### 4.4 演进 / 踩坑

- 验证码 key 带手机号 + 随机串，避免敏感信息直存；
- 短信发送放**异步线程池**，不阻塞登录主流程；
- 密码登录走 RPC 查用户（`UserFeignApi`），体现微服务间调用。

## 5. 网关统一鉴权与登录态透传（gateway）

### 5.1 核心思路

网关是唯一入口，统一做两件事：**登录/权限校验**、**userId 透传**。

### 5.2 关键代码

- [SaTokenConfigure](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-gateway/src/main/java/com/quanxiaoha/xiaohashu/gateway/auth/SaTokenConfigure.java)：注册 `SaReactorFilter`，配置哪些路由需要登录、哪些需要权限；
- [AddUserId2HeaderFilter](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-gateway/src/main/java/com/quanxiaoha/xiaohashu/gateway/filter/AddUserId2HeaderFilter.java)：登录用户 ID 写入请求头 `userId`；
- 权限数据：`PushRolePermissions2RedisRunner` 启动时把"角色→权限"同步到 Redis，`StpInterfaceImpl` 从 Redis 查询。

### 5.3 底层原理（userId 全链路透传）

```
网关 AddUserId2HeaderFilter 写入请求头 userId
  → 下游 HeaderUserId2ContextFilter（自研 Starter）解析到 ThreadLocal
  → Feign 调用时 FeignRequestInterceptor 再写回请求头透传
  → 业务代码 LoginUserContextHolder.getUserId() 获取当前用户
```

### 5.4 演进 / 踩坑

- ThreadLocal 用 `TransmittableThreadLocal`（支持线程池传递），且 **finally 中 remove 防内存泄漏**；
- 网关用响应式编程（WebFlux），下游服务用 Servlet 栈，靠请求头解耦。

## 6. 用户服务（user）

### 6.1 核心思路

注册（生成工大社区号 + 用户 ID + 分配默认角色 + 角色权限入 Redis）、用户信息更新（头像/背景图走 OSS）、按手机号查询、更新密码。

### 6.2 关键代码

- 注册：RPC 调 `DistributedIdGeneratorFeignApi` 生成 ID，`UserDOMapper.insert`（`useGeneratedKeys` 回填主键）；
- 批量查用户：[UserServiceImpl.findByIds](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/service/impl/UserServiceImpl.java) 用 **Redis Pipeline** 批量回填缓存，减少 RTT。

### 6.3 底层原理

- 逻辑删除：`is_deleted` 字段，查询统一带 `is_deleted = 0`；
- Pipeline vs Lua：Pipeline 批量快写**不保证原子性**，Lua 脚本保证原子性——两者分工明确。

## 7. 笔记服务（note）

### 7.1 发布笔记（分布式 ID + KV 存正文）

**核心思路**：正文（大文本）与元数据分离——MySQL 存元数据（标题/图片/视频/话题/可见性），Cassandra 存正文。

**关键代码**：[NoteServiceImpl.publishNote](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java)：

```java
// 1. RPC 生成雪花笔记 ID
// 2. RPC 存正文到 KV（Cassandra）
// 3. 元数据落 MySQL
// 4. 发 MQ（NoteOperateTopic）通知数据对齐服务
```

### 7.2 查询笔记详情（三级缓存）

**核心思路**：`Caffeine（本地）→ Redis（二级）→ MySQL`，多级兜底；作者/正文用 `CompletableFuture` 并行查询；空值写 Redis 占位防穿透。

**演进 / 坑**：缓存 TTL 用"保底 1 天 + 随机 0~1 天"打散防雪崩；空值占位 60s + 随机 60s 防穿透；热点 key 由 Caffeine 本地缓存防击穿。

### 7.3 更新笔记（延迟双删）—— 面试必讲

**核心思路**：先更库再删缓存会存在"并发读回填旧值"的脏读窗口，用"删缓存 → 更库 → 延时消息再删一次"解决。

**关键代码**：[NoteServiceImpl.updateNote](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java)：

```java
// ① 更新 DB
// ② 删除 Redis 缓存
// ③ 广播 MQ 删各实例本地缓存（DeleteNoteLocalCacheTopic, BROADCASTING）
// ④ 发延时消息（DelayDeleteNoteRedisCacheTopic, 1s 档）
//    → DelayDeleteNoteRedisCacheConsumer 到点后二次删 Redis
```

**底层原理**：RocketMQ 延时消息只能选预设 18 级档位（1s/5s/10s/30s/1m...），`RocketMQHeaders.DELAY` 设置级别；延时 T 要大于"最慢读回填 + 主从同步"耗时。

### 7.4 删除 / 仅自己可见 / 置顶

- 删除：逻辑删除（`status` 置 0），并删缓存、发 MQ 通知数据对齐；
- 置顶/仅自己可见：`updateIsTop`、`updateVisibleOnlyMe` 都带 `creator_id` 校验（只能操作自己的笔记）。

## 8. 关注 / 粉丝（user-relation）

### 8.1 核心思路

关注关系先写 **Redis ZSET**（score = 关注时间，承载热点读 + 原子判断），再通过 **MQ 异步落库**（关注表 + 粉丝表），消费者用 **Guava 令牌桶**削峰。

### 8.2 关键代码

[RelationServiceImpl.follow](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user-relation/xiaohashu-user-relation-biz/src/main/java/com/quanxiaoha/xiaohashu/user/relation/biz/service/impl/RelationServiceImpl.java)：

```java
// ① 校验用户存在、不能关注自己
// ② Lua 脚本：判重（已关注返回 -3）+ 上限（-2）+ 添加（原子性）
// ③ 发 MQ（FollowUnfollowTopic + Tag Follow/Unfollow）
//    → FollowUnfollowConsumer 令牌桶 acquire() 削峰
//    → 编程式事务写 t_following + t_fans
//    → Lua 更新粉丝 ZSET
//    → 发计数 MQ（CountFollowingTopic + CountFansTopic）
```

### 8.3 底层原理（为什么 ZSET + Lua）

- 关注列表按时间排序 → ZSET（score=时间戳）；
- "判重 + 上限 + 添加"三步需要原子性 → Lua 脚本一次完成，避免并发重复关注；
- 关注上限（如 5000）用 Lua 比较 zcard。

### 8.4 演进 / 坑

- Redis 负责"热点读 + 原子判断"，MySQL 负责"持久化兜底"，MQ 负责"异步解耦 + 削峰"，各司其职；
- 令牌桶速率由 Nacos 配置 + `@RefreshScope` 动态重建（单机内存限流，多实例各自独立）。

## 9. 计数服务（count）

### 9.1 核心思路

粉丝数/关注数/点赞数/收藏数等计数，**先更新 Redis Hash，再异步落库**；高频消息用 **BufferTrigger 批量聚合** 削峰。

### 9.2 关键代码

- [CountFansConsumer](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-count/xiaohashu-count-biz/src/main/java/com/quanxiaoha/xiaohashu/count/biz/consumer/CountFansConsumer.java)：BufferTrigger（bufferSize 50000 / batchSize 1000 / linger 1s）→ 按目标用户分组**合并净变化量** → Redis Hash `increment`；
- [CountFollowingConsumer](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-count/xiaohashu-count-biz/src/main/java/com/quanxiaoha/xiaohashu/count/biz/consumer/CountFollowingConsumer.java)：关注数频率低，**直更不聚合**；
- 落库：`CountFans2DBConsumer` 令牌桶削峰 + `UserCountDOMapper.insertOrUpdateFansTotalByUserId`（`ON DUPLICATE KEY UPDATE`）。

### 9.3 底层原理

- Redis Hash：`count:user:{id}`，字段 `fansTotal / followingTotal / likeTotal / collectTotal / noteTotal`；Hash 存在才更新（初始化交给查询侧）；
- **`INSERT ... ON DUPLICATE KEY UPDATE` 幂等累加**：不存在即插入、存在即 `原值 + count`，避免"先查后更"的并发问题，count 可正可负。

### 9.4 演进 / 坑

粉丝数高频 → 聚合后按目标用户合并净变化量，一条消息可能代表几百次粉丝变动，大幅降级 DB/MQ 压力。

## 10. 数据对齐服务（data-align）—— 项目最大亮点

### 10.1 为什么需要数据对齐

**问题**：点赞/收藏/关注/发布都是高频操作，若每次操作都实时更新计数表（`t_user_count` / `t_note_count`），**写放大严重**，且高并发下计数容易漂移。

**方案（增量记录 + 次日重算对齐）**：当天只记"谁/哪篇笔记变了"到日增量临时表，次日由对齐任务**从源表重算**准确值回写计数表，保证**最终一致**。

### 10.2 分片存储（写侧）

- 临时表按 **日期 + 分片序号** 拆分（`t_data_align_*_count_temp_{日期}_{分片}`，`table.shards` 默认 3，Nacos 动态刷新）；
- 消费者按 `id % tableShards` 写入对应分片表；
- 覆盖 7 类计数：关注 / 粉丝 / 笔记点赞 / 笔记收藏 / 用户获赞 / 用户获收藏 / 笔记发布。

### 10.3 双布隆过滤器（幂等去重）

**为什么双**：同一位发布者的多篇笔记当天被点赞时，若按"笔记 ID + 发布者 ID"绑在一个事务里写两张表，发布者维度的唯一索引会冲突导致整体回滚，第二篇笔记丢失。

**方案**：笔记 ID 与发布者 ID **各自独立**布隆过滤器，各自判断、各自落库、互不影响（详见《开发问题记录》第 5 节）。

```java
// 笔记维度
if (BF.EXISTS(noteBloomKey, noteId) == 0) {
    try {
        insert note 表;           // 成功后才登记
        BF.ADD(noteBloomKey, noteId);   // 先落库、后登记
    } catch (Exception e) { log.error(...); }  // 冲突被吞，不影响另一维度
}
// 发布者维度：同样的独立逻辑
```

**底层原理**：
- 布隆过滤器只存**哈希指纹**，不存原始值、不能反查，内存极小；
- 误判**只可能"误判已存在"**（假阳性），不会漏判；误判导致该条跳过落库，极端情况少对齐一次，可接受；
- `BF.ADD` 必须在 insert 成功之后执行（先落库、后登记），否则落库失败却登记 → 当天数据静默丢失。

### 10.4 XXL-JOB 分片广播（读侧）

**原理**：分片广播 = 一次调度把任务分发给**所有注册实例**，每个实例拿到不同的 `shardIndex / shardTotal`，各处理一个分片，并行互不冲突（实例数 = 分片数；单实例时 shardTotal=1 只处理分片 0）。

**9 个 Job**：

| Job | 作用 |
|---|---|
| `CreateTableXxlJob` | 每日创建**次日** 7 类 × 分片临时表 |
| `FollowingCountShardingXxlJob` | 对齐关注数：`t_following` → `t_user_count.following_total` + Redis |
| `NoteLikeCountShardingXxlJob` | 对齐笔记点赞数：`t_note_like` → `t_note_count.like_total` + Redis |
| `NoteCollectCountShardingXxlJob` | 对齐笔记收藏数：`t_note_collection` → `t_note_count.collect_total` + Redis |
| `FansCountShardingXxlJob` | 对齐粉丝数：`t_fans` → `t_user_count.fans_total` + Redis |
| `UserLikeCountShardingXxlJob` | 对齐用户获赞数：`t_note_like join t_note` → `t_user_count.like_total` + Redis |
| `UserCollectCountShardingXxlJob` | 对齐用户获收藏数：`t_note_collection join t_note` → `t_user_count.collect_total` + Redis |
| `NotePublishCountShardingXxlJob` | 对齐发布数：`t_note` → `t_user_count.note_total` + Redis |
| `DeleteTableXxlJob` | 清理一个月前的临时表 |

**对齐任务通用逻辑**：

```java
int shardIndex = XxlJobHelper.getShardIndex();  // 分片序号
int shardTotal = XxlJobHelper.getShardTotal();  // 总分片
// 处理昨天：date = LocalDate.now().minusDays(1)
// 兜底建表：CREATE TABLE IF NOT EXISTS（防建表任务漏跑报"表不存在"）
for (;;) {
    ids = selectBatch(临时表, 1000);   // 批量取
    if (ids.isEmpty()) break;
    ids.forEach(id -> {
        total = selectCountFromSource(id);   // 从源表 count
        updateCountTable(id, total);          // 回写计数表
        updateRedisHash(id, total);           // 更新 Redis（Hash 存在才更新）
    });
    batchDelete(临时表, ids);                 // 删除已处理记录
}
```

### 10.5 演进 / 踩坑

- 曾出现"建表任务当天没跑 → 次日对齐查 `表不存在`"：给每个对齐任务加**查询前兜底建表**自愈；
- 曾出现同发布者多篇笔记撞唯一索引 → **双 Bloom** 解决；
- 曾出现 `BF.ADD` 在 insert 失败后仍登记 → 修正为**先落库、后登记**。

## 11. 分布式 ID（美团 Leaf）

### 11.1 核心思路

基于美团 Leaf 提供两种 ID 生成算法，通过 Feign 对外提供：用户注册生成工大社区号/用户 ID，笔记发布生成笔记 ID。

### 11.2 两种模式对比

| 模式 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 号段（Segment） | DB 预取号段 + 双 Segment 切换 + 动态步长 | 性能高、可用性强 | 依赖 DB，号段用完前要预取 |
| 雪花（Snowflake） | 时间戳 + workerId + 序列号（ZK 分配 workerId） | 无 DB 依赖、趋势递增 | 依赖时钟，时钟回拨需处理 |

### 11.3 演进 / 坑

- 用户注册从 Redis 自增切到 Leaf（全局唯一 + 高性能）；
- 雪花模式 ZK 不可用时降级 `ZeroIDGen`。

## 13. 项目最佳实践总结

1. **多级缓存**：Caffeine → Redis → DB，配合空值占位（防穿透）、TTL 随机（防雪崩）、本地缓存（防击穿）。
2. **延迟双删**：更新先删缓存 → 更库 → 延时消息二次删，消除并发回填脏读窗口。
3. **异步解耦 + 削峰**：MQ 串联关注/点赞/收藏；BufferTrigger 批量聚合 + 令牌桶限流双削峰。
4. **幂等三板斧**：`ON DUPLICATE KEY UPDATE`（upsert）、布隆过滤器（先查后写）、联合唯一索引（兜底）。
5. **数据对齐**：高频计数不实时写库，日增量 + 分片 + 次日源表重算，保证最终一致。
6. **原子性**：Redis 复杂操作一律 Lua 脚本；MySQL 多语句用编程式事务。
7. **基础设施自研**：4 个 Starter（通用类库 / Jackson / 登录上下文 / 操作日志），`AutoConfiguration.imports` 注册，开箱即用。
8. **配置动态化**：Nacos + `@RefreshScope` 管理分片数、令牌桶速率、存储策略等，运行期热生效。

## 15. 面试题答案

1. **计数为什么不实时写库？** 点赞/收藏/关注/发布高频，实时更新计数表写放大严重、计数易漂移。改为：当天把"谁变了"写入日增量临时表，次日对齐任务从源表重算回写，保证最终一致（第 10 节）。
2. **布隆过滤器 + 为什么双？** 幂等去重、挡在 DB 之前；只存 ID 哈希指纹、误判只可能"误判已存在"。双 = 笔记 ID 与发布者 ID 各自独立，避免同发布者多篇笔记撞 `uk_user_id` 导致整体回滚（10.3）。
3. **三级缓存与三大缓存问题？** Caffeine 本地（防击穿）+ Redis（防穿透：空值占位）+ DB；TTL 随机打散防雪崩；延迟双删防双写不一致（第 7 节）。
4. **为什么延迟双删？** 先更库后删缓存存在"并发读回填旧值"窗口；延迟 T 后再删一次清掉窗口内脏数据，T 需大于主从同步 + 最慢读回填耗时（7.3）。
5. **为什么 ZSET + Lua？** 关注列表按时间排序用 ZSET；判重/上限/添加需原子性，用 Lua 一次完成，防并发重复关注（第 8 节）。
6. **落库幂等？** `INSERT ... ON DUPLICATE KEY UPDATE` 依赖 `(user_id, note_id)` 唯一索引，不存在即插入、存在即更新，原子累加（9.3）。
7. **为什么 BufferTrigger 聚合？** 粉丝数高频消息攒批，1s/1000 条触发，按目标用户合并净变化量，一条消息代表多次变动，大幅降 DB/MQ 压力；关注数频率低直更（9.2）。
8. **分片广播原理？** 一次调度把任务分发给所有注册实例，每个实例拿到不同 `shardIndex/shardTotal` 各处理一个分片；实例数 = 分片数时并行度最高，单实例只处理分片 0（10.4）。
9. **分布式 ID？** 美团 Leaf：号段（DB 预取 + 双 Segment + 动态步长，性能高依赖 DB）与雪花（时间戳 + workerId + 序列号，无 DB 依赖、时钟回拨需处理），ZK 不可用降级（第 11 节）。
10. **为什么 BF.ADD 在 insert 之后？** "先落库、后登记"保证"已登记 = 已落库"；若 insert 失败仍登记，该条当天不会重试，数据静默丢失（10.3）。
