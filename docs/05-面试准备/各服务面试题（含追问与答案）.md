  ## 深度回答模板
  
  每道题至少讲清四件事：
  
  1. **职责边界**：当前服务负责什么，哪些数据属于别的服务，为什么通过 Feign/MQ 交互。

  面试时可以先用一段话概括，再按这四点展开；不要只背“用了 Redis、MQ、Cassandra”这些组件名。

  ## 1. 网关（gateway）
  
  **Q1：网关在项目里起什么作用？为什么需要网关？**
  **A**：网关是所有外部流量的第一跳，当前主要承担三类职责：
  
  1. 按路径把请求转发到 Nacos 服务名对应的微服务，并处理 StripPrefix、负载均衡和统一异常响应；
  2. 用 Sa-Token 过滤器完成登录态校验，并在配置了权限校验的路由上调用 `checkPermission`；当前源码并不是每条业务路由都已经配置了完整的细粒度权限矩阵，所以面试时应说“登录校验已统一，权限校验按路由逐步配置”，不要夸大为完整 RBAC 网关；
  3. `AddUserId2HeaderFilter` 从登录态取出 userId 写入请求头，给下游 `biz-context` Starter 使用。
  
  网关的价值是把跨服务共性的入口治理集中起来，但业务服务仍应校验资源归属（例如笔记作者），不能把网关当成唯一安全边界。
  
  **追问：为什么不把鉴权直接写在每个业务服务里？**
  **追问A**：写在每个服务里会造成重复代码、策略难以统一变更；放网关可"一处改、全局生效"，还能拦截未到业务层的非法请求。
  
  **Q2：Sa-Token 与网关是怎么集成的？**
  **A**：Gateway 是 WebFlux 应用，注册 Sa-Token 的 `SaReactorFilter` 作为全局过滤器。过滤器先匹配白名单，再对需要登录的路径调用 `StpUtil.checkLogin()`；只有明确配置了权限规则的路径才调用 `checkPermission`。通过后由 `AddUserId2HeaderFilter` 继续向下游透传身份。
  
  权限加载由 `StpInterfaceImpl` 接入角色/权限数据，数据主要从 Redis 读取。这里要区分认证和授权：Sa-Token token 证明“是谁”，权限列表决定“能做什么”；当前项目的授权配置覆盖范围有限，不能把注释示例当成已启用规则。
  
  **追问：token 存在哪里？校验一次要几次 Redis？**
  **追问A**：登录时 `StpUtil.login(userId)` 生成普通 Sa-Token，并由 Sa-Token 管理 token 与会话；请求校验时读取 token 对应的登录态，若还配置了权限则再加载角色/权限。具体 Redis 访问次数会受 Sa-Token 配置、本地缓存和权限实现影响，不能固定说“一定是两次”。生产需要关注 Redis 超时时是 fail-close 还是降级，以及网关线程不能被同步 Redis 调用长期阻塞。
  
  **Q3：userId 是怎么透传到下游服务的？**
  **A**：网关 `AddUserId2HeaderFilter` 把登录用户 ID 写入请求头 `userId` → 下游服务通过自研 Starter `biz-context` 的 `HeaderUserId2ContextFilter` 解析进 ThreadLocal → Feign 调用时 `FeignRequestInterceptor` 再写回请求头，实现全链路透传。
  
  **追问：为什么用请求头而不是参数？**
  **追问A**：请求头是 HTTP 标准机制，不侵入业务参数；参数容易被伪造/修改，请求头配合网关统一写入更安全。
  
  **Q4：网关用的响应式编程（WebFlux），和传统 Servlet 有什么区别？**
  **A**：WebFlux 基于 Reactor 非阻塞 IO，少量线程即可支撑高并发，适合 IO 密集的网关；Servlet 是阻塞式线程模型（一请求一线程）。本项目网关选 WebFlux 是 Spring Cloud Gateway 的标准实现。
  
  **追问：网关性能瓶颈通常在哪？**
  **追问A**：路由转发本身开销小，瓶颈常在鉴权时的 Redis IO、下游服务响应慢、日志打印等；可用缓存、异步、限流缓解。
  
  **Q5：未登录/无权限时网关怎么返回？**
  **A**：网关通过 `GlobalExceptionHandler` 实现 WebFlux 的 `ErrorWebExceptionHandler`，捕获 Sa-Token 的未登录和无权限异常，统一写出 JSON 错误体。未登录通常映射为 401，无权限映射为业务拒绝码；路由转发失败、下游超时和网关自身异常要与鉴权失败区分，否则前端会把服务故障误显示成“请登录”。
  
  **追问：为什么用 ErrorWebExceptionHandler 而不是 @ControllerAdvice？**
  **追问A**：Gateway 不是传统 MVC Controller，异常可能发生在路由过滤器、响应式链和转发阶段，`@ControllerAdvice` 不覆盖整个 WebFlux 过滤链。`ErrorWebExceptionHandler` 能在响应式上下文统一写响应，但要注意响应一旦提交就不能再次改写，异常处理器里也不能使用阻塞式 IO。
  
  **Q6：网关和 Filter/拦截器有什么区别？**
  **A**：网关是独立进程，处理进入系统的外部请求并负责路由；Servlet Filter 运行在某个服务的容器层，Spring MVC Interceptor 运行在该服务的 Controller 调用链。网关适合统一鉴权、路由、跨服务限流；服务内 Filter/Interceptor 仍适合做请求头解析、审计和资源权限校验。两者不是替代关系。
  
  **追问：本项目的网关有没有做限流/熔断？**
  **追问A**：当前未做网关层限流/熔断（业务层的限流在消费者里用令牌桶）。演进方向：Spring Cloud Gateway 的 RequestRateLimiter 或接入 Sentinel。
  
  **Q7：为什么权限数据要放 Redis？启动时怎么同步？**
  **A**：权限校验是高频读，放 Redis 避免每次查库；`user-biz` 的 `PushRolePermissions2RedisRunner` 在应用启动时把"角色→权限"关系同步进 Redis，并用 Redis 原子标记避免多实例重复同步。
  
  **追问：权限变更后缓存怎么更新？**
  **追问A**：启动同步属于兜底；若运行期权限变更，需主动删/更新 Redis 对应 key（本项目当前以启动同步为主）。
  
  **Q8：网关路由怎么配置的？**
  **A**：`application.yml` 中按服务配置 `spring.cloud.gateway.routes`：路径前缀（如 `/auth/**`）→ 转发到 `lb://xiaohashu-auth` 负载均衡目标，另配 StripPrefix 去掉前缀。
  
  **追问：lb:// 是什么？**
  **追问A**：`lb://` 表示走 LoadBalancer（Spring Cloud LoadBalancer）按服务名做客户端负载均衡，从 Nacos 拉取实例列表。
  
  **Q9：登录白名单（放行路径）怎么处理？**
  **A**：在 `SaReactorFilter` 配置中排除不需要登录的路径（如 `/auth/loginAndRegister`、验证码接口等），其余默认校验登录。
  
  **追问：放行路径会不会有安全隐患？**
  **追问A**：放行仅限于公开接口（登录、验证码、静态资源）；涉及用户数据的接口不放行，且业务层还有参数校验。
  
  **Q10：网关挂了怎么办？**
  **A**：当前项目能通过 Nacos 发现下游实例，但网关本身仍需要多实例和前置负载均衡才能消除单点。重试要按接口语义设计：GET 查询通常可重试，登录/点赞/关注等写请求不能盲目重试，必须带幂等键或由业务判断是否已处理。还要为网关 Redis、Nacos 和下游超时设置连接/线程池上限，避免故障扩散。
  
  **追问：网关做重试要注意什么？**
  **追问A**：只对 GET 等幂等请求重试，写请求重试可能造成重复提交，需配合幂等设计。

  ## 2. 认证服务（auth）
  
  **Q1：登录的整体流程是什么？**
  **A**：当前 auth 服务把两种方式收敛到 `loginAndRegister`：验证码分支先校验手机号和 Redis 中的验证码，再通过 `UserFeignApi` 查询用户；没有用户时调用注册接口创建用户；密码分支查询带 BCrypt 密文的用户信息并调用 `matches` 校验。两条分支最终都拿到 userId，调用 `StpUtil.login(userId)` 创建 Sa-Token 登录会话并返回 token。
  
  这里没有 JWT 签名和自包含 claims 校验，认证状态由 Sa-Token 管理；面试时不要把 Sa-Token 普通 token 说成 JWT。
  
  **追问：两种登录共用一个接口还是分开？**
  **追问A**：共用一个 `loginAndRegister` 接口，通过 `type`（登录类型）区分（`LoginTypeEnum`：1 验证码 / 2 密码），代码用 switch 分支处理。
  
  **Q2：为什么验证码登录等于自动注册？**
  **A**：新用户首次用手机号 + 验证码登录时，数据库无记录，直接按手机号创建用户并返回 ID，前端无感知——这就是"验证码登录即注册"，降低注册门槛。
  
  **追问：自动注册会不会造成脏数据？**
  **追问A**：可能（如骚扰号注册），但项目以体验优先；注册即登录，后续可加人工审核/封禁机制。
  
  **Q3：验证码为什么存 Redis 而不是 Session？**
  **A**：①多实例部署时 Session 不共享（每台 Tomcat 一份），Redis 天然共享；②验证码有过期时间（3 分钟），Redis TTL 天然支持；③Session 拷贝方案有延迟和服务器压力问题。
  
  **追问：验证码 key 怎么设计？防碰撞？**
  **追问A**：key 以手机号为业务维度，例如 `verification:code:{phone}`，验证码值和 TTL 一起由 Redis 管理。手机号本身能避免不同用户互相覆盖，但不能防止同一手机号被高频请求；频率控制要另外设计计数 key 或网关规则。当前源码确认的是 3 分钟 TTL，不能把 TTL 等同于“60 秒发送间隔”。
  
  **Q4：短信验证码发送是怎么实现的？为什么异步？**
  **A**：`VerificationCodeServiceImpl` 生成 6 位验证码，先写 Redis 并设置 3 分钟 TTL，再通过线程池异步调用短信 SDK。异步的目的只是让短信供应商的网络延迟不阻塞接口响应；它会引入“Redis 已写、短信未送达”的状态，所以不能把写 Redis 视为短信发送成功。
  
  **追问：异步发送失败怎么办？**
  **追问A**：当前实现没有完整的发送确认、重试和补偿状态机，短信调用失败时用户可能收不到码，但 Redis 中的码仍会在 3 分钟后过期。生产应记录发送状态和供应商回执，用带退避的重试/死信处理，并限制同一手机号的重发次数；同时要避免重试导致重复扣费或多条短信。
  
  **Q5：密码为什么用 BCrypt？**
  **A**：BCrypt 加盐 + 慢哈希，抗彩虹表、抗暴力破解；`matches` 校验时内部自动提取盐，无需单独存盐字段；不可逆，数据库泄露也难还原明文。
  
  **追问：MD5 为什么不行？**
  **追问A**：MD5 无盐且速度快，彩虹表可秒破；加盐 MD5 仍需防暴力，BCrypt 的慢哈希成本更高。
  
  **Q6：token 是怎么签发的？**
  **A**：登录成功后调用 `StpUtil.login(userId)`，Sa-Token 创建登录会话并返回 tokenValue；客户端后续把 token 放在请求头，Gateway 的 `SaReactorFilter` 校验登录态，通过后把 userId 写入内部请求头。token 本身不承载完整用户资料，用户昵称、头像等仍由 user 服务查询。
  
  **追问：token 过期怎么办？**
  **追问A**：过期行为由 Sa-Token 配置决定，可以设置 token 有效期、活动续签或强制注销。当前项目没有单独实现 JWT refresh token 流程；如果要做长期登录，应明确短 token、refresh token、踢人和改密后的会话失效规则，不能只说“自动刷新”。
  
  **Q7：登录返回的用户信息怎么做脱敏？**
  **A**：不直接返回完整用户实体，返回 DTO/VO（只含 id、昵称、头像等展示字段），敏感信息（密码等）不出接口。auth 服务实际只下发 token，用户信息走 user 服务查询。
  
  **追问：脱敏还体现在哪？**
  **追问A**：用户查询接口只返回展示字段；数据库密码 BCrypt 密文，任何人不可见明文。
  
  **Q8：修改密码流程？**
  **A**：`UpdatePasswordReqVO`（新密码）→ 校验登录态 → 更新 `t_user.password`（BCrypt 加密）→ 可让旧 token 失效（Sa-Token 支持踢人/注销）。
  
  **追问：改密后旧 token 还能用吗？**
  **追问A**：默认还能用（Sa-Token 不自动失效），严格场景应调用 StpUtil 使该用户会话全部注销。
  
  **Q9：登录接口怎么防刷？**
  **A**：当前能确认的是验证码 Redis TTL 为 3 分钟，以及验证码校验本身会限制无效登录；代码没有形成完整的网关级 IP/手机号限流体系，不能把“3 分钟 TTL”说成“60 秒发送间隔”。生产应在网关和 auth 业务层分别按 IP、手机号、设备和失败次数限流，并对短信发送做成本控制。
  
  **追问：和网关限流什么关系？**
  **追问A**：网关限流负责尽早拒绝明显超量流量，auth 负责验证码正确性、失败次数和手机号业务规则；当前网关限流属于演进项，不能说已经和 auth 形成完整的双层防刷。
  
  **Q10：auth 服务怎么调用 user 服务？**
  **A**：通过 `UserRpcService` 封装 `UserFeignApi`（OpenFeign）：`registerUser`、`findUserByPhone`、`updatePassword`，服务间走 HTTP + JSON。
  
  **追问：Feign 调用失败怎么办？**
  **追问A**：当前未配置重试/降级；失败抛异常由 `GlobalExceptionHandler` 统一转响应码。生产可加 OpenFeign 重试 + 熔断。

  ## 3. 用户服务（user）
  
  **Q1：用户注册流程是什么？**
  **A**：注册由 auth 触发，但用户数据由 user 服务负责。服务先通过 `DistributedIdGeneratorFeignApi` 取得用户 ID 和对外展示的小哈书号，再写入 `t_user`；随后在 `t_user_role_rel` 分配默认角色，保证新用户拥有基础权限。角色权限还要推送到 Redis，供网关的 `StpInterfaceImpl` 读取，最后才返回 userId。
  
  这几步不是一个跨服务分布式事务：ID 服务调用失败应直接终止注册；用户表已写、角色或 Redis 同步失败时，当前实现需要通过异常重试或启动同步补齐。面试时要说明“数据库注册成功”和“权限缓存已经可用”是两个状态，不能只说一条 insert 就完成注册。
  
  **追问：为什么用户 ID 和小哈书号都走分布式 ID？**
  **追问A**：保证全局唯一且趋势递增；小哈书号是用户对外展示的 ID，也需唯一不冲突。早期用 Redis 自增，迁移到 Leaf 解决高并发唯一性问题。实际采用号段还是雪花要以调用方 key 为准，不能只凭实体名称判断。
  
  **Q2：为什么注册要分配默认角色？**
  **A**：项目把角色和权限拆开：用户通过 `t_user_role_rel` 关联角色，角色再映射到权限码。注册时写入 `RoleConstants` 对应的普通用户角色，后续网关才能根据 userId 加载角色并判断接口权限。默认角色不是为了在 user 服务里做所有授权，而是建立用户初始身份；资源归属（例如只能修改自己的笔记）仍由业务服务校验。
  
  **追问：权限是怎么生效的？**
  **追问A**：注册时把"该角色的权限列表"写入 Redis（`role:permissions:`），网关 `StpInterfaceImpl` 从 Redis 取权限做校验。
  
  **Q3：`PushRolePermissions2RedisRunner` 启动同步的原理？**
  **A**：`PushRolePermissions2RedisRunner` 在 Spring Boot 完成初始化后查询启用的角色和权限关系，把角色到权限码的映射写入 Redis。多实例同时启动时用 Redis `SETNX` 标记抢占同步资格，避免每台机器重复全量写入。这个标记只能减少启动时重复操作，不能自动感知运行期间的权限修改，所以权限后台变更后仍需要删除/刷新相关 key，或增加版本号和发布事件。
  
  **追问：为什么用 setnx 而不是直接同步？**
  **追问A**：多实例同时启动会重复写 Redis 浪费资源；setnx 保证只有一个实例执行，其他实例跳过。
  
  **Q4：批量查用户为什么用 Redis Pipeline？**
  **A**：`UserServiceImpl.findByIds` 先批量查出用户展示字段，再把结果回填到 Redis。若逐个 `SET`，每个 key 都会产生一次网络往返；`executePipelined` 将多条命令一次发送，主要收益是减少 RTT。Pipeline 只优化传输，不保证原子性；中途失败时要允许下次查询重新回源，不能把 Pipeline 当成 Lua 事务。
  
  **追问：Pipeline 和 Lua 有什么区别？**
  **追问A**：Pipeline 只管"批量快发"不保证原子性（中途可被其他命令插入）；Lua 脚本在 Redis 内原子执行。本项目 Pipeline 用于批量写缓存，Lua 用于需要原子性的业务（关注判重等）。
  
  **Q5：逻辑删除（is_deleted）是怎么设计的？**
  **A**：用户表使用 `is_deleted` 标记删除，删除操作只更新标志位，不立即物理删除；常用查询（如 `selectByIds`、`selectEnabledList`）统一加 `is_deleted = 0`。这样可以保留审计和关联数据，避免物理删除后历史关系找不到用户。代价是索引和表会持续变大，任何漏写过滤条件的 SQL 都可能把“已删除”用户查出来，长期还需要归档或物理清理策略。
  
  **追问：逻辑删除的缺点？**
  **追问A**：数据只增不减，需定期归档；所有查询都要带过滤条件，漏写会查脏数据。
  
  **Q6：更新用户信息流程？**
  **A**：请求进入 user 服务后先校验当前登录 userId 和字段格式；头像、背景图通过 `OssRpcService` 调用 `FileFeignApi` 上传，拿到 URL 后再与昵称、小哈书号、性别、生日、简介一起更新 `t_user`。更新数据库成功后删除用户信息缓存，让后续读请求按新数据重建。
  
  这里仍有跨服务失败窗口：文件已上传但数据库更新失败会留下孤儿对象，数据库更新成功但删缓存失败会短暂读旧值。生产应为文件上传和缓存失效增加补偿/重试，并用用户版本号或更新时间避免旧缓存覆盖新数据。
  
  **追问：缓存怎么更新？**
  **追问A**：更新 DB 后删 Redis 用户信息缓存（也可发 MQ 广播删本地缓存），下次查询重建。
  
  **Q7：DTO/VO/DO 分层在 user 服务怎么体现？**
  **A**：`*-api` 模块放 Feign 接口 + DTO（跨服务传输）；`*-biz` 内 `model.vo` 是接口入参/出参、`domain.dataobject` 是数据库实体（DO，MyBatis Generator 生成）、`domain.mapper` 是对应 Mapper。各层职责分离，避免直接暴露数据库实体。
  
  **追问：DO 和 DTO 字段不一致时怎么办？**
  **追问A**：通过 BeanUtils 拷贝 + 按需字段设计，接口只暴露展示所需字段，敏感字段不出 DO。
  
  **Q8：`selectByIds` 的 SQL 有什么特点？**
  **A**：只查 `id, nickname, avatar, introduction` 四列（按需查询），带 `status=0 and is_deleted=0` 过滤，用 `<foreach>` 动态拼接 IN 列表。
  
  **追问：IN 列表太长怎么办？**
  **追问A**：超长 IN 会超 SQL 长度限制/性能下降，可按批次拆分（如每次 1000 个 ID）。
  
  **Q9：性别、状态等字段为什么用枚举？**
  **A**：如 `SexEnum`（0 女/1 男）、`StatusEnum`、`DeletedEnum`：语义清晰、类型安全、取值单一来源，避免魔法数字散落各处。
  
  **追问：枚举跨服务传输是数字还是对象？**
  **追问A**：序列化后是数字（code），跨服务用数字传输，消费端再映射回枚举或与枚举 code 比较。
  
  **Q10：用户服务对外暴露了哪些 Feign 接口？**
  **A**：`UserFeignApi`：注册、按手机号查询（含密码密文）、更新密码，供 auth 等服务调用。
  
  **追问：为什么密码查询走 Feign 而不是直接查库？**
  **追问A**：微服务间数据不能跨服务直连库，必须通过服务提供的 Feign 接口访问，保证数据访问受控、可审计。

  ## 4. 笔记服务（note）
  
  **Q1：发布笔记的完整流程？**
  **A**：发布接口先通过分布式 ID 服务取得 noteId；正文作为大文本调用 `KeyValueRpcService` 写入 KV/Cassandra，返回 contentUuid；标题、媒体 URL、话题、可见性、作者等元数据再写入 MySQL `t_note`。元数据落库成功后发送 `NoteOperateTopic`，通知 data-align 记录发布数变更。正文和元数据分别落在两个存储，当前没有跨存储事务，因此失败时需要根据 contentUuid 做清理或补偿。
  
  **追问：为什么正文和元数据要分开存？**
  **追问A**：正文是大文本，放 MySQL 会让行变大、影响索引与查询性能；Cassandra 适合大文本 KV 读写，两者分工：MySQL 管关系型元数据，Cassandra 管大内容。
  
  **Q2：查询笔记详情为什么用三级缓存？**
  **A**：当前缓存的主体是笔记元数据，链路是 `Caffeine（当前实例）→ Redis（共享）→ MySQL t_note`。缓存 miss 后，note 服务还要通过 user RPC 获取作者信息、通过 KV RPC 获取 Cassandra 正文，并用 `CompletableFuture` 并发两个下游；所以不能把链路简化成“Redis 命中就拿到完整详情”。本地缓存降低单实例热点访问，Redis 负责跨实例共享，MySQL 是元数据兜底。
  
  **追问：三级缓存的一致性问题怎么解决？**
  **追问A**：更新时先写 MySQL，再删 Redis，广播 MQ 删除各实例 Caffeine，并发送约 1 秒延迟消息再次删除 Redis。它覆盖了共享缓存和本地缓存的主要脏数据窗口，但依赖 MQ 广播和延迟消息成功；Cassandra 正文与 MySQL 元数据也没有本地事务，因此只能说最终一致，不能说更新返回后所有实例立即一致。
  
  **Q3：缓存穿透/击穿/雪崩分别怎么治理的？**
  **A**：穿透是大量非法 noteId，当前通过查空写短 TTL 空值占位；击穿是单个热点 key 失效，Caffeine 和 TTL 打散只能缓解，源码没有完整互斥锁/逻辑过期；雪崩是大量 key 同时失效，正常详情 TTL 使用基础值加随机量。生产还要限流回源、热点预热和单飞重建，不能把本地缓存描述成已经彻底解决击穿。
  
  **追问：空值缓存有什么风险？**
  **追问A**：数据"从无到有"后 TTL 窗口内仍读空，所以 TTL 设短（1~2 分钟）；大量不存在的 key 会占内存。
  
  **Q4：更新笔记的延迟双删是怎么做的？**
  **A**：①更新 MySQL 元数据；②删除共享 Redis；③发送广播消息，让每个 note 实例删除 Caffeine；④发送延时消息（当前使用约 1s 档），由 `DelayDeleteNoteRedisCacheConsumer` 再删一次 Redis。第二次删除针对的是“第一次删除后，并发读把旧值重新回填”的窗口。它不是分布式事务，消息失败或主从延迟超过档位仍可能留下旧缓存。
  
  **追问：为什么第二次删除要延迟？**
  **追问A**：第一次删除到主从同步完成之间，可能有读请求把旧值回填缓存；延迟 T（> 最慢读回填 + 主从同步耗时）后再删一次，能把这些脏数据清掉。
  
  **追问：延时时间怎么选？**
  **追问A**：RocketMQ 延时消息只能选预设档位（1s/5s/10s/30s/1m...）；本地单机 MySQL 用 1s 档足够，生产按主从延迟评估（一般 1~10s）。
  
  **Q5：广播删本地缓存和延时删 Redis 是什么关系？**
  **A**：广播（BROADCASTING 模式）让所有实例删各自的 Caffeine 本地缓存；延时消息是删共享的 Redis。两者配合覆盖"多级缓存"的两层，保证更新后各层都不残留旧值。
  
  **追问：广播模式所有实例都消费同一份消息，怎么保证？**
  **追问A**：RocketMQ 广播模式下每个消费者实例都会收到该消息（普通集群模式只会被一个实例消费），天然适合"每台机器都要执行"的场景。
  
  **Q6：置顶/仅自己可见怎么防止操作别人的笔记？**
  **A**：Mapper 层校验：`updateIsTop` 带 `where id=? and creator_id=?`，`updateVisibleOnlyMe` 带 `where id=? and status=1`。业务层 `checkNoteIsExistAndGetCreatorId` 先校验笔记存在且取作者 ID。
  
  **追问：为什么校验放 SQL 里而不是纯业务判断？**
  **追问A**：SQL 条件是最底层兜底，即使业务逻辑漏判，DB 层面也不会越权更新；同时减少一次查询。
  
  **Q7：笔记删除是物理删还是逻辑删？**
  **A**：逻辑删除：`status` 置 0（`NoteStatusEnum`），并删缓存、发 MQ 通知数据对齐（发布数需重算）。查询统一过滤有效状态。
  
  **追问：删除后详情还能查到吗？**
  **追问A**：查不到——查询 SQL 带 `status = 1` 条件，逻辑删除的记录对外不可见。
  
  **Q8：`selectCountByNoteId` 这种方法的用途？**
  **A**：判断笔记是否存在且有效（`count(*) where id=? and status=1`），供点赞/收藏/置顶等操作的预校验使用，比 `selectByPrimaryKey` 返回全对象更轻量。
  
  **追问：为什么不用 selectByPrimaryKey 判空？**
  **追问A**：count 只回 1/0，网络与解析开销更小；且天然带上 status=1 的有效性过滤。
  
  **Q9：话题（Topic）和频道（Channel）是什么关系？**
  **A**：`t_topic` 话题、`t_channel` 频道，`t_channel_topic_rel` 关联表；笔记可挂话题（`TopicDOMapper.selectNameByPrimaryKey` 取话题名展示）。这是内容组织维度。
  
  **追问：为什么建关联表而不是外键？**
  **追问A**：多对多关系用中间表扩展性好；分布式/微服务下不推荐数据库外键，靠应用层维护一致性。
  
  **Q10：笔记详情缓存的 key 怎么设计？空值怎么防穿透？**
  **A**：key = `note:detail:{noteId}`；查库判空后写 `"null"` 占位（TTL 1~2 分钟），下次命中解析出 null 直接返回，不再打 DB。
  
  **追问：为什么占位要随机过期？**
  **追问A**：随机化避免大量空值 key 同时过期（防雪崩）与集中重建（防击穿）。

  ## 5. 关注/粉丝（user-relation）
  
  **Q1：关注用户的流程？**
  **A**：入口先校验目标用户存在、不能关注自己，然后在 Redis ZSET 中执行 Lua：检查是否已经关注、是否达到上限，并把 followingUserId 加入当前用户的关注集合。状态变化成功后发送 `FollowUnfollowTopic`，`FollowUnfollowConsumer` 取得令牌后在事务中写 `t_following` 和 `t_fans`，再更新目标用户的粉丝 ZSET，并发送关注数/粉丝数计数消息。
  
  这条链路是“Redis 先反馈、MySQL 异步持久化”，所以关注按钮可能先显示成功，数据库列表稍后才出现；如果 MQ 生产或消费者失败，必须依赖重试、死信和缓存重建，不能只靠 Redis 永久保存关系。
  
  **追问：为什么先写 Redis 再发 MQ 落库？**
  **追问A**：Redis 承载热点读和原子判重，MQ 把关系操作异步送到消费者，MySQL 保存持久化关系。这里的先 Redis 后 MQ 会产生短暂窗口：Redis 已显示关注但 MySQL 还未落库；如果消息发送失败，不能靠“Redis 是缓存”自动恢复，必须重试、死信或从 Redis/MySQL 做对账。关系明细最终以 MySQL 为准，Redis 需要能从 MySQL 重建。
  
  **Q2：关注列表为什么用 Redis ZSET？**
  **A**：关注列表需要按关注时间排序展示 → ZSET 的 score 天然是时间戳；且支持范围查询（`ZRANGE`）、去重、上限判断（`ZCARD`），比 List/Set 更贴合业务。
  
  **追问：ZSET 和 List 有什么区别？**
  **追问A**：List 支持重复元素、按插入序，ZSET 按 score 有序且元素唯一，天然适合"按时间排序的用户 ID 集合"。
  
  **Q3：Lua 脚本在这里保证什么？**
  **A**：`redis.call` 完成"判断是否已关注 + 判断是否达上限 + 添加"三步原子执行，防止并发重复关注；返回码语义化（`LuaResultEnum`：-1 ZSET 不存在 / -2 达上限 / -3 已关注）。
  
  **追问：不用 Lua 会怎样？**
  **追问A**：需要多次 Redis 往返 + 业务层判断，并发下会"同时判重都通过"，导致重复关注；Lua 一次调用原子完成。
  
  **Q4：关注上限（如 5000）怎么实现？**
  **A**：Lua 内 `ZCARD` 获取当前关注数，与上限比较，达到则返回 -2，业务层抛 `FOLLOWING_COUNT_LIMIT`。
  
  **追问：上限为什么放 Lua 而不是代码里判断？**
  **追问A**：代码判断存在并发窗口（两个请求都读到 4999 都放行）；Lua 内判断 + 添加是原子的。
  
  **Q5：为什么要分 t_following 和 t_fans 两张表？**
  **A**：关注关系双向：`t_following`（我关注了谁，user_id + following_user_id）、`t_fans`（谁关注了我，user_id + fans_user_id）；各自带唯一索引，方便按维度计数和查列表。
  
  **追问：只建一张表可以吗？**
  **追问A**：可以（单向关系表 + 查询时反查），但两张表查询更直接（关注数/粉丝数各查各表），代价是写入时双写，用同一事务保证。
  
  **Q6：取关流程？**
  **A**：类似关注的反向操作：删 Redis ZSET 中记录 → 发 MQ（Tag=Unfollow）→ 消费者删 `t_following` / `t_fans` 记录 → 发计数 MQ（-1）。
  
  **追问：取关的幂等怎么做？**
  **追问A**：关系删除按 `(user_id, following_user_id)` 条件执行，重复删除没有副作用；但计数的 `increment(-1)` 只是增量操作，不是幂等操作，重复取关消息可能把计数多减一次。当前依赖入口状态判断、消费顺序和次日对齐，生产应使用唯一事件 ID 或从关系源表覆盖重算。
  
  **Q7：关注/粉丝列表分页怎么查？**
  **A**：`selectPageListByUserId` 按 `order by create_time desc limit offset, limit` 分页；另有 `select5000FansByUserId`（粉丝列表缓存/推送固定取 5000）。
  
  **追问：为什么固定 5000？**
  **追问A**：展示/推送场景有容量上限，取最新 5000 足够覆盖展示需求，避免超大返回。
  
  **Q8：消费者为什么要令牌桶削峰？**
  **A**：关注/取关是高频操作，MQ 消费若不限速会瞬间打满 DB；`FollowUnfollowConsumer` 消费前 `rateLimiter.acquire()` 阻塞获取令牌，控制落库速率。
  
  **追问：令牌桶和 MQ 天然削峰有什么区别？**
  **追问A**：MQ 本身只是异步缓冲（积压），令牌桶在消费端主动限速，防止"消息洪峰转成 DB 洪峰"；速率可用 Nacos 配置动态调整。
  
  **Q9：计数 MQ 是怎么发的？**
  **A**：落库成功后发两条：`CountFollowingTopic`（关注数变化，targetUserId 是操作者）、`CountFansTopic`（粉丝数变化，targetUserId 是目标用户），交给 count 服务聚合计数。
  
  **追问：为什么关注数直更、粉丝数聚合？**
  **追问A**：关注数频率低直接更新即可；粉丝数（大 V 场景）可能同时被大量人关注，消息高频，必须 BufferTrigger 聚合后批量更新（见 count 服务）。
  
  **Q10：如果 Redis 数据丢了（如宕机），怎么恢复关注关系？**
  **A**：Redis 是缓存，MySQL 是源：启动/缓存缺失时从 `t_following`/`t_fans` 全量同步到 ZSET（`selectByUserId` 等批量查询 + Lua 批量写入 + 过期时间）。
  
  **追问：批量同步会不会把已取关的记录同步回去？**
  **追问A**：同步以 MySQL 为准（MySQL 删了就不在查询结果里），Redis 侧先删后建或按查询结果重建，不会回放已删除记录。

  ## 6. 计数服务（count）
  
  **Q1：计数服务的整体链路？**
  **A**：业务服务先完成关注、点赞、收藏等事实操作，再发送计数事件。count 服务消费一级 MQ：粉丝数等高频维度进入 `BufferTrigger` 聚合，低频维度可直接处理；聚合结果先更新 Redis Hash，供详情页准实时读取，再发送 `CountXxx2DBTopic` 二级消息，由落库消费者限速后通过 upsert 更新 MySQL 计数表。Redis 和 MySQL 的写入都不是同一个事务，data-align 负责最终修正。
  
  **追问：为什么要 Redis 和 MySQL 双写？**
  **追问A**：Redis 负责低延迟读，MySQL 负责持久化基数和重算来源。Redis 先更新只能说明读侧更快，不能保证消息和数据库“不丢”；二级 MQ、消费者重试、数据库 upsert 和 data-align 共同构成最终一致链路。Redis key 过期后必须从完整计数表初始化，不能只接收后续增量。
  
  **Q2：BufferTrigger 聚合的原理？**
  **A**：源码配置是 `bufferSize(50000)`、`batchSize(1000)`、`linger(1s)`：缓冲区最多接收约 5 万条，凑够 1000 条或等待 1 秒触发一次批处理，再按目标用户合并净变化量。比如同一个用户在一批内收到 100 次关注、取消 30 次，最终只更新 +70。它是当前 JVM 进程内的内存缓冲，不是 RocketMQ 的持久化队列；进程在批次落库前宕机，未处理数据可能丢，面试时必须主动说出这个风险。
  
  **追问：合并净变化量是什么意思？**
  **追问A**：同一个人一秒钟内被 100 人关注又 50 人取关，聚合后净变化 +50，只产生 1 条计数更新，而不是 150 条。
  
  **Q3：为什么粉丝数聚合、关注数直更？**
  **A**：粉丝数高频（一个热点用户瞬间大量涨粉），必须聚合削峰；关注数低频（一个人操作频率有限），直更简单可靠。
  
  **追问：如果都直更会怎样？**
  **追问A**：热点粉丝事件会导致 MQ 积压、DB 频繁 upsert，压力大；聚合把高频转低频。
  
  **Q4：Redis Hash 计数结构怎么设计的？**
  **A**：key `count:user:{id}`，字段 `fansTotal / followingTotal / likeTotal / collectTotal / noteTotal`；`count:note:{id}` 字段 `likeTotal / collectTotal`。更新用 `increment(field, count)`，count 可正可负。
  
  **追问：为什么 Hash 而不是 String？**
  **追问A**：一个用户的多个计数（粉丝/关注/获赞/收藏/发布）用一个 key 管理，一次请求可读全部，字段独立增减。
  
  **Q5：为什么"Hash 存在才更新"，初始化交给查询侧？**
  **A**：计数缓存带 TTL 会过期，过期后已删除；若直接 `increment` 会重建一个"只有增量"的错误计数（丢失历史基数）。所以只对存在的 key 累加，不存在时由查询侧从 DB 初始化全量值。
  
  **追问：初始化怎么保证准确？**
  **追问A**：查询侧读不到缓存时查 DB 计数表（或重算）回填完整值，再后续 increment 才准确。
  
  **Q6：落库的幂等累加怎么实现？**
  **A**：`UserCountDOMapper.insertOrUpdateFansTotalByUserId` 用 `INSERT INTO t_user_count (user_id, fans_total) VALUES (?,?) ON DUPLICATE KEY UPDATE fans_total = fans_total + ?`，依赖 `user_id` 唯一索引：不存在即插入、存在即累加，原子且防并发重复。
  
  **追问：ON DUPLICATE KEY UPDATE 有什么坑？**
  **追问A**：依赖唯一索引生效；多字段更新时要注意 `VALUES()` 的用法；并发下数据库行锁能保证两个合法更新不会互相覆盖，但唯一索引和 upsert 不等于消息幂等，重复的 `+1` 仍会被累加两次。
  
  **Q7：count 参数为什么可正可负？**
  **A**：关注/取关、点赞/取消点赞会让计数增减，聚合后的净变化量可为负（如取关多），`increment` 支持负数天然处理。
  
  **追问：会不会减成负数？**
  **追问A**：理论上基于源数据的净变化不会为负（历史基数在初始化时已写入）；异常场景可用 `MAX(0, ...)` 兜底。
  
  **Q8：为什么要两级 MQ（一级计数 + 二级落库）？**
  **A**：一级 MQ 做计数聚合（Redis），二级 MQ 做落库解耦——聚合与落库解耦，落库消费者还能再令牌桶削峰，避免"聚合后的更新"再次冲击 DB。
  
  **追问：两级 MQ 消息丢失怎么办？**
  **追问A**：先看生产确认、消费返回、重试队列和死信，不能笼统说“MQ 不丢”。计数消息即使丢失，源表和 data-align 可能在次日把计数覆盖回来；但如果事实关系本身没有落库，data-align 没有来源可重算。BufferTrigger 进程内未落批消息还可能绕过 MQ 直接丢失，生产应增加可重放事件或落盘缓冲。
  
  **Q9：计数和 Redis 缓存的一致性怎么保证？**
  **A**：增量靠 MQ 精确累加（upsert 幂等），基数靠查询侧初始化；偏差靠 data-align 次日从源表重算回写兜底。
  
  **追问：如果实时计数和重算值不一致，以谁为准？**
  **追问A**：以重算值（源表 count）为准，实时链路只保证"准实时"，最终一致性由对齐任务收敛。
  
  **Q10：计数服务支持哪些计数？**
  **A**：用户维度：粉丝数、关注数、获赞数、获收藏数、发布笔记数；笔记维度：点赞数、收藏数。Redis 字段与 data-align 回写字段一一对应。
  
  **追问：新加一种计数类型要改哪些地方？**
  **追问A**：新增 Redis 字段常量 + count 消费者 + `t_user_count` 列 + upsert 方法 + data-align 临时表/对齐任务，链路较长，这也是拆独立对齐服务的原因之一。

  ## 7. 数据对齐服务（data-align）
  
  **Q1：为什么需要数据对齐服务？**
  **A**：点赞/收藏/关注/发布的明细操作频繁，如果每次都直接重算总数会产生写放大；实时计数又可能因重复消费或故障漂移。因此当天只记录“哪些 userId/noteId 发生过变化”，次日由 XXL-JOB 分片任务从源表重新 `count`，覆盖计数表并修正 Redis。它是计数兜底，不是所有业务事实的备份。
  
  **追问：实时计数还有存在的必要吗？**
  **追问A**：有。实时计数让详情页立刻有值（体验好），对齐是兜底修正；两者配合：实时准实时、对齐最终一致。
  
  **Q2：分片存储是怎么做的？**
  **A**：临时表按 `日期 + 分片序号` 拆分，例如 `t_data_align_*_count_temp_{yyyyMMdd}_{分片}`；消费者按 `id % tableShards` 写入。分片数来自 `table.shards` 配置，当前默认值和运行期配置必须以 Nacos 为准。日期让数据可过期清理，分片让 XXL-JOB 能并行处理，但修改分片数会改变后续取模结果，不能随意在线切换。
  
  **追问：分片数改大后旧分片表怎么办？**
  **追问A**：只影响后续写入分布（mod 结果变化），旧表数据靠删表任务清理；建议稳定后不轻易改，或改后做全量重算。
  
  **Q3：XXL-JOB 分片广播的原理？**
  **A**：分片广播 = 一次调度把任务分发给**所有注册实例**，每个实例通过 `XxlJobHelper.getShardIndex()/getShardTotal()` 拿到自己的分片序号和总数，只处理自己分片对应的临时表，互不冲突、并行执行。
  
  **追问：实例数必须等于分片数吗？**
  **追问A**：XXL-JOB 的 shardTotal 由在线执行器数决定，而临时表的分片数由 `table.shards` 决定，两者不是天然相等。实例少于业务分片数时可能有表无人处理；实例数变化还会让任务分片重新分配。部署时要保证每个业务表分片都有执行器覆盖，并把“本次任务处理了哪些日期/分片”写进日志，不能只看任务总状态成功。
  
  **Q4：为什么点赞/收藏要用"双"布隆过滤器？**
  **A**：同一个发布者有多篇笔记当天被点赞时，若笔记 ID 和发布者 ID 绑在一个事务写两张表，发布者维度撞 `uk_user_id` 导致整体回滚、第二篇笔记丢失。双 Bloom 让笔记 ID 与发布者 ID **各自独立判断、独立落库、互不影响**。
  
  **追问：单 Bloom（只有笔记 ID）不行吗？**
  **追问A**：单 Bloom 只能去重笔记维度，无法避免发布者维度的重复 insert 冲突，正是这个 bug 的根因。
  
  **Q5：布隆过滤器原理和误判？**
  **A**：多个哈希函数把元素映射到 bitmap 位；判断存在时只要有一位为 0 则一定不存在，全为 1 才判存在（可能误判）。本项目用 RedisBloom 的 BF 命令，存的是 ID 哈希指纹，**只可能误判"已存在"（假阳性），不会漏判**。
  
  **追问：误判会有什么后果？**
  **追问A**：假阳性会把本来没处理过的对象当成已处理，从而不写入当天临时表。如果该对象没有其他记录，次日对齐任务可能根本拿不到它，不能简单说“次日一定自动修复”。因此 Bloom 只能作为降重优化，生产需要合理误判率、定期重建或独立事件日志，并对源表与计数表做抽样校验。
  
  **Q6：为什么"先落库、后登记"（BF.ADD 在 insert 成功后）？**
  **A**：保证"已登记 = 已落库"。若 insert 失败仍登记，该条当天不会重试，数据静默丢失；先落库后登记，失败可重试（MQ 或下一条消息再次触发）。
  
  **追问：insert 冲突（并发重复）时怎么办？**
  **追问A**：撞唯一索引抛异常被 catch 吞掉，不登记也不影响——另一条并发消息成功时会登记；临时表唯一索引是并发兜底。
  
  **Q7：9 个 Job 分别干什么？**
  **A**：建表 1 个（`CreateTableXxlJob` 建次日 7 类 × 分片表）、对齐 7 个（关注/粉丝/笔记点赞/笔记收藏/用户获赞/用户获收藏/发布，各读对应临时表 → 源表 count → 回写计数表 + Redis → 删记录）、删表 1 个（`DeleteTableXxlJob` 清理一个月前）。
  
  **追问：为什么建表任务建"明天"的表？**
  **追问A**：当天消费写的是当天表，建表需提前一天把次日表建好，否则次日对齐/当天消费可能"表不存在"；对齐任务查询前还有 `CREATE TABLE IF NOT EXISTS` 兜底。
  
  **Q8：对齐任务的处理逻辑是什么？**
  **A**：死循环分批（1000 条/批）：`selectBatch` 临时表 ID → 对每个 ID 从源表 count 出准确值 → 更新计数表 + 更新 Redis Hash（存在才更新）→ 批量删除已处理记录 → 空则退出。
  
  **追问：为什么处理完要删除临时表记录？**
  **追问A**：对齐是"一次性消费"，删除防止第二天重复处理（幂等）；删表任务只删整表，记录级删除由对齐任务完成。
  
  **Q9：为什么用临时表 + 次日重算，而不是直接更新计数？**
  **A**：直接更新（实时）写放大 + 漂移；临时表只记"谁变了"（几行），次日重算把 N 次变动收敛成 1 次准确更新，且以源表为准天然准确。
  
  **追问：源表数据量大会不会很慢？**
  **追问A**：count 走唯一索引（user_id/note_id）快速统计；分片并行 + 批处理，单用户/单笔记的 count 都是索引查找，量级可控。
  
  **Q10：临时表怎么建、怎么删？**
  **A**：`CreateTableMapper` 提供 7 个 `CREATE TABLE IF NOT EXISTS`（含 `uk_note_id`/`uk_user_id` 唯一索引）；`DeleteTableXxlJob` 循环最近一个月日期 × 分片 `DROP TABLE IF EXISTS`。建/对齐/删三个任务时间错开。
  
  **追问：表结构为什么带唯一索引？**
  **追问A**：唯一索引把同一日期、同一分片内的重复记录挡住，防止对齐任务重复处理同一个对象；但它只解决重复写，不解决 Bloom 假阳性漏记，也不替代跨分片或跨实例的任务覆盖检查。

  ## 8. 分布式 ID（distributed-id-generator）
  
  **Q1：分布式 ID 要满足什么要求？**
  **A**：全局唯一、趋势递增（利于索引）、高可用、高性能。本项目用户注册、笔记发布都需要全局唯一 ID。
  
  **追问：数据库自增主键为什么不行？**
  **追问A**：单库自增有上限且分库分表后冲突；多实例各自自增不唯一。
  
  **Q2：号段模式（Segment）的原理？**
  **A**：DB 维护一张号段表（`leaf_alloc`），每次从 DB 取一段连续 ID（如步长 1000）缓存到内存，用完再取；取号段时 CAS 更新 step，避免并发冲突。
  
  **追问：号段用完了会怎样？**
  **追问A**：内存号段耗尽会阻塞等待下一次 DB 取号；用**双 buffer**（提前加载下一段）避免临界阻塞。
  
  **Q3：双 buffer（双 Segment）是怎么工作的？**
  **A**：内存维护两个号段 buffer，一个在用、一个预加载；当前号段使用率过半时后台异步加载下一段，切换无感知，保证取号不断档。
  
  **追问：异步加载失败怎么办？**
  **追问A**：双 buffer 的容错——失败时仍可用当前号段，重试加载；极端情况降级/告警。
  
  **Q4：雪花模式（Snowflake）的原理？**
  **A**：64 位 = 1 位符号 + 41 位时间戳（毫秒）+ 10 位 workerId + 12 位序列号；同一毫秒内序列号递增，不同 workerId 保证全局唯一。
  
  **追问：workerId 怎么分配？**
  **追问A**：通过 ZooKeeper 临时节点注册分配（`SnowflakeZookeeperHolder`），保证集群内不重复；ZK 不可用时降级 `ZeroIDGen`（本地生成，牺牲部分唯一性保证可用）。
  
  **Q5：雪花模式时钟回拨怎么处理？**
  **A**：Leaf 内部校验时间不能回退，回拨时抛异常（`ClockGoBackException` 等）或等待追上；本项目有对应的异常体系兜底。
  
  **追问：时间回拨会怎样？**
  **追问A**：可能生成重复 ID（同一 workerId 同一毫秒）；需等待或拒绝服务，避免发重复 ID。
  
  **Q6：号段模式和雪花模式怎么选？**
  **A**：号段：性能高、ID 可预测、依赖 DB；雪花：无 DB 依赖、纯内存计算、依赖时钟与 ZK。本项目两者都提供，按业务选择（Feign 接口区分 `/segment` 与 `/snowflake`）。
  
  **追问：你们项目实际用了哪个？**
  **追问A**：项目同时暴露号段和雪花两类 Feign 接口，业务通过 key 选择生成器。回答时应沿调用方代码确认具体场景、key 和接口，不要凭“用户一定号段、笔记一定雪花”做未经核对的承诺；能确认的部分是号段适合需要趋势递增的业务，雪花适合高频且不希望每次依赖 DB 的业务。
  
  **Q7：为什么从 Redis 自增迁移到 Leaf？**
  **A**：Redis 自增（`INCR`）在单点/网络异常时可能跳号或不可用，且与业务耦合；Leaf 号段 + 雪花性能高、语义清晰、高可用。
  
  **追问：Redis INCR 的问题具体是什么？**
  **追问A**：Redis 主从切换可能丢计数（重复号）；集群模式下 INCR 不是严格全局单调；高并发下也是热点写。
  
  **Q8：ID 的全局唯一性最终靠什么保证？**
  **A**：号段靠 DB 号段分配（每段不重叠）+ 内存串行取号；雪花靠"时间戳 + workerId + 序列号"组合唯一，workerId 由 ZK 保证不重复。
  
  **追问：如果雪花序列号在同一毫秒内用完？**
  **追问A**：等待下一毫秒（时间戳变化后序列号归零），`SnowflakeIDGenImpl` 内部自旋等待。
  
  **Q9：ID 服务的接口怎么设计的？**
  **A**：`DistributedIdGeneratorFeignApi`：`/id/segment/get/{key}`（按业务 key 取号段 ID）、`/id/snowflake/get/{key}`；key 区分业务（如用户、笔记），各业务号段独立。
  
  **追问：为什么带 key？**
  **追问A**：不同业务的号段/雪花独立管理，避免相互影响、便于监控各业务消耗量。
  
  **Q10：ID 服务的可用性保障？**
  **A**：号段依赖 DB（可用性靠 DB），双 buffer 降低 DB 压力；雪花依赖 ZK（不可用降级 ZeroIDGen）；服务本身多实例 + Nacos 负载均衡。
  
  **追问：降级 ZeroIDGen 有什么代价？**
  **追问A**：本地生成 ID 无法保证集群唯一（可能重复），只适合"ID 冲突影响小"的场景兜底，正常情况应避免走到降级。

  ## 9. KV 存储（kv）
  
  **Q1：为什么笔记正文用 Cassandra 而不是 MySQL？**
  **A**：正文是大文本且访问模式主要是按内容 ID 读写，不需要复杂的关联查询。项目把元数据放 MySQL，把正文放 Cassandra 的宽列/分布式列族表，通过 KV 服务隔离存储访问。这样可以独立扩容和控制正文读写；代价是 Cassandra 与 MySQL 之间没有本地事务，发布和更新必须有补偿、对账和孤儿内容清理。
  
  **追问：为什么不用 Redis？**
  **追问A**：Redis 是内存存储，存海量大文本成本高、易淘汰；Cassandra 是磁盘持久化存储，适合大容量内容，Redis 更适合放热点小数据（缓存）。
  
  **Q2：KV 服务对外提供了哪些能力？**
  **A**：`KeyValueFeignApi`：新增、查询、删除笔记内容（`/kv/note/content/add|find|delete`），参数带笔记 ID。
  
  **追问：为什么按笔记 ID 存？**
  **追问A**：一个笔记 ID 对应一个正文，1:1 关系，直接以业务 ID 为 key 最自然。
  
  **Q3：笔记正文与元数据分离的好处？**
  **A**：①MySQL 行变小、查询快；②大文本独立扩展（Cassandra 集群扩容不影响 MySQL）；③读写分离管理，各自按需优化。
  
  **追问：事务怎么办？正文和元数据能同时失败吗？**
  **追问A**：跨存储无法用数据库事务；通过流程编排（先 KV 后 MySQL，失败补偿删除）或 MQ 补偿保证最终一致，本项目发布流程顺序写 + 失败清理。
  
  **Q4：Cassandra 的数据模型？**
  **A**：`note_content` 表位于 `xiaohashu` keyspace，使用 Spring Data Cassandra 的 `NoteContentRepository` 提供 CRUD。Cassandra 应准确称为宽列/列族数据库，不是传统分析场景里的“列式数据库”；查询必须围绕分区键设计，不能照搬 MySQL 任意条件查询。
  
  **追问：主键用 UUID 而不是业务 ID？**
  **追问A**：UUID 可以作为记录唯一标识并帮助分散分区，但业务关联仍需要保存 contentUuid 与 noteId 的映射，不能说“UUID 就自动等于笔记 ID”。如果需要按 noteId 查询，表模型必须把 noteId 设计为可查询的分区键或建立明确映射，否则会退化成不可接受的全表扫描。
  
  **Q5：KV 场景下 CAP 怎么权衡？**
  **A**：Cassandra 偏向 AP（可用性 + 分区容忍），弱一致性（最终一致）；正文内容场景能接受最终一致，换取高可用水平扩展。
  
  **追问：读到旧正文怎么办？**
  **追问A**：更新后短暂可能读到旧值（最终一致）；业务上可接受，极端场景可加版本号。
  
  **Q6：为什么用 Feign 接口而不是直接让 note 服务连 Cassandra？**
  **A**：微服务数据访问受控原则——每个服务只访问自己的数据存储，跨服务必须走接口，避免数据层耦合。
  
  **追问：kv 服务当前被谁调用？**
  **追问A**：接口已就绪（`KeyValueFeignApi`），note 服务发布/查询正文接入；当前业务链路已打通。
  
  **Q7：什么场景适合用 KV 存储？**
  **A**：大文本内容（正文）、无需复杂关系查询、读多写少、可接受最终一致——笔记正文典型匹配。
  
  **追问：和 MySQL 的关系型查询怎么配合？**
  **追问A**：关系查询（按用户查笔记列表等）走 MySQL，正文内容走 KV，两者以笔记 ID 关联。
  
  **Q8：Cassandra 本地部署注意什么？**
  **A**：配置 contact-points（本地 127.0.0.1:9042）、keyspace 需先创建；`CassandraConfig` 继承 `AbstractCassandraConfiguration` 配置连接。
  
  **追问：keyspace 没建会怎样？**
  **追问A**：连接报错；需先用 CQL 建 keyspace（可脚本初始化）。
  
  **Q9：正文内容会不会有敏感/超限问题？**
  **A**：接口层可做长度校验（发布时限制正文长度）；存储层 Cassandra 大文本无压力。
  
  **追问：超大内容性能？**
  **追问A**：单行大文本读多写少场景 Cassandra 处理良好；可配合 CDN/分块（演进方向）。
  
  **Q10：KV 服务后续演进方向？**
  **A**：热点正文加 Redis 缓存（读热降 Cassandra 压力），但必须配合版本号或失效消息；增加正文版本管理和审核状态；为 Cassandra 查询建立按业务访问模式设计的分区键，并补充 MySQL 元数据与正文的对账、孤儿内容清理和备份恢复演练。
  
  **追问：为什么现在没加缓存？**
  **追问A**：当前笔记详情已经缓存元数据，正文仍通过 KV RPC 获取，项目规模和访问量下先保持实现简单。若正文成为热点，再增加正文级缓存，但要单独解决正文更新失效、缓存穿透和 Cassandra 降级，不能因为元数据有三级缓存就认为正文也被缓存了。

  ## 10. 对象存储（oss）
  
  **Q1：为什么需要 OSS 服务？**
  **A**：用户头像/背景图、笔记图片/视频等文件不能存数据库，需对象存储（Minio / 阿里云 OSS），提供上传、URL 访问、容量扩展。
  
  **追问：文件为什么不存本地磁盘？**
  **追问A**：多实例部署本地磁盘不共享、易丢失；对象存储高可用、容量弹性、访问 URL 直接给前端用。
  
  **Q2：策略模式是怎么设计的？**
  **A**：`FileStrategy` 接口定义上传方法 → `MinioFileStrategy`、`AliyunOSSFileStrategy` 两个实现 → `FileStrategyFactory` 工厂按配置 `storage.type` 注册对应 Bean；业务层只依赖接口，不感知具体实现。
  
  **追问：策略模式的好处？**
  **追问A**：新增存储实现只需加一个策略类，不改业务代码（开闭原则）；实现可替换。
  
  **Q3：Nacos 怎么动态切换存储实现？**
  **A**：`FileStrategyFactory` 用 `@RefreshScope`，配置 `storage.type` 变化时重新注入对应策略 Bean，运行期切换 Minio/OSS 无需重启。
  
  **追问：切换瞬间会不会有影响？**
  **追问A**：新上传走新实现，已上传文件 URL 不变（文件已存），无影响；只需保证两个实现都可用。
  
  **Q4：文件上传的流程？**
  **A**：当前是服务端中转：前端 multipart 表单进入 `FileController (/file/upload)`，`FileServiceImpl` 根据工厂选出的 `FileStrategy` 调用 Minio 或阿里云 OSS，成功后返回 URL，业务服务再保存 URL。Feign 跨服务传文件需要 `SpringFormEncoder`。这条链路适合中小文件；大文件直传、分片和断点续传属于演进，不要把它说成已经实现。
  
  **追问：为什么走服务端转发而不是前端直传 OSS？**
  **追问A**：中转便于做鉴权、类型/大小校验和统一审计，但业务服务承担全部文件带宽；直传通过 STS 让客户端直接写对象存储，服务端只签发权限并确认结果，适合大文件。直传要限制 bucket、目录、有效期和回调签名，不能只返回一个永久 URL。
  
  **Q5：上传有哪些安全/规范考虑？**
  **A**：文件类型/大小校验、文件名处理（防路径穿越）、按用户/业务隔离目录、防盗链（演进）。
  
  **追问：本项目做了哪层校验？**
  **追问A**：接口层 + 业务层参数校验；生产需补文件类型白名单、大小上限、签名 URL。
  
  **Q6：Minio 和阿里云 OSS 有什么区别？**
  **A**：Minio 自部署（开源、S3 兼容、适合私有化/开发），OSS 云服务（免运维、高可用、按量付费）；本项目通过策略模式兼容两者。
  
  **追问：生产选哪个？**
  **追问A**：有云预算选 OSS（省运维）；数据敏感/私有化选 Minio。策略模式让切换零成本。
  
  **Q7：上传返回的 URL 是永久的吗？**
  **A**：是否永久取决于桶权限和 URL 类型，不能只看接口返回字符串。公共读 URL 易泄露且难撤销；生产私有桶通常返回短期预签名 URL 或使用 CDN 鉴权。本项目应按当前 Minio/OSS 配置如实回答，开发配置不能代表生产安全策略。
  
  **追问：私有桶怎么访问？**
  **追问A**：用预签名 URL（服务端生成带签名的临时链接）或 CDN + 鉴权回源，前端拿签名 URL 直接访问。
  
  **Q8：大文件上传怎么优化（演进）？**
  **A**：分片上传 + 断点续传（OSS/Minio 均支持）、服务端合并；当前项目以普通上传为主。
  
  **追问：分片上传的并发问题？**
  **追问A**：分片按 uploadId 关联，服务端需做分片去重与合并校验，失败可重传未完成分片。
  
  **Q9：图片处理（缩略图/裁剪）怎么做？**
  **A**：OSS 提供图片处理服务（阿里云 ImageService / Minio + Thumbor）；当前项目直接存原图，演进可加缩略图 URL。
  
  **追问：为什么笔记列表用缩略图？**
  **追问A**：列表页并发高，原图流量大加载慢；缩略图大幅降带宽与首屏时间。
  
  **Q10：OSS 服务的接口设计？**
  **A**：`FileFeignApi`（`multipart/form-data`），`FeignFormConfig` 配置 `SpringFormEncoder` 支持文件表单编码（Feign 默认不支持 multipart，需专门配置）。
  
  **追问：Feign 传文件踩过什么坑？**
  **追问A**：Feign 默认编码器不支持 multipart，必须加 `SpringFormEncoder`，否则文件流无法正确编码传输。
  
  ## 11.遇到的问题
  
  #### 1.XXL-Job 任务报 job handler not found（@RefreshScope 冲突）
  
  **报错现象**
  
  xxl-job-admin 调度日志：
  
  ```
  code: 500
  msg: job handler [createTableJobHandler] not found.
  ```
  
  执行器只启动了一个实例、`@Component` + `@XxlJob("createTableJobHandler")` 写法也正确，但任务一直失败；服务启动日志里**看不到** `register jobhandler success, name:createTableJobHandler` 这行注册日志。
  
  **根因**
  
  `@RefreshScope` 加在了 Job 类上。XXL-Job 的 `XxlJobSpringExecutor` 注册 handler 的流程是：
  
  1. `applicationContext.getBeansWithAnnotation(XxlJob.class)` 找到带注解的 Bean
  2. 反射 `bean.getClass().getDeclaredMethods()` 找方法上的 `@XxlJob` 注解
  
  而 `@RefreshScope` 会把该 Bean 替换成 **CGLIB 代理对象**（为了支持配置热刷新），第 2 步拿到的是代理类，代理类生成的方法**不携带 `@XxlJob` 注解** → handler 被静默跳过，任务调度时执行器侧就报 `job handler not found`。
  
  > 验证过的现象：同一个 Job 类，加 `@RefreshScope` 前注册正常（日志有 register success），加上后立刻注册不上——即"加了动态刷新，handler 就没了"。
  
  **解决办法**
  
  1. **Job 类上去掉 `@RefreshScope`**（只保留 `@Component` + `@XxlJob`）
  2. 需要动态刷新的配置（如 `@Value("${table.shards}")`）**单独放到一个 `@RefreshScope` 的配置类**（如 `TableConfig`），Job 类注入该配置类使用：
  
  ```java
  @Component
  @RefreshScope
  @Data
  public class TableConfig {
      @Value("${table.shards}")
      private int shards;
  }
  ```
  
  ```java
  @Component   // Job 类不再加 @RefreshScope
  public class CreateTableXxlJob {
      @Resource
      private TableConfig tableConfig; // 动态配置注入，Nacos 改配置自动生效
      ...
  }
  ```
  
  3. 重启服务，确认启动日志出现 `xxl-job register jobhandler success, name:createTableJobHandler`
  4. 再到 admin 触发任务验证
  
  **排查技巧**：
  
  - 先看执行器启动日志有没有 `register jobhandler success`——没有 → 注册侧问题（如本次 @RefreshScope）；有 → 是调度侧问题
  
  - 调度侧问题通常是**多实例/脏地址**：旧进程没关、admin 执行器列表残留旧地址，任务轮询路由到没有该 handler 的旧实例。用 `netstat -ano | findstr <执行器端口>` 确认只有一个实例，admin 执行器管理里只保留一个在线地址
  
  - 执行器配置 `ip:` 留空会自动获取本机 IP，若机器 IP 会变，建议固定 `ip: 127.0.0.1`
  
  #### 2. 数据对齐中同一作者的第二篇笔记没有记录
  
  **现象**：同一天内，用户点赞同一作者的多篇笔记，第一篇能进入 data-align 临时表，第二篇的 noteId 却没有记录；第二天对齐后，作者维度的获赞/获收藏计数可能少算。
  
  **根因**：原设计把 noteId 和 noteCreatorId 放在同一条去重/插入链路中。临时表对作者维度有 `uk_user_id` 唯一约束；同一作者的第二篇笔记再次写入时触发唯一键冲突，如果两类记录放在同一个事务里，异常会让整次写入回滚，连本来应该记录的新 noteId 也丢失。单独只用 noteId 的 Bloom 只能防笔记重复，不能解决作者维度冲突。
  
  **修复和当前口径**：将 noteId 与 noteCreatorId 拆成两个 Bloom 判断和两个独立落库动作；先确保临时表 insert 成功，再登记 Bloom，避免“先登记、后落库失败”造成静默漏记；保留临时表唯一索引作为并发兜底。面试时要补充 Bloom 假阳性风险：它可能把新对象误判为已存在，导致该对象没有进入临时表，不能宣称对齐一定能发现所有漏记。
  
  #### 3. 服务启动顺序和依赖就绪问题
  
  **现象**：本地同时启动 Nacos、RocketMQ、Redis、MySQL、Cassandra、XXL-JOB 和多个业务服务时，部分服务注册失败、Feign 调用超时，或 XXL-JOB 执行器显示在线但 handler 尚未注册。
  
  **排查顺序**：先确认基础设施端口和健康状态，再看 Nacos 注册/配置拉取；之后检查网关、auth、user、note 等服务的启动日志，最后验证 RocketMQ producer/consumer、Cassandra keyspace 和 XXL-JOB handler。不能只看 Spring Boot 的“Started”日志，因为异步消费者、任务 handler 和外部连接可能仍未就绪。
  
  **改进方案**：生产使用健康检查和 readiness，将“进程已启动”和“可以接收流量”分开；Feign 调用配置连接/读取超时和有限重试，写请求必须幂等；XXL-JOB 执行器启动后确认 `register jobhandler success` 再启用任务；Cassandra/MySQL 初始化脚本和 Nacos 配置纳入部署顺序。依赖暂时不可用时应快速失败或降级，避免启动线程无限阻塞。
  
  #### 4. 异步链路成功但数据没有落到最终计数
  
  **现象**：接口返回成功，Redis 中短时间有变化，但 MySQL 计数表没有更新，或 BufferTrigger/二级 MQ 消费后计数多加。
  
  **排查思路**：沿事件唯一标识检查“业务事实写入 → 一级 MQ 生产确认 → count 消费 → BufferTrigger 是否入批 → Redis Hash 更新 → 二级 MQ 生产确认 → 落库消费者/重试/死信 → MySQL upsert”。重点看进程重启导致的内存丢批、消息重复投递、数据库唯一键和锁等待。
  
  **改进方案**：为计数事件增加业务幂等键和处理记录；对 MQ 生产失败、重试和死信做告警；BufferTrigger 不应作为唯一可靠缓冲，生产可使用可重放事件日志或在落批前持久化；最终以 data-align 从源表覆盖计数，并对齐前后做抽样校验。这样回答比“有 MQ 所以最终一致”更完整。
