## 三、项目简介

面向图文和视频内容发布、互动与搜索的内容社区平台，支持用户认证、笔记发布与编辑、笔记详情、点赞收藏、关注关系、评论、计数和用户/笔记搜索。后端基于 Spring Cloud Alibaba 拆分为网关、认证、用户、笔记、关系、计数、搜索、对象存储、KV 存储和数据对齐等服务，围绕热点内容读取、高频互动写入、缓存一致性、消息异步化和搜索索引同步实现业务链路。

## 五、简历项目描述（推荐版）

### 1. 统一认证与跨服务用户上下文

针对微服务请求经过网关后需要在多个下游服务中识别当前用户的问题，使用 Sa-Token 在 Gateway 完成登录态校验，由网关过滤器将用户 ID 写入请求头；下游服务通过统一 Starter 将请求头解析到用户上下文，Feign 调用时自动透传用户 ID，并在请求结束后清理上下文，统一了认证链路和业务服务的用户身份获取方式。

### 2. 笔记详情多级缓存与并行组装

针对笔记详情同时依赖 MySQL 元数据、KV/Cassandra 正文和用户服务信息的问题，采用 Caffeine → Redis → MySQL 的多级读取链路，使用空值缓存处理不存在笔记的重复请求，并通过 `CompletableFuture` 并发获取作者信息和正文内容；缓存命中后仍执行笔记可见性校验，支持公开和仅自己可见等访问规则。

### 3. 笔记更新的缓存一致性处理

针对笔记更新后 Redis、本地缓存和数据库可能返回旧数据的问题，更新流程先删除 Redis 详情缓存，再通过 RocketMQ 广播消息清理各实例本地缓存，同时发送延迟消息进行二次删除；笔记元数据更新和正文 KV 更新分别执行对应的事务与失败处理，形成数据库、缓存和异步消息之间的最终一致性链路。

### 4. 点赞、收藏和关注的高频互动链路

针对点赞、收藏和关注请求存在重复操作且直接同步写数据库的问题，使用 Redis Bloom 进行快速判重，使用 ZSET 保存用户与笔记或用户之间的关系状态，并通过 Lua 脚本原子完成状态检查和变更；状态变化通过 RocketMQ 异步发送到持久化消费者，关注与取关消息按照用户维度发送顺序消息。

### 5. 互动计数的异步聚合与数据校准

针对点赞、收藏、关注等操作产生大量计数更新的问题，使用 RocketMQ 将互动事件与计数处理解耦，count 服务通过 BufferTrigger 按批次和时间窗口聚合增量，Redis Hash 用于准实时展示，MySQL 使用 upsert 持久化；data-align 服务按日期和分片记录发生变化的用户或笔记，XXL-JOB 分片任务从源表重新统计并回写计数数据。

### 6. MySQL 与 Elasticsearch 的索引同步

针对笔记和用户信息变更后搜索索引需要同步更新的问题，使用 Canal 订阅 MySQL 行变更事件，根据新增、修改和删除事件更新或删除 Elasticsearch 文档；搜索服务使用 Bulk 请求批量写入索引，Canal 消费采用批次 ACK，索引处理异常时回滚消费位点，支持失败批次重新处理。

## 七、项目 30 秒介绍

我参与开发的是“拾笺”内容创作与互动平台，主要业务包括图文和视频笔记、点赞收藏、关注关系、评论和搜索。项目采用 Spring Cloud Alibaba 微服务架构，比较核心的设计有三部分：笔记详情使用 Caffeine、Redis 和 MySQL 多级缓存，正文通过 KV/Cassandra 服务独立存储；点赞、收藏和关注先通过 Redis 和 Lua 完成状态处理，再使用 RocketMQ 异步落库；互动计数通过 BufferTrigger 聚合，配合 Redis 准实时展示、MySQL 持久化和 XXL-JOB 定时重算。搜索部分使用 Canal 捕获数据库变化并同步 Elasticsearch。

## 八、项目亮点的面试展开顺序

### 亮点一：为什么要把笔记正文从 MySQL 中拆出来？

项目将笔记标题、作者、图片、可见性等元数据放在 MySQL，正文通过 KV 服务访问 Cassandra。这样详情列表和权限查询不需要每次读取大文本，正文可以独立扩展和缓存。代价是发布和更新会涉及 MySQL 与 Cassandra 两个存储，项目通过失败清理、状态判断和后续补偿思路处理跨存储一致性。

### 亮点二：为什么点赞不能直接更新 MySQL？

点赞请求可能出现重复点击和短时间集中写入。如果每次请求都同步更新关系表和计数表，数据库会承担大量细粒度写操作。项目先用 Redis 记录用户和笔记的关系状态，Lua 保证判断与变更的原子性，再通过 RocketMQ 异步持久化；计数单独由 count 服务消费互动事件，避免互动请求直接阻塞在计数更新上。

### 亮点三：为什么已经有实时计数，还要 data-align？

实时链路关注页面响应速度，消息重试、重复消费、进程内批量缓冲和依赖异常都可能造成计数暂时偏差。data-align 不保存每一次加一操作，而是记录当天发生变化的对象，次日从点赞、收藏、关注等源表重新统计真实值，再覆盖 MySQL 和 Redis 中的计数，作为实时链路之外的校准机制。

### 亮点四：Canal 为什么需要 ACK 和 rollback？

搜索索引更新不是数据库事务的一部分。Canal 批次只有在对应的 Elasticsearch 文档处理完成后才确认；如果批量写入或单条索引处理失败，就回滚当前批次的消费位点，让后续任务重新处理，避免数据库已经变更但搜索索引永久缺失。
