# 场景设计题（含答案与追问）

> 大厂面试常考的"场景设计题"合集，答案以 `D:\java\xiaohashu\xiaohashu` 源码为准。
> 每题格式：**场景 → 设计思路 → 参考答案 → 追问 → 追问答案**。答案故意按“链路、数据、失败、边界”展开，面试时可以先给 30 秒版本，再根据追问展开。
> **口径说明**：`[现状]` 是源码已经实现的内容；`[演进]` 是当前项目没有实现、如果上生产会补的方案；`[风险]` 是当前方案必须主动承认的边界。不要把演进方案说成已经落地。
> 更新时间：2026-08-22

## 面试回答方法

遇到场景题，建议按下面顺序组织答案：

1. 先说目标和约束：读写比例、峰值、是否允许最终一致、数据丢失的代价。
2. 再画主链路：请求入口 → Redis/MQ → 消费者 → MySQL/Cassandra，并说明每一步写的是什么。
3. 再解释削峰和幂等：哪些地方批量、哪些地方用 Lua/唯一索引，重复消息会发生什么。
4. 最后说故障和兜底：Redis、MQ、数据库、消费者宕机时的表现，以及 data-align 能兜住什么、兜不住什么。

只说“加 Redis、上 MQ、最终一致”不够。面试官通常会继续追问：消息到底在哪产生、谁消费、如何确认、是否会重复、缓存失效后基数从哪里来。

## 1. 设计一个高并发点赞/收藏计数系统

**场景**：一篇爆款笔记 1 分钟内被点赞 10 万次，还要实时展示点赞数，且不能丢失。

**设计思路**：把“用户是否点过”和“总数是多少”拆成两条链路。前者必须在 note 服务内快速、原子地完成；后者允许异步聚合并最终一致。这样既不把 10 万次请求直接打到数据库，也不把 Redis 的临时计数误当成最终真相。

**参考答案**（本项目方案）：
1. **点赞入口（[现状]）**：note 服务先用 Bloom 判断笔记是否存在，再用 Redis ZSET 保存用户点赞集合；Lua 脚本在一次 Redis 执行中完成“是否已点赞、添加/取消、返回状态”等判断，避免多个请求在判重和写入之间产生竞态。这个步骤解决的是用户维度的幂等，不是总数落库。
2. **事件通知（[现状]）**：状态变化成功后发送 RocketMQ 顺序消息。消息中带有笔记 ID、作者 ID、操作者和增量方向，供 count 服务和 data-align 服务分别处理；取消点赞发送负增量。发送和消费是异步边界，接口不会等待 MySQL 更新完成。
3. **计数聚合（[现状]）**：count 服务消费消息后，使用 `BufferTrigger` 在进程内缓冲，配置为 `bufferSize(50000)`、`batchSize(1000)`、`linger(1s)`；同一笔记在一个批次内的多次 +1/-1 合并成净变化量，再更新 Redis Hash，并继续发送落库消息。Redis Hash 只承担准实时读，不负责保存完整的点赞明细。
4. **持久化与对齐（[现状]）**：落库消费者通过 `INSERT ... ON DUPLICATE KEY UPDATE` 累加 `t_note_count`，点赞明细表的 `(user_id, note_id)` 唯一索引保证状态关系不重复。data-align 记录当天发生变化的 noteId/作者 ID，次日按分片从 `t_note_like` 等源表重新 `count`，以覆盖写修正计数表和 Redis。
5. **必须说明的边界（[风险]）**：RocketMQ、Redis 或进程内 BufferTrigger 出故障时，页面可能短时间少显示或延迟显示；data-align 只能修正“已经进入源表、且被记录进临时表”的对象，不能证明所有中间消息都绝不丢失。因此项目口径是“准实时 + 最终对齐”，不是强一致，也不能说“绝对不丢”。

**追问：为什么不在点赞请求里直接写数据库？**
**追问A**：如果入口同步更新 MySQL，10 万次点赞至少产生 10 万次行更新，还会与索引维护、事务提交、锁竞争叠加，接口延迟会随峰值抖动。当前实现把高频状态判断放到 Redis/Lua，把计数更新交给 MQ 和 BufferTrigger；请求只等待 Redis 状态操作和消息发送。代价是用户刚点赞后，其他读请求看到的总数可能晚几百毫秒到几秒，必须向面试官明确这是有意选择的最终一致性。

**追问：Redis 挂了计数会丢吗？**
**追问A**：要分情况回答。若只是计数缓存丢失，查询侧应从计数表或源表初始化完整基数；若点赞状态所在的 Redis ZSET 丢失，则用户可能重复点赞，必须依赖 MySQL 明细表重建缓存，不能只说“MQ 会恢复”。如果 Redis 在状态写成功前宕机，事件可能没有产生；如果 BufferTrigger 在落批前进程宕机，内存中的净增量也可能丢。当前项目依靠 MySQL 明细和次日 data-align 做业务兜底，生产还应增加 Redis 持久化、消息发送确认/重试、BufferTrigger 落盘或可重放日志，并对丢失窗口报警。

## 2. 设计一个笔记详情的多级缓存（含更新一致性）

**场景**：笔记详情读多写少，要求读快（毫秒级）、更新后尽量及时生效。

**设计思路**：缓存的对象要先说清楚：本项目缓存的是笔记详情元数据，不是把所有内容都塞进 Redis。正文仍在 Cassandra/KV 服务，作者信息通过 user 服务获取；详情组装时再并行拉取。更新时采用失效而不是主动拼装完整对象，接受短暂最终一致。

**参考答案**（本项目方案）：
1. **读取链路（[现状]）**：先查当前实例 Caffeine，再查共享 Redis，最后查 MySQL 的 `t_note` 元数据。Redis/Caffeine 命中后仍要按需补齐作者和正文；note 服务用 `CompletableFuture` 并发调用 user RPC 与 KV RPC，避免串行等待两个下游。
2. **缓存内容和 TTL（[现状]）**：不存在的笔记会写短 TTL 的空值占位，避免恶意 noteId 穿透数据库；正常详情使用“基础 TTL + 随机 TTL”打散过期时间。这里的 TTL 只是缓解手段，不等价于强一致。
3. **更新链路（[现状]）**：先更新 MySQL 元数据，再删除 Redis；随后发送 RocketMQ 广播消息，让每个 note 实例删除本地 Caffeine；最后发送约 1 秒延迟消息再次删除 Redis，处理并发读在第一次删除后回填旧值的窗口。
4. **为什么正文单独走 KV（[现状]）**：MySQL 只保存标题、媒体、可见性等关系型字段，正文通过 `KeyValueFeignApi` 从 Cassandra 读取。这样缓存 miss 时不是“直接查 MySQL 得到完整详情”，而是 MySQL + user + KV 三个来源拼装。
5. **一致性边界（[风险]）**：广播消息未送达、某实例消费失败、延迟消息失败或 Cassandra 与 MySQL 更新时序异常，都可能造成短时间旧数据；当前实现没有分布式事务，也没有互斥锁/逻辑过期。面试应说“通过删除、广播、TTL 收敛”，不要说“更新后立即所有节点一致”。

**追问：多级缓存的一致性最坏情况是什么？**
**追问A**：最坏不是简单的“Redis 旧”，而是不同层和不同来源组合出不一致：Caffeine 可能是旧元数据，Redis 可能已经删除，Cassandra 正文可能已经更新，作者服务也可能返回新资料。当前没有跨存储事务，所以只能保证通过广播删除和 TTL 最终收敛。支付、库存这类要求读后立即正确的场景不能照搬，应改为版本号、强制回源或事务消息。

**追问：为什么删缓存而不是更新缓存？**
**追问A**：主动更新缓存需要在写线程中重新查询并拼装元数据、作者和正文，还要处理多个并发更新的顺序；一旦某个下游失败，缓存可能比数据库更难恢复。删除缓存把复杂度放到下一次读：读请求发现 miss 后按固定顺序回源、组装、回填。它牺牲了更新后的瞬时命中率，但更容易重试和定位。若是极热点 key，生产可再引入逻辑过期或异步重建。

## 3. 一个热点笔记瞬间被 10 万人访问（缓存击穿/雪崩）

**场景**：一篇笔记上热搜，缓存刚好过期，10 万请求同时打向 DB。

**设计思路**：先区分击穿和雪崩：击穿是一个热点 key 失效，雪崩是大量 key 同时失效。当前项目已经做本地缓存和 TTL 打散，但没有完整的互斥重建，因此回答时要把“源码现状”和“生产演进”分开。

**参考答案**（本项目 + 演进）：
1. **当前能做的缓解（[现状]）**：Caffeine 让同一实例的热点请求不必每次访问 Redis；Redis TTL 带随机量，降低批量 key 同时失效的概率；空值占位阻止非法 ID 持续打 DB。
2. **当前缺口（[风险]）**：Caffeine 和 Redis 同时 miss 时，多个请求仍可能并发回源，源码没有 `setIfAbsent` 互斥锁，也没有逻辑过期对象。因此不能把“有 Caffeine”说成已经彻底解决缓存击穿。
3. **生产演进（[演进]）**：对热点 key 使用 Redis 分布式锁或单飞机制，只允许一个请求重建；其他请求短暂等待、读旧值或返回降级结果。更高流量时使用逻辑过期：缓存不物理删除，读到过期标记后由后台线程异步刷新，避免所有请求同时阻塞。
4. **雪崩止损（[演进]）**：为不同业务设置不同 TTL、预热热点、限流回源，并在 DB 连接池和线程池上设置上限。否则即使 Redis 只是短暂故障，也可能把压力整体转移到 MySQL。

**追问：本地缓存会不会造成各实例数据不一致？**
**追问A**：会。每个实例的 Caffeine 是独立内存，命中和过期时刻都不同；广播删除依赖 RocketMQ 广播消费成功，实例重启或消息消费失败时仍可能保留旧值。当前方案是“更新时广播删除 + Redis 延迟双删 + TTL 兜底”，只能把窗口压小，不能宣称强一致。生产还要监控广播消费失败，并在发布/更新接口返回版本号时让读侧拒绝旧版本。

**追问：互斥锁的缺点？**
**追问A**：锁能降低回源风暴，但会引入锁等待、锁续期和异常释放问题。锁超时太短会出现多个重建者，太长会把数据库故障放大成大量等待；拿到锁的线程在下游超时前必须释放或让锁自动过期。对允许短暂旧值的详情页，优先“读旧值 + 单线程后台刷新”，比让 10 万请求同步等待更稳。

## 4. 大 V 粉丝数激增：关注/粉丝系统如何扛住

**场景**：一个 1000 万粉丝的大 V 发动态，一小时内新增 50 万粉丝，粉丝数、粉丝列表、消息全量冲击系统。

**设计思路**：关注关系、粉丝数、粉丝列表和通知不是同一份数据，分别选择适合的存储和一致性策略。关系写入要防重复，计数写入要削峰，列表查询要控制返回规模，消息通知要能承受积压。

**参考答案**（本项目方案）：
1. **关系入口（[现状]）**：关注请求在 Redis ZSET 中用 Lua 原子完成“已关注判断、关注上限判断、写入关注者集合”；成功后发送 `FollowUnfollowTopic`，消费者再事务写 `t_following` 和 `t_fans`。Redis 先响应是为了保护接口延迟，MySQL 是关系持久化来源。
2. **落库削峰（[现状]）**：`FollowUnfollowConsumer` 消费前调用 Guava `RateLimiter.acquire()`，将 MQ 洪峰转换成可控制的数据库写入速率；消费者失败时应让消息重试，而不是在业务代码中静默吞掉。令牌桶只保护当前消费者实例，不能替代 MQ 的重试和集群扩容。
3. **计数链路（[现状]）**：关注关系落库成功后分别发送关注数和粉丝数计数消息。`CountFansConsumer` 用 BufferTrigger 按目标用户合并净增量，再更新 Redis Hash 并发二级 MQ 落 MySQL；一个大 V 的 50 万条关注可能被压缩为少量计数更新，但明细关系仍要逐条落库。
4. **读侧（[现状]）**：粉丝数优先读 `count:user:{id}` Hash；粉丝列表不把千万级成员全部放 Redis，而是按 `create_time desc` 在 MySQL 分页，另有固定上限的 5000 条查询用于展示/推送。
5. **兜底与边界（[现状]/[风险]）**：data-align 次日从 `t_fans` 重算粉丝数并覆盖回写。它能修正计数偏差，不能替代关系明细的实时落库；如果 MQ 长期积压，页面会先表现为计数滞后，列表也可能暂时查不到刚关注的数据。

**追问：粉丝列表要不要放 Redis？**
**追问A**：全量放 Redis 会把一个大 V 的粉丝关系变成超大的热 key，内存、重建时间和主从同步成本都很高，更新也难与 MySQL 保持一致。项目只提供最近 5000 条的受控查询，用于展示或推送；真正的全量列表按索引分页。若生产需要高频翻页，可以按用户分片、冷热分层，或将关注关系同步到专门的检索存储，但仍要定义 MySQL 与索引的最终一致边界。

**追问：50 万条关注 MQ 会不会压垮消费者？**
**追问A**：MQ 只是持久化和缓冲，不能直接保证“积压不丢”；还要看生产确认、重试、死信和保留时间。处理顺序应是：先查消费者异常和重试队列，再增加同一消费组实例/线程，确认分区和并发度足够，最后按数据库承载能力调整令牌桶。粉丝计数可以聚合，但 `t_following/t_fans` 明细不能简单跳过；最多是在确认源表已完整、且有可重放/对账方案后做受控降级。

## 5. MQ 消息积压百万条怎么办

**场景**：凌晨一次性导入数据或消费端故障，`CountFansTopic` 积压了 100 万条消息，消费滞后严重。

**设计思路**：积压处理的核心是先判断消息代表的是“事实明细”还是“可重算计数”。前者不能随便丢，后者在源表完整且有对账的前提下才可降级。处理过程必须同时关注消费延迟、重试/死信、数据库写入速率和消息保留时间。

**参考答案**：
1. **先止血（[通用]）**：看生产速率、消费速率、最老消息年龄、重试次数和死信数量，确认是消费者挂死、下游 DB 慢、线程池耗尽还是流量突增。先暂停非关键批任务，避免对齐任务与积压消费同时争抢数据库。
2. **再恢复吞吐（[通用]）**：修复异常后扩充同一消费组实例或消费线程，检查 RocketMQ 队列数是否足够；逐步调高批量和并发，持续观察 DB 锁等待、连接池、CPU，而不是一次性把并发拉满。
3. **利用聚合（[现状]）**：count 侧的 BufferTrigger 可以把同一目标对象的增量合并，减少计数表更新，但不能替代关注/点赞明细消息。对明细消息要保留重试和死信，必要时按业务优先级分流。
4. **使用对齐兜底（[现状]/[风险]）**：data-align 只能在源表已经正确落库、且变更对象成功写入日增量临时表时修正计数。不能因此宣称“消息可以直接跳过”或“消息不会丢”；跳过前必须有离线重放、源表校验和业务负责人确认。

**追问：为什么本项目对积压"不慌"？**
**追问A**：只能说“计数有较强兜底”，不能说整个业务不怕积压。粉丝/点赞总数有源表重算，最坏是展示滞后；但如果关系明细没有落库，data-align 没有事实来源，无法把它凭空补回来。还要关注消息保留期、死信处理和临时表是否成功写入。

**追问：积压会不会拖垮 DB？**
**追问A**：有可能。积压恢复时如果瞬间放开消费，批量 upsert 会形成新的 DB 洪峰。应通过令牌桶、批量大小、消费者并发和数据库连接池共同限速；对齐任务与实时消费共享源表/计数表时，还要错峰或降低优先级。所有临时调参都要记录恢复前后的消费延迟、DB QPS 和错误率。

## 6. 保证 MQ 消费幂等（重复消费不重复处理）

**场景**：RocketMQ 是"至少一次"投递，消费者宕机重启后同一消息可能被重复消费，怎么保证不重复处理？

**设计思路**：先给消息定义业务语义，再选择幂等方式。状态消息可以按业务主键 upsert，净增量消息必须有唯一事件 ID 或可重算来源，日增量记录则用 Bloom 加临时表唯一索引降低重复写。

**参考答案**（本项目三种手段）：
1. **状态明细（[现状]）**：点赞/收藏明细表以 `(user_id, note_id)` 做联合唯一索引，重复消费同一个状态不会插入第二行；取消操作按同一业务主键删除，重复删除无副作用。这里的幂等键是“谁对哪篇笔记”，不是 MQ 的 messageId。
2. **计数增量（[风险]）**：`ON DUPLICATE KEY UPDATE total = total + ?` 只保证并发下的原子累加，不保证同一增量消息重复到达时不重复计算。当前依赖上游状态判重、BufferTrigger 合并和最终 data-align；生产应给事件加唯一 ID/消费记录，或把计数改为按源表覆盖重算。
3. **日增量记录（[现状]）**：data-align 使用 noteId Bloom 和 noteCreatorId Bloom 分开判断，并由日期+分片临时表的唯一索引兜底。双 Bloom 是为避免同一作者多篇笔记时，作者维度唯一索引冲突导致整条事务回滚。

**追问：计数累加如果消费端重复发送会怎样？**
**追问A**：会，`+1` 到达两次就会累加两次；数据库 upsert 的“原子”不等于“幂等”。要么在消息中携带唯一事件 ID，消费前做去重并记录处理状态；要么只把计数当缓存，定期从点赞/关注源表覆盖重算。项目采用后者作为最终兜底，但实时窗口仍可能短暂偏大。

**追问：布隆过滤器防重复的局限？**
**追问A**：Bloom 只能保证“判断不存在时一定不存在”，判断存在可能是假阳性。假阳性会让本来应该写入的日增量被跳过；如果该对象没有进入临时表，后续对齐任务也可能根本不会处理它，所以不能简单说“次日一定修复”。当前只能把 Bloom 当作降重优化，生产要通过更低误判率、定期重建或独立事件日志降低风险。

## 7. 设计一个全局唯一且趋势递增的分布式 ID 方案

**场景**：分布式系统需要全局唯一、趋势递增、高可用、高性能的 ID。

**设计思路**：先明确 ID 的使用场景：是否要求连续、是否暴露给用户、是否允许号段浪费、是否能接受时钟回拨。号段和雪花没有绝对优劣，关键是把唯一性、高可用和可运维性讲清楚。

**参考答案**（本项目美团 Leaf）：
1. **号段模式（[现状]）**：Leaf 从 `leaf_alloc` 号段表通过 CAS 更新 step，一次取一段连续区间到本地；业务线程在内存中递增取号，接近耗尽时双 Buffer 异步预加载下一段。它趋势递增且不要求每次请求访问 DB，但服务重启会浪费未用号段，DB 不可用时最多用完本地缓存。
2. **雪花模式（[现状]）**：Leaf 使用时间戳、workerId 和毫秒内序列号组合 ID；workerId 通过 ZooKeeper 注册。它不依赖每次 DB 请求，适合高频写入，但必须处理时钟回拨、workerId 重复和序列号用尽。
3. **项目选型（[现状口径]）**：项目同时提供 `/segment` 和 `/snowflake` 接口，具体业务要以调用方代码为准，不能只凭“用户 ID/笔记 ID”猜测。面试回答应指出调用链和 key，而不是把所有 ID 都概括成一种模式。

**追问：号段模式 DB 挂了怎么办？**
**追问A**：如果已经取到本地号段，DB 短暂故障时仍可继续发号；当前号段用尽且下一段无法加载，就必须阻塞或失败，不能继续“本地猜一个”。双 Buffer 只是把 DB 故障窗口推迟，不是消除依赖；生产要监控号段剩余量、预加载失败和 DB 可用性，并准备明确降级策略。

**追问：雪花时钟回拨怎么处理？**
**追问A**：Leaf 检测到当前时间小于上次时间时不能继续按原 workerId 发号，否则可能与历史 ID 冲突。可选择抛 `ClockGoBackException`、等待时钟追上，或在有备用 workerId 时切换；NTP、虚拟机迁移和人工改时都要纳入监控。面试中要说明“保证唯一性优先于短暂不可用”。

## 8. 计数最终一致性：实时计数和真实值偏差了怎么办

**场景**：实时计数链路偶发丢消息/重复累加，粉丝数显示和真实粉丝数对不上。

**设计思路**：承认实时链路会错，用"以源表为准的重算"兜底收敛。

**参考答案**（本项目 data-align 方案）：
1. **实时层**：关注、点赞、收藏等操作先形成源表事实，再由 MQ/count 更新 Redis 和计数表，页面得到准实时值；这条链路追求低延迟，不承诺每一次增量都不会重复或丢失。
2. **记录变更对象**：data-align 只记录“当天哪些 userId/noteId 发生过变化”，而不是保存每一次 +1。临时表按日期和分片拆分，Bloom 降低重复 insert，唯一索引做最终兜底。
3. **次日重算**：XXL-JOB 分片广播后，各实例批量读取临时表，从 `t_fans`、`t_note_like`、`t_note_collection`、`t_following`、`t_note` 等源表重新 `count`，覆盖写计数表，并在 Redis key 存在时同步修正缓存，最后删除已处理记录。
4. **最终一致边界**：对齐只能修正“源表已有事实 + 临时表记录到的对象”。如果源表写失败、临时表建表失败、Bloom 假阳性导致记录未进入临时表，不能保证次日自动发现；因此还需要任务失败告警、全量抽样校验和必要的重跑机制。

**追问：对齐任务和实时任务同时写同一行会不会冲突？**
**追问A**：项目通过凌晨错峰降低冲突，但不是事务级协调。对齐执行时仍可能有新的关注/点赞写入：对齐读取源表的时间点不同，覆盖值可能暂时落后，随后实时增量再补上。生产可用快照时间、版本号或按业务日期切分，确保“对齐到哪个时间点”可追踪，而不是笼统说覆盖后就绝对正确。

**追问：对齐任务挂了怎么办？**
**追问A**：先看 XXL-JOB 调度日志、执行器日志和具体失败分片；确认是连接池、锁等待、表不存在还是实例没有拿到对应分片。失败分片应单独重跑，并保留临时表记录直到成功。只有在确认所有分片完成、计数抽样校验通过后，才删除历史表；不能把“任务配置了重试”当成已经成功。

## 9. 用户/笔记数据量级增长到亿级：怎么分库分表

**场景**：`t_note` 表 1 亿行，单表查询越来越慢。

**设计思路**：先索引/归档，再水平拆分；拆分维度与现有"分片对齐"机制结合。

**参考答案**：
1. **先确认瓶颈（[通用]）**：用执行计划、慢查询、表和索引基数判断是缺索引、深分页、热点锁还是单表容量问题；先做覆盖索引、冷热归档和查询字段裁剪。
2. **拆分维度（[演进]）**：若核心查询是“某用户发布的笔记”，按 `creator_id` 分片可以把查询路由到单分片；若核心是按笔记 ID 访问，按 `note_id` 更均衡，但用户列表需要额外索引表或检索服务。
3. **全局 ID 与路由（[现状/演进]）**：Leaf 保证主键跨分片唯一；分表后要在应用层或 ShardingSphere 中固定路由规则，避免同一用户的数据因规则变化无法定位。
4. **读写与迁移（[演进]）**：先双写/回填新表，再校验新旧数据，最后切读并保留回滚窗口；读写分离只能降低读压力，不能替代分片和索引设计。
5. **项目边界（[现状]）**：当前项目只在 data-align 临时表使用日期+取模分片，业务 `t_note` 尚未完成分库分表，不要把临时表方案说成线上业务表已经拆分。

**追问：分表后跨分片查询（如"我发布的笔记"）怎么办？**
**追问A**：按 `creator_id` 分片时可以根据用户 ID 直接路由，分页和排序在单分片内完成；按 `note_id` 分片时，用户的笔记散落多个分片，需要先查“用户→笔记 ID”索引，再批量回源并在应用层归并排序，复杂度和延迟都会上升。因此分片键必须由最主要的查询维度决定，而不是只看数据均匀性。

**追问：和项目里的分片对齐什么关系？**
**追问A**：临时表按 `id % shards` 解决的是日增量任务的并行处理和表生命周期，任务知道日期与分片即可定位数据；业务表分片还要解决跨分片查询、唯一索引、事务、扩容迁移和路由规则。两者能借鉴“取模和分片任务”思想，但不能直接等同。

## 10. 设计"关注的人"的笔记 Feed 流

**场景**：App 首页是"我关注的人发布的笔记"时间线，如何设计？

**设计思路**：Feed 的瓶颈取决于粉丝数和关注数：推模式把成本放在发布时，拉模式把成本放在读取时。要先定义分页一致性、去重、置顶和计数拼装，再选择普通用户与大 V 的不同策略。

**参考答案**：
1. **推模式（[演进]）**：发布笔记后查粉丝，把 noteId 和发布时间写入每个粉丝的 Redis ZSET 收件箱；读侧只需按 cursor 取 ID，再批量查详情。优点是读快，缺点是大 V 发布会产生粉丝数级写放大，必须异步投递、限速和设置收件箱容量。
2. **拉模式（[可基于现状演进]）**：读请求先从关注关系 ZSET 取关注用户，再按用户查询最近笔记并做归并排序；关注数大时 RPC/SQL 扇出明显，需要批量接口、热点用户缓存和游标。
3. **推拉结合（[生产选择]）**：普通用户采用推，大 V 或粉丝数超过阈值的用户采用拉；Feed 响应统一去重、过滤已删除/不可见笔记，并以 `(publish_time,note_id)` 作为稳定 cursor。
4. **项目边界（[现状]）**：拾笺当前已有关注关系 Redis ZSET、笔记元数据和计数服务，但没有完整 Feed 收件箱实现。面试应说“可以基于现有关系和笔记列表演进”，不要说项目已经实现推送 Feed。

**追问：Feed 里笔记点赞数怎么实时展示？**
**追问A**：Feed 收件箱只保存 noteId、发布时间和必要版本信息，不复制完整详情；组装响应时批量查 note 服务，再读取 `count:note:{id}` 的点赞/收藏字段。计数缓存 miss 要从计数表初始化完整基数，不能直接对不存在 Hash 做增量；data-align 负责最终纠偏。

**追问：推送的收件箱用什么数据结构？**
**追问A**：ZSET 用发布时间作为 score、noteId 作为成员，适合按时间倒序和 cursor 分页；同一 noteId 天然去重。实际还要处理 score 相同、删除笔记、不可见笔记和收件箱容量上限，常见做法是保留最近 N 条并异步清理。List 插入简单，但按时间范围和稳定分页不如 ZSET 直接。

## 11. 接口被刷/恶意请求：如何限流与防护

**场景**：登录接口被脚本刷、验证码接口被轰炸，如何防护？

**设计思路**：按“请求入口、业务规则、下游资源”三层做防护，并区分当前已有的验证码 TTL/消费者限速和生产需要补的网关限流。限流要回答清楚维度、返回方式、恢复策略，否则只是组件名堆砌。

**参考答案**（本项目 + 演进）：
1. **验证码业务限制（[现状]）**：验证码按手机号作为 Redis key 保存，TTL 实际为 3 分钟；发送逻辑写入 Redis 后异步调用短信服务。当前代码不能表述为“60 秒内不能重复发送”，除非配置和代码另有明确的发送间隔校验；面试时应以实际 TTL 和发送控制代码为准。
2. **消费者限速（[现状]）**：关注/取关落库消费者使用 Guava `RateLimiter`，速率由 Nacos 配置控制，防止 MQ 消费瞬间把数据库打满。这是消费端削峰，不会阻止恶意请求进入网关，也不能保护所有接口。
3. **网关限流（[演进]）**：生产可在 Gateway 按 IP、用户 ID、手机号和接口维度配置 `RequestRateLimiter`/Sentinel，并返回明确的 429；对登录和验证码要区分“同一 IP 多手机号”和“同一手机号多 IP”两类攻击。
4. **风控和资源保护（[演进]）**：增加图形/滑块验证码、黑名单、请求体大小限制、连接/线程池隔离，以及对短信供应商的熔断。限流规则要可动态调整并有命中率、误杀率和恢复时间监控。

**追问：令牌桶和漏桶区别？**
**追问A**：令牌桶按固定速率生成 token，桶内有余量时允许短时突发，适合“平时低流量、偶尔突发”的消费场景；漏桶把请求按固定速率流出，突发会排队或丢弃，延迟更稳定。当前项目令牌桶放在消费者侧，目标是控制数据库写入速率，不是接口级安全限流。

**追问：限流放网关还是业务层？**
**追问A**：网关负责尽早拒绝明显超量的请求，避免请求穿透所有服务；业务层根据手机号、用户状态、资源类型做更精细的规则；消费者侧再保护数据库写入。三层的阈值和返回码要协调，否则网关放行后业务层全部阻塞，用户只会看到超时。

## 12. 大文本笔记正文的存储方案

**场景**：笔记正文最长几万字符，量大（千万级笔记），如何存储与查询？

**设计思路**：把关系型查询和大文本读写拆开，但要明确 Cassandra 的准确定位：它是宽列/分布式列族数据库，不应简单说成“列式 KV”。note 服务只通过 KV 服务的 Feign 接口访问正文，避免跨服务直连 Cassandra。

**参考答案**（本项目方案）：
1. **数据分工（[现状]）**：MySQL `t_note` 保存标题、图片、视频、话题、可见性、作者等元数据；KV 服务使用 Cassandra `note_content` 表保存正文，Repository 负责 CRUD。note 服务发布时先通过 `KeyValueFeignApi` 写正文取得 contentUuid，再写 MySQL 元数据。
2. **读取链路（[现状]）**：详情缓存 miss 后，note 从 MySQL 读元数据，同时通过 KV RPC 读正文；作者信息再从 user 服务获取。Cassandra 负责持久化和水平扩展，Redis/Caffeine 只适合做热点缓存，不是正文的唯一存储。
3. **为什么不把正文放 MySQL（[现状判断]）**：不是说 MySQL 一定不能存 TEXT，而是大文本会放大行读取、备份和主从复制成本，且关系查询通常只需要元数据。拆分后可以分别扩容、限流和设置缓存策略。
4. **跨存储一致性（[风险]）**：MySQL 和 Cassandra 没有本地分布式事务。当前流程有顺序写和失败清理，但中途宕机仍可能留下孤儿正文或缺正文元数据；生产应增加状态字段、补偿任务、幂等写和对账，而不是宣称两边强一致。

**追问：为什么不用 MySQL TEXT 字段？**
**追问A**：MySQL TEXT 并非不能用，关键在访问模式和规模。如果详情查询经常只要标题/封面，正文跟着元数据一起回表会增加 IO；大文本还会影响备份、复制和缓存命中。当前项目选择 Cassandra 是为了让正文存储独立扩展，换来的代价是跨存储写一致性、查询链路更长和运维组件更多。

**追问：正文和元数据跨存储，写失败怎么办？**
**追问A**：发布必须设计可重试：正文写成功、MySQL 失败时，记录 contentUuid 并执行删除补偿，或把状态标成 `PENDING` 交给对账任务；MySQL 成功、正文读取失败时，详情应返回可识别的降级状态而不是把异常吞掉。当前项目是顺序写 + 失败清理，属于尽力而为的最终一致方案，仍应补充孤儿内容扫描和删除策略。

## 13. 文件上传下载的大文件场景

**场景**：用户上传大视频（几百 MB），或批量上传图片。

**设计思路**：先区分项目现状与大文件生产方案。当前 OSS 服务是普通 multipart 的服务端中转，解决的是统一鉴权和存储策略切换；几百 MB 视频的可靠传输还需要分片、校验、断点和异步处理。

**参考答案**（本项目 + 演进）：
1. **当前链路（[现状]）**：前端把 multipart 文件发到 OSS 服务，`FileController` 调用 `FileStrategy`；`MinioFileStrategy` 或 `AliyunOSSFileStrategy` 上传成功后返回 URL，Feign 侧通过 `SpringFormEncoder` 完成文件编码。当前链路会占用 OSS 服务的网络带宽和连接数。
2. **大文件上传（[演进]）**：先由服务端创建 `uploadId` 和临时凭证，客户端把文件切片并发上传到对象存储；服务端记录每个分片的 ETag/大小，全部完成后调用 complete，并校验总大小和哈希。失败只重传缺失分片，不重新传整个文件。
3. **一致性和清理（[演进]）**：上传状态要有 `INIT/UPLOADING/COMPLETED/ABORTED`，同一 uploadId 的分片接口幂等；超时未完成的 uploadId 由定时任务清理，避免对象存储残留。业务数据库只在 complete 成功后保存最终 URL。
4. **访问优化（[演进]）**：视频/图片完成后异步转码、生成缩略图和 CDN 地址；私有桶返回短期签名 URL，不能把永久公开 URL 当成通用安全方案。

**追问：服务端中转 vs 前端直传 OSS？**
**追问A**：服务端中转流程简单，鉴权、大小和内容校验都集中，但文件流会经过业务服务，吞吐受服务实例和带宽限制；前端直传用 STS 临时凭证，文件不经过业务服务，适合大文件和高并发，但需要严格限制 bucket、目录、有效期，并让服务端最终确认上传结果。当前项目是中转，直传属于演进。

**追问：分片上传的幂等/一致性？**
**追问A**：分片号应是 `(uploadId, partNumber)` 的幂等键，重复上传同一分片要覆盖或返回已完成；complete 前检查分片数量、顺序、大小和 ETag/哈希，避免缺片拼出损坏文件。合并请求也必须幂等，重复 complete 直接返回已生成 URL；异常 uploadId 由过期任务清理。

## 14. 慢查询优化：笔记列表分页越来越慢

**场景**：`select ... from t_note order by create_time desc limit offset, n` 在第 100 万页之后越来越慢。

**设计思路**：先用执行计划确认慢在哪里，再区分“查询本身慢”和“分页越深越慢”。不要一上来就分库分表；先让过滤条件、排序字段和返回列与索引匹配。

**参考答案**：
1. **证据优先（[通用]）**：用 `EXPLAIN`、慢查询日志和 Druid 监控确认是否全表扫描、回表过多、排序落盘或锁等待；再根据真实 where/order by 设计复合索引。
2. **分页改造（[通用]）**：`offset` 越大，数据库越要扫描并丢弃前面的记录。对按时间/ID 向下翻页的接口改成游标条件，如 `where (create_time,id) < (?,?) order by create_time desc,id desc limit n`，避免只用时间造成同一时间戳漏数或重复。
3. **减少回表（[通用]）**：列表只返回封面、标题、作者等必要字段，尽量让索引覆盖；详情再按 ID 查完整数据并走多级缓存。
4. **容量演进（[演进]）**：数据量继续增长后再考虑冷热归档、读写分离、按 creator_id 分表或引入检索系统，并同步评估跨分片排序和一致性成本。
5. **项目边界（[现状]）**：当前关注/粉丝列表仍采用 MySQL 分页和固定上限查询，不能宣称已经完成游标分页或分库分表。

**追问：为什么本项目列表用 offset 分页？**
**追问A**：当前数据量和接口需求下，offset 易实现且支持按页跳转；这是工程取舍，不代表它在亿级数据上仍然合适。粉丝/关注列表的固定上限只能控制返回量，不能自动解决深 offset；如果业务改成无限下拉，应以 `(create_time,id)` 游标分页并同步修改前端协议。

**追问：游标分页的缺点？**
**追问A**：游标分页不适合随机跳页，且翻页期间有新增/删除时结果集是一个时间窗口，不是静态快照；必须使用稳定的排序组合键并把 cursor 加签防篡改。它牺牲了跳页能力，换来深页性能稳定，适合 Feed 和无限滚动。

## 15. 线上系统突然告警：如何快速定位问题

**场景**：凌晨收到 CPU 飙高 / 接口超时告警，如何排查？

**设计思路**：先建立故障时间线和影响面，再做止损；排查必须覆盖同步请求、异步消息、缓存、数据库和任务调度，不能只盯着某一条异常日志。

**参考答案**（结合本项目可观测手段）：
1. **确认影响面（[通用]）**：记录告警时间、接口错误率/P95、受影响服务和最近发布；区分是所有请求慢，还是某个 topic、某个分片或某个热点 key 慢。
2. **同步链路（[现状]）**：查看 `GlobalExceptionHandler`、`@ApiOperationLog`、Feign 调用耗时和连接池；Druid/慢查询日志确认是否索引、锁等待或连接耗尽。先保护数据库，必要时降级非核心查询。
3. **异步链路（[现状]）**：查看 RocketMQ 最老消息年龄、重试/死信、消费 TPS；检查 BufferTrigger 当前缓冲量、批处理耗时和消费者线程。BufferTrigger 是进程内内存缓冲，实例重启可能丢未落批数据，要把它当成事故排查项。
4. **缓存和依赖（[现状]）**：确认 Redis 命中率、连接数、慢命令、内存淘汰，检查 Nacos、Cassandra/KV 和 OSS 是否超时；笔记详情还要区分 Caffeine、Redis、MySQL、user RPC、KV RPC 是哪一层失败。
5. **任务和止损（[现状]/[演进]）**：查看 XXL-JOB 是否有失败分片、表不存在或执行器未注册；可以暂时降低消费者令牌速率、暂停低优先级对齐、扩容消费者或限流入口。恢复后做消息重放、计数抽样和数据对齐，不以“接口恢复”作为事故结束。

**追问：定位到是某个消费者处理慢，怎么进一步排查？**
**追问A**：先用消息时间戳和日志 traceId 定位是接收慢、批处理慢还是落库慢；再看 BufferTrigger 缓冲量、batch 耗时、令牌桶等待时间、Feign/Redis/DB 子调用耗时。调大批量或实例数前先确认下游连接池和锁不会成为新瓶颈，并保留调参前后的指标，避免只凭感觉扩容。

**追问：怎么避免类似问题再发生？**
**追问A**：把事故转成可观测指标和演练项：接口 P95/P99、MQ 最老消息、重试/死信、BufferTrigger 丢批风险、Redis 命中率、DB 锁等待、XXL-JOB 分片成功率；为每个指标写阈值和处理手册。再用压测验证限流、扩容、重放和对齐流程，才能证明系统真的能恢复，而不是只补一条日志。
