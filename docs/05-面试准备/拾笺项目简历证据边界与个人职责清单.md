## 二、源码事实不等于个人职责

源码只能说明项目中存在这些实现，不能据此直接使用“我主导”“我独立设计”“我负责全链路”等表述。下面的状态需要你在面试前逐项确认：

| 模块/亮点 | 源码能证明 | 尚不能证明 | 未确认前的安全写法 |
|---|---|---|---|
| 微服务拆分 | 工程已经拆分出多个服务和 API/Biz 模块 | 你是否参与服务拆分、接口设计或部署 | “参与后端服务开发，项目采用……” |
| 多级缓存 | 代码中存在 Caffeine、Redis、数据库读取分支 | 你是否亲自设计缓存层级、配置过期策略、处理过故障 | “参与笔记详情读取链路实现，采用……” |
| 延迟双删/广播清理 | 代码中有 Redis 删除、RocketMQ 广播和延迟消息 | 你是否提出方案、定位过脏读、验证过多实例行为 | “项目通过……处理缓存失效” |
| 点赞/关注链路 | 代码中有 Bloom、ZSET、Lua、顺序消息 | 你是否负责 Lua 脚本、数据恢复和消费者幂等 | “参与互动状态链路开发” |
| 计数校准 | count 和 data-align 模块存在增量及重算逻辑 | 是否由你实现任务、处理过重复消息或校准异常 | “项目包含实时计数与定时重算机制” |
| Canal/ES | 代码中有 Canal 批次处理、Bulk、ACK/rollback | 是否由你搭建 Canal、维护索引、处理过积压 | “参与搜索索引同步功能开发” |

## 三、不能证实前不要写进简历的结果

### 1. 数字类结果

没有压测报告、监控截图、日志样本、数据库统计或可复现脚本时，不写：

- QPS、TPS、并发用户数、峰值流量；
- 平均/TP95/TP99 延迟；
- 缓存命中率、消息堆积量、索引延迟；
- “性能提升 30%”“响应时间降低 50%”“数据库压力下降 xx%”；
- 用户量、笔记量、订单量、日活、线上请求量。

可以改写成架构事实：

```text
使用本地缓存、Redis 和数据库组成分层读取链路。
使用 RocketMQ 将互动请求与持久化、计数处理解耦。
使用批量聚合和定时重算处理计数写入与数据校准。
```

### 2. 上线和业务结果

没有部署记录、发布记录、线上日志或用户反馈时，不写：

- 已上线生产、服务真实用户；
- 支撑大促、热点事件或高并发活动；
- 提升用户留存、转化率或内容发布量；
- 故障率下降、稳定性提升、成本下降；
- 被公司正式采用、在生产环境长期运行。

可以只描述代码中存在的处理机制，并明确“项目代码中实现了”。

### 3. 过强的架构结论

以下说法容易被追问，且不能只凭当前源码证明，不建议直接写：

- “设计并主导了平台整体微服务架构”；
- “保证 MySQL、Redis、Cassandra、RocketMQ 的分布式强一致”；
- “保证消息绝不丢失、绝不重复消费”；
- “实现了完整的高可用、自动扩缩容和生产级容灾”；
- “解决了所有缓存穿透、击穿和雪崩问题”；
- “实现了实时一致的搜索结果”。

更稳妥的写法是说明机制和边界，例如“通过缓存删除、广播清理和延迟消息降低缓存旧值残留风险；该链路属于最终一致性处理，未宣称跨存储强一致”。

## 五、推荐简历正文（保守版）

下面这版只使用可从源码核对的架构事实，并把个人职责控制在“后端开发/参与实现”范围。最终使用前，请把没有亲自做过的条目删除。

### 项目名称

```text
拾笺｜内容创作与互动平台
```

### 项目简介

```text
参与开发图文/视频笔记、点赞收藏、关注关系、评论和搜索等后端功能。项目采用 Spring Cloud Alibaba 微服务架构，围绕笔记详情读取、互动状态处理、计数持久化和搜索索引同步，使用 Redis、RocketMQ、Canal、Elasticsearch 等组件组织业务链路。
```

### 项目要点

```text
• 参与统一认证与跨服务用户上下文开发：Gateway 完成登录校验并透传用户 ID，下游服务通过统一上下文和 Feign 拦截器获取调用方身份，业务层继续执行资源归属校验。

• 参与笔记详情读取链路开发：笔记元数据与正文分开存储，读取路径使用 Caffeine、Redis 和 MySQL 分层获取，并在数据库回源时并行获取作者信息与正文；对不存在笔记写入短期空值缓存，并在返回前执行可见性校验。

• 参与笔记更新和缓存失效处理：更新时删除 Redis 详情缓存，通过 RocketMQ 广播清理多实例本地缓存，并发送延迟消息进行再次删除；正文存储更新失败时返回业务失败，避免把跨存储操作描述成强一致事务。

• 参与互动状态链路开发：点赞使用 Redis Bloom、ZSET 和 Lua 脚本进行判重与原子状态变更，再通过 RocketMQ 异步处理持久化；关注关系采用 Redis 状态和按用户维度的消息顺序处理。

• 参与互动计数与搜索同步功能：count 服务对互动事件进行批量聚合，分别写入 Redis Hash 和 MySQL；data-align 通过 XXL-JOB 分片任务按源表重算计数，Canal 消费 MySQL 变更并通过 Elasticsearch Bulk 更新搜索文档，异常批次保留回滚处理路径。
```

## 六、面试时的边界回答模板

### 面试官问：“这些方案是你设计的吗？”

```text
我能确认的是项目源码中已经实现了这条链路，我在简历里把自己表述为后端开发/参与相关模块实现，不把整个项目架构都认领为个人成果。对于我亲自改过的部分，我可以继续展开接口、数据结构、异常分支和消息链路；没有亲自参与的模块，我会明确说明是阅读和理解过项目实现，而不是声称由我独立设计。
```

### 面试官问：“性能提升了多少？”

```text
目前没有完整压测报告或线上监控数据，所以我不会给出百分比或 QPS 结论。能从代码确认的是：详情读取有本地缓存、Redis 和数据库分层路径；互动持久化和计数处理通过消息异步化、批量聚合与定时重算拆开。若要量化，应该补充固定数据集、并发模型、缓存命中率、TP95/TP99 和数据库写入量等可复现实验。
```

### 面试官问：“能保证一致性吗？”

```text
这套实现不是跨 MySQL、Redis、Cassandra 和 RocketMQ 的分布式强一致事务。源码中采用的是数据库事务、失败清理、缓存删除、广播失效和延迟消息二次删除等组合，目标是降低旧缓存和跨存储失败造成的不一致窗口。消息重试、重复消费、远程 KV 失败和补偿任务仍需要结合消费者实现和运行数据进一步验证。
```

## 八、最终审核规则

- 简历正文只放：已确认的个人经历 + 源码可核对的实现 + 能够现场解释的设计。
- `待确认`、`无法证实`、`未压测`、`个人边界不清`的内容只放在本文件，不放最终简历。
- 没有结果证据时写架构动作，不写收益数字。
- 没有个人提交或明确职责证据时写“参与/项目采用”，不写“主导/独立负责”。
- 任何一句话都要能回答三件事：问题是什么、代码如何处理、你本人做到了哪一步。
- 面试官追问到个人边界时，优先诚实区分“我实现的”“团队已有的”“我阅读后理解的”。
