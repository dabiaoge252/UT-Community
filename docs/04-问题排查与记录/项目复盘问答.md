## 问题一：服务间调用为什么有的用 RocketMQ、有的用 RPC？

### 结论

| 通信方式 | 本质 | 何时用 |
|---------|------|--------|
| **RPC（Feign）** | 同步阻塞调用，必须立刻拿到结果 | 需要返回值、强一致、查询性质、结果参与当前业务流程 |
| **RocketMQ** | 异步解耦，发完消息就走，下游自己消费 | 下游处理不要求马上完成、可接受最终一致、要削峰/解耦 |

### 项目中的 Feign 场景（必须同步拿结果）

- 登录时查用户、校验密码 → auth 服务调 `UserRpcService.userFeignApi`，拿不到用户信息就没法继续；
- 发布笔记时生成笔记 ID → note 服务调 `DistributedIdGeneratorRpcService`，ID 必须在事务里同步拿到才能落库；
- 查笔记作者信息、保存笔记内容到 KV、用户上传头像到 OSS（`FileFeignApi`）。

### 项目中的 RocketMQ 场景（异步解耦/削峰）

- 点赞、收藏、关注是高频操作，note 服务 `asyncSendOrderly` 发消息后请求立刻返回，count 服务异步消费，再用 BufferTrigger 聚合成批落库，削峰填谷；
- 一次点赞要同时通知 count（计数）、data-align（当天增量落库）、note 本地（状态），发一条 MQ 各服务各取所需，实现解耦；
- 延时删 Redis 缓存、通知清本地缓存，用 MQ 的延时/广播特性实现，RPC 做不到；
- MQ 消费失败可重试，即使下游暂时不可用也不影响主流程。

### 判断口诀

> **"现在就要"用 Feign，"以后再说"用 MQ。**

| 判断问题 | 用 Feign | 用 MQ |
|---------|:---:|:---:|
| 调用方是否需要返回值？ | 是 | 否 |
| 结果是否必须强一致？ | 是 | 否 |
| 下游能否容忍几秒延迟？ | 否 | 是 |
| 是否要削峰（高并发写）？ | 否 | 是 |
| 是否要解耦（一事件通知多服务）？ | 否 | 是 |
| 是否要延时执行？ | 否 | 是 |

## 问题二：AutoConfiguration.imports 文件的作用？存放什么？

### 结论

`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 是 **Spring Boot 2.7+/3.x 的自动配置注册清单**，作用是告诉 Spring Boot："这个 jar 包里有哪些自动配置类，启动时要加载它们"。

### 存放内容

每行一个 `@AutoConfiguration` 自动配置类的**全限定类名**（`包名.类名`），可写多个。以 operationlog 为例：

```
com.quanxiaoha.framework.biz.operationlog.config.ApiOperationLogAutoConfiguration
```

### 生效原理

1. Spring Boot 启动时扫描 classpath 下所有 jar 里的该文件；
2. 读出的类名作为自动配置候选，条件满足（依赖存在等）就创建其中的 Bean；
3. 不写该文件，Spring 根本不知道配置类存在，切面/过滤器等不会自动生效。

### 为什么用这个文件

- 早期 Spring Boot 2.6 及以前注册在 `META-INF/spring.factories`；
- 2.7+ 起官方建议改用 `AutoConfiguration.imports`（更清晰、按行排列、支持排序），`spring.factories` 仅用于其他类型入口。

### 项目对照

| Starter | imports 文件注册的自动配置类 |
|---------|-----------------|
| biz-operationlog | `ApiOperationLogAutoConfiguration` |
| biz-context | `ContextAutoConfiguration` + `FeignContextAutoConfiguration`（两行） |
| jackson | `JacksonAutoConfiguration` |

## 问题三：自己配置的 Starter 采用自动配置注册清单吗？为什么 common 不用？

### 结论

**三个 Starter 都采用**了自动配置注册清单；`xiaoha-common` 不用，因为它**不是 Starter**。

### 为什么 Starter 必须用

Starter 的目的就是"**引入即生效**"：业务模块加一行依赖，Spring Boot 启动时自动创建切面、过滤器、拦截器、ObjectMapper 等 Bean。要实现"自动装配"，就必须通过 imports 清单告诉 Spring Boot 自动配置类的位置。

### 为什么 xiaoha-common 不用

`xiaoha-common` 内容全是**纯 Java 类，没有 Spring 注解、没有 Bean**：

```
constant/    # 常量接口（GlobalConstants、DateConstants）
enums/       # 枚举（DeletedEnum、StatusEnum）
exception/   # 异常类（BizException）
response/    # 响应体（Response、PageResponse）
util/        # 工具类（JsonUtils、DateUtils、ParamUtils）
validator/   # 校验注解 + 校验器（PhoneNumber、PhoneNumberValidator）
```

- 这些类不依赖 Spring 容器，也不需要启动时装配任何东西，只是被其他模块直接 import 引用；
- 没有 `@AutoConfiguration` 类，自然没有"自动配置注册清单"的需求；
- 本质是普通 jar 工具包，被三个 Starter 及业务模块依赖。

### 一句话区分

> **Starter = 带自动装配能力的 jar（@AutoConfiguration + imports 清单）；common = 纯工具 jar（只被动提供类，不需要 Spring 启动时做任何事）。**

判断一个模块要不要写 imports 文件，就看它**有没有需要在 Spring 启动时自动创建的 Bean**。

## 问题四：GlobalConstants 接口的作用？被谁调用？

### 结论

[GlobalConstants.java](file:///d:/java/xiaohashu/xiaohashu/xiaoha-framework/xiaoha-common/src/main/java/com/quanxiaoha/framework/common/constant/GlobalConstants.java) 是**全局常量接口**，目前只定义一个常量：

```java
String USER_ID = "userId";
```

它是整个系统中"用户 ID"的**统一键名**，同时充当三层角色：

1. **请求头键名**：网关/上游往 HTTP 请求头写 userId 的 key；
2. **ThreadLocal 的 Map 键**：登录用户上下文存取的 key；
3. **Feign 请求头键名**：Feign 透传 userId 的 key。

核心价值：把魔法字符串 `"userId"` 收敛到一处，保证写 header、读 header、存 ThreadLocal 用的是同一个字符串，不会出现键名对不上导致拿不到登录用户。

### 被谁调用（全部在 biz-context 模块，共 3 个类）

| 调用方 | 用途 |
|--------|------|
| `HeaderUserId2ContextFilter` | 入站请求：`request.getHeader(GlobalConstants.USER_ID)` 从请求头取用户 ID |
| `LoginUserContextHolder` | 上下文存取：作为 ThreadLocal Map 的 key，put/get 用户 ID |
| `FeignRequestInterceptor` | 出站 Feign 调用：`requestTemplate.header(GlobalConstants.USER_ID, ...)` 写入请求头透传下游 |

### 遗留风险点（已修复）

网关 `AddUserId2HeaderFilter` 原本硬编码 `"userId"`，未复用该常量（值恰好一致所以链路正常），已改为直接引用 `GlobalConstants.USER_ID`（见问题五）。

## 问题六：枚举的编写格式？为什么用枚举类而不是直接用 true/false？

### 枚举的编写格式（以 DeletedEnum 为例）

[DeletedEnum.java](file:///d:/java/xiaohashu/xiaohashu/xiaoha-framework/xiaoha-common/src/main/java/com/quanxiaoha/framework/common/enums/DeletedEnum.java)

```java
@Getter
@AllArgsConstructor          // ③ Lombok：生成带参构造器
public enum DeletedEnum {
    // ① 枚举实例列表：必须写在第一行，以分号结尾
    YES(true),
    NO(false);
    // ② 成员变量：声明在实例列表之后，通常 final
    private final Boolean value;
}
```

格式要点：
1. **实例列表必须放在最前面**（`YES(true), NO(false);`），这是 Java 语法的硬性要求；
2. 每个实例可以**带构造参数**，参数对应下面的成员变量；
3. 成员变量 + 构造器 + getter，用 Lombok `@Getter` / `@AllArgsConstructor` 一步生成；
4. 项目里 `StatusEnum`（`ENABLE(0)/DISABLED(1)`）和 `NoteStatusEnum`（业务自定义）都是同一套路：**"业务语义枚举名 + value 存储值"**。

### 为什么不用 true/false，而要写枚举类、再转成 value？

关键点：**枚举名（YES/NO）是"业务语义"，value（true/false）是"存储值"**。二者解耦才有价值。理由如下：

1. **语义化，可读性（最大原因）**

   项目真实用法 [UserServiceImpl.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/service/impl/UserServiceImpl.java#L122-L125)：

   ```java
   .status(StatusEnum.ENABLE.getValue())   // 0：状态为启用
   .isDeleted(DeletedEnum.NO.getValue())   // false：逻辑删除
   ```

   读代码的人一眼看出这是"用户状态"和"逻辑删除标志"。如果直接写 `.status(0)`、`.isDeleted(false)`，只有值没有含义。特别是布尔型参数：`check(true)` 没人知道 true 代表什么，而 `check(DeletedEnum.YES.getValue())` 语义一目了然。

2. **消灭魔法值、统一约束**：不用枚举时 true/false、0/1 散落在各服务代码里，含义靠猜；用枚举后同一概念全局只有一份定义，合法取值只有枚举里那几种，编译器帮你拦截非法值（类型安全）。

3. **业务语义与存储值解耦，便于演进**：数据库 `is_deleted` 列存的就是 true/false（Boolean），所以枚举映射成 `Boolean`；`status` 列存 0/1，所以 `StatusEnum` 映射成 `Integer`。将来存储表示变了（如删除状态改成 0/1/2），**只改枚举一处**，业务代码不用动。

4. **可扩展性**：布尔只有两个值。将来逻辑删除要加第三种状态（如"回收站待清理"），布尔不够用；枚举加一个实例即可。`StatusEnum` 同理（加"冻结"状态直接加实例）。

5. **全项目统一**：A 服务用 `true` 表示未删除、B 服务用 `false` 表示未删除，早晚出 bug。集中到 `xiaoha-common` 的枚举，全项目行为一致。

### 澄清："不直接用 YES 而是转化成 true？"

- 代码里**写的是 `DeletedEnum.NO`**（语义），**落库的是 `getValue()` 转出的 `false`**（存储值）；
- 因为 DO 实体/数据库字段 `isDeleted` 是 `Boolean` 类型，MyBatis 直接映射 true/false，所以需要 `getValue()` 这一步"转化"；
- 枚举名和存储值本就是两层：**枚举名给你看，value 给数据库/DO 用**。

## 问题七：BizException 的构造器？实现 BaseExceptionInterface 的都能作为参数传入？

### 这是一个构造器吗？—— 是

[BizException.java](file:///d:/java/xiaohashu/xiaohashu/xiaoha-framework/xiaoha-common/src/main/java/com/quanxiaoha/framework/common/exception/BizException.java#L23-L26)

```java
public BizException(BaseExceptionInterface baseExceptionInterface) {
    this.errorCode = baseExceptionInterface.getErrorCode();
    this.errorMessage = baseExceptionInterface.getErrorMessage();
}
```

判断它是构造器（构造方法）的三个依据：
1. **方法名与类名完全一致**（都是 `BizException`）；
2. **没有返回类型**（连 `void` 都没有）；
3. 通过 **`new` 关键字**调用，如 `new BizException(ResponseCodeEnum.USER_NOT_FOUND)`。

作用：把传入对象提供的 `errorCode` / `errorMessage` 拷贝到自身字段，供后续全局异常处理器取用。

### 实现 BaseExceptionInterface 的都能作为参数传入？—— 是

这是 Java **多态（面向接口编程）**：参数类型是接口 `BaseExceptionInterface`，运行时实际收到的是它的实现类对象，接口类型自动"向上转型"接收。

```java
// 接口：定义了错误码体系必须有的两个方法
public interface BaseExceptionInterface {
    String getErrorCode();
    String getErrorMessage();
}

// 实现：每个服务自己的错误码枚举
public enum ResponseCodeEnum implements BaseExceptionInterface {
    USER_NOT_FOUND("USER-20007", "该用户不存在");
    private final String errorCode;
    private final String errorMessage;
}
```

- 传参过程：`new BizException(ResponseCodeEnum.USER_NOT_FOUND)` → 枚举实例自动向上转型为 `BaseExceptionInterface` → 构造器里 `getErrorCode()/getErrorMessage()` 运行时多态调用枚举实现 → 拿到 `"USER-20007"` / `"该用户不存在"`；
- **结论**：任何 `implements BaseExceptionInterface` 的类或枚举都能作为该参数传入。项目里每个服务（user、auth、note、kv、oss、gateway）都有自己的 `ResponseCodeEnum implements BaseExceptionInterface`，所以都能 `new BizException(ResponseCodeEnum.XXX)`。

### 为什么这样设计

1. **解耦**：`BizException` 不依赖任何具体错误码枚举，只面向接口编程；新增服务/错误码枚举时 `BizException` 一行不用改；
2. **统一约束**：接口强制错误码必须有 `errorCode` + `errorMessage`，各服务格式统一；
3. **复用**：`Response.fail(BaseExceptionInterface)` 也面向同一接口，异常与响应体共用一套错误码定义。

### 注意：谁需要实现接口？

> **BizException 不需要实现 `BaseExceptionInterface`；需要实现接口的是"传进来的参数对象"（如 ResponseCodeEnum）。** 接口类型能当参数，靠的是传入对象的实现，而不是本类自己实现。

## 问题八：Response 为什么有 3 个带错误码和错误信息的 fail 重载？

### 三个重载与各自场景

[Response.java](file:///d:/java/xiaohashu/xiaohashu/xiaoha-framework/xiaoha-common/src/main/java/com/quanxiaoha/framework/common/response/Response.java#L47-L69)

| 重载版本 | 入参来源 | 典型调用场景 |
|---------|---------|-------------|
| `fail(String errorCode, String errorMessage)` | 直接给两个字符串 | 最底层/最灵活：错误信息需要动态拼接、来自外部配置、不在枚举里 |
| `fail(BizException bizException)` | 一个已抛出的异常对象 | **全局异常处理器**捕获到 `BizException` 后直接传，省去手写 getter |
| `fail(BaseExceptionInterface baseExceptionInterface)` | 错误码枚举（如 `ResponseCodeEnum`） | 业务代码里**没有异常对象**，但有一个错误码枚举，直接传枚举即可 |

### 为什么弄三种（本质是方法重载）

- 三个方法内部做的事**完全一样**：`success=false` + 填 `errorCode` + 填 `message`，区别只是**从哪拿值**：
  - 传 `BizException` → `getErrorCode()/getErrorMessage()` 从异常取；
  - 传枚举 → 从枚举实例取（多态，见问题七）；
  - 传两个字符串 → 直接拿来用。
- **重载（overload）的价值是"便捷"**：调用方不必先 `new` 异常、也不必手动 `getErrorCode()` 再传参，直接把手头有的东西丢进去。Java 编译时按实参类型自动选最匹配的版本。
- 三个签名**互不冲突**：`BizException` 没有实现 `BaseExceptionInterface`（它继承的是 `RuntimeException`），所以传异常对象时不会与第三个重载混淆。

### 调用示例

```java
// 场景一：捕获异常后，直接传异常对象
catch (BizException e) {
    return Response.fail(e);
}

// 场景二：只有错误码枚举，直接传枚举
return Response.fail(ResponseCodeEnum.USER_NOT_FOUND);

// 场景三：错误信息需要动态拼接
return Response.fail("USER-99999", "用户" + userId + "操作过于频繁");
```

### 一句话记忆

> **三个 fail 重载 = 同一套"填错误信息"逻辑 + 三种取值来源（字符串 / 异常对象 / 错误码枚举），用重载让调用方"手头有什么就传什么"。**

## 问题九：JsonUtils 要解决的问题和解决办法？

[JsonUtils.java](file:///d:/java/xiaohashu/xiaohashu/xiaoha-framework/xiaoha-common/src/main/java/com/quanxiaoha/framework/common/util/JsonUtils.java)

### 解决的问题与对应解决办法

| 要解决的问题 | 解决办法（代码对应） |
|-------------|--------------------|
| ① **样板代码重复**：对象↔JSON 互转要反复 `new ObjectMapper` + 写 try/catch | 静态共享一个 `ObjectMapper`，提供 4 个静态方法 `toJsonString / parseObject / parseMap / parseList`；受检异常用 Lombok `@SneakyThrows` 吞掉 |
| ② **反序列化遇未知属性直接抛异常**（默认 `FAIL_ON_UNKNOWN_PROPERTIES=true`，前端多传一个字段就崩） | 静态代码块 `configure(FAIL_ON_UNKNOWN_PROPERTIES, false)`，忽略未知属性 |
| ③ **空对象序列化报错**（默认 `FAIL_ON_EMPTY_BEANS`） | `configure(FAIL_ON_EMPTY_BEANS, false)` |
| ④ **Java 8 时间类型序列化难看/不可读**：`LocalDateTime` 默认输出成数组/时间戳 | 注册 `JavaTimeModule`；且 `init()` 注入 Spring 统一配置的 ObjectMapper（时间统一为 `yyyy-MM-dd HH:mm:ss` 等格式） |
| ⑤ **泛型类型擦除**：反序列化成 `List<User>`、`Map<K,V>` 时，只传 `Class` 表达不了泛型 | `parseList` 用 `TypeReference<List<T>>` 匿名内部类 + 重写 `getType()` 返回 `CollectionType`；`parseMap` 用 `getTypeFactory().constructMapType(...)` 构造带泛型的类型 |
| ⑥ **每次 new ObjectMapper 性能浪费** | 用 `static` 全局共享单例 |
| ⑦ **工具类与接口出参格式不一致**（Controller 用的 Spring Mapper 和代码里手写 JSON 格式不同） | 提供 `init(ObjectMapper)`，由 jackson Starter 的 `JacksonAutoConfiguration` 把 Spring 的 ObjectMapper 注入覆盖，全局行为一致 |

### 关键方法速查

| 方法 | 作用 | 备注 |
|------|------|------|
| `toJsonString(Object)` | 对象 → JSON 字符串 | — |
| `parseObject(json, clazz)` | JSON → 指定类型对象 | 空串返回 null |
| `parseMap(json, K, V)` | JSON → `Map<K,V>` | 用 `constructMapType` 构造泛型 |
| `parseList(json, clazz)` | JSON → `List<T>` | 用 `TypeReference` 匿名类保留泛型 |
| `init(ObjectMapper)` | 注入 Spring 统一配置的 Mapper | 被 `JacksonAutoConfiguration` 调用 |

### 一句话记忆

> **JsonUtils = 全局共享一个配置好的 ObjectMapper（忽略未知属性/空 Bean + JavaTimeModule），把"对象↔JSON"的样板代码收敛成 4 个静态方法，并通过 `init()` 与 Spring 的序列化配置保持完全一致。**

## 问题十：配置类返回 Bean 还是本身？为什么一个返回 FilterRegistrationBean、一个直接返回拦截器？

### 现象

biz-context 里两个自动配置类，返回方式不同：

[ContextAutoConfiguration.java](file:///d:/java/xiaohashu/xiaohashu/xiaoha-framework/xiaoha-spring-boot-starter-biz-context/src/main/java/com/quanxiaoha/framework/biz/context/config/ContextAutoConfiguration.java#L8-L16) 返回 **FilterRegistrationBean**（包装过滤器）：

```java
@Bean
public FilterRegistrationBean<HeaderUserId2ContextFilter> filterFilterRegistrationBean() {
    HeaderUserId2ContextFilter filter = new HeaderUserId2ContextFilter();
    return new FilterRegistrationBean<>(filter);
}
```

[FeignContextAutoConfiguration.java](file:///d:/java/xiaohashu/xiaohashu/xiaoha-framework/xiaoha-spring-boot-starter-biz-context/src/main/java/com/quanxiaoha/framework/biz/context/config/FeignContextAutoConfiguration.java#L8-L13) 直接返回**拦截器本身**：

```java
@Bean
public FeignRequestInterceptor feignRequestInterceptor() {
    return new FeignRequestInterceptor();
}
```

### 为什么一个返回注册器、一个返回本身？

| | `HeaderUserId2ContextFilter`（Servlet Filter） | `FeignRequestInterceptor`（Feign 拦截器） |
|---|---|---|
| 属于哪一层 | **Servlet 容器（Tomcat）**层 | **OpenFeign** 框架层 |
| 生效条件 | 必须注册进 **Servlet 容器的过滤器链**，否则请求不会经过它 | 只要成为 **Spring 容器里的 Bean**，OpenFeign 自动收集应用 |
| 返回方式 | 用 `FilterRegistrationBean` 包装注册 | 直接 `@Bean` 返回 |

- **Filter 是 Servlet 容器概念**：光成为 Spring Bean 不够，必须注册进 Tomcat 过滤器链，且可配置顺序/URL 规则 → 用官方"注册器" `FilterRegistrationBean` 完成注册；
- **Feign 拦截器是 OpenFeign 的扩展点**：创建每个 Feign 客户端时，OpenFeign 自动从容器收集所有 `RequestInterceptor` 类型的 Bean 应用到请求上 → 只要"是个 Bean"就够，直接返回即可。

### 通用判断：写配置类时怎么决定返回什么？

**原则：`@Bean` 方法永远返回"对象本身"，关键是"用哪个类型进容器"——看谁消费它、消费方按什么类型从容器里捡。**

三步决策法：

1. **它是框架扩展点，只要在容器里就会被自动收集吗？**（如 Feign 的 `RequestInterceptor`、AOP 切面、Spring 的 `HandlerInterceptor`）→ **直接返回本身**；
2. **它需要注册进外部容器（如 Servlet 容器）或要配额外参数吗？**（执行顺序、URL 规则、初始化参数）→ **返回注册器**（`FilterRegistrationBean` / `ServletRegistrationBean` / `ServletListenerRegistrationBean`）；
3. **都不是？** → 返回你想注入/暴露给容器用的那个类型。

> 本质：`@Bean` 方法的**返回类型 = 这个 Bean 在容器里的类型**，Spring/框架就按这个类型来找它。

### 一句话记忆

> **返回什么取决于"谁消费它"：框架按类型从容器收集 → 返回本身；组件要进 Servlet 等外部容器且需配置 → 返回注册器包装。** 本项目对照：`FeignRequestInterceptor`（返回本身）vs `HeaderUserId2ContextFilter`（返回 FilterRegistrationBean）。

## 问题十一：SaTokenConfigure 两个 match 规则执行顺序？checkPermission 的权限从哪来？

### 问题背景

[SaTokenConfigure.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-gateway/src/main/java/com/quanxiaoha/xiaohashu/gateway/auth/SaTokenConfigure.java#L27-L39) 的 `setAuth` 里写了两段规则：

```java
// 规则一：所有路径登录校验（排除登录/验证码接口）
SaRouter.match("/**")
        .notMatch("/auth/login")
        .notMatch("/auth/verification/code/send")
        .check(r -> StpUtil.checkLogin());

// 规则二：特定路径权限校验
SaRouter.match("/auth/logout", r -> StpUtil.checkPermission("app:note:publish"));
```

疑问一：访问 `/auth/logout` 时，会不会先被规则一（`match("/**")`）拦下抛异常，规则二根本执行不到？
疑问二：规则二里只写了 `StpUtil.checkPermission("app:note:publish")`，没显式调用 `getPermissionList`，用户的权限列表是从哪来的？

### 结论一：两条规则按代码顺序"立即执行"，/auth/logout 会先走登录校验

- Sa-Token 的 `SaRouter.match(...)` 链式调用在 `setAuth` 回调里**按代码顺序立即执行**（不是注册后统一处理），每次请求都从上到下跑一遍。
- 访问 `/auth/logout` 时：
  1. **规则一**：路径匹配 `/**` 且不在两个 `notMatch` 排除列表里 → `StpUtil.checkLogin()` 执行。
     - **未登录** → 抛 `NotLoginException` → `setError` 重新抛出 → 全局异常处理器 [GlobalExceptionHandler.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-gateway/src/main/java/com/quanxiaoha/xiaohashu/gateway/exception/GlobalExceptionHandler.java#L45-L49) 返回 **401**，规则二此时确实执行不到；
     - **已登录** → 校验通过，继续向下执行。
  2. **规则二**：`/auth/logout` 命中 → 权限校验。
- 所以"先被 `/**` 拦下"确实会发生，但**只有未登录时才会发生**；而退出登录本身就必须已登录——先做通用登录校验、再做特定路径权限校验，这个顺序是正确且符合预期的，不是 bug。

### 结论二：checkPermission 内部会隐式调用 getPermissionList

- `StpUtil.checkPermission("app:note:publish")` 是 Sa-Token 提供的静态方法，内部三步：
  1. 从当前请求携带的 token 解析出**当前登录用户 loginId**；
  2. 调用 `SaManager.getStpInterface().getPermissionList(loginId, loginType)` 拉取该用户权限列表；
  3. 判断列表是否包含 `"app:note:publish"`，不包含则抛 `NotPermissionException`。
- `getStpInterface()` 返回的是 Spring 容器里唯一的 `StpInterface` 实现——即网关 [StpInterfaceImpl.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-gateway/src/main/java/com/quanxiaoha/xiaohashu/gateway/auth/StpInterfaceImpl.java)（实现了 `StpInterface` 且被 `@Component` 注册，Sa-Token 自动收集）。
- 所以 `getPermissionList` **确实被调用了**，只是由 Sa-Token **内部隐式调用**；业务代码的 lambda 里只指定了"要检查哪个权限字符串"。
- 完整调用链：

```
StpUtil.checkPermission("app:note:publish")
  → Sa-Token 内部解析出当前 loginId
  → SaManager.getStpInterface().getPermissionList(loginId, "login")
  → StpInterfaceImpl.getPermissionList
      → Redis 读 user:roles:{userId}（用户角色）
      → 批量读 role:permissions:{roleId}（角色权限，multiGet）
  → 判断 "app:note:publish" 是否在权限列表中
```

### 性能注意

Sa-Token **默认不缓存权限列表**（网关 [application.yml](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-gateway/src/main/resources/application.yml#L80-L97) 的 `sa-token` 配置里也没开缓存），每次 `checkPermission` 都会实时走一遍 Redis（用户角色 + 角色权限两次读取）。当前接口量小可接受；若后续权限校验接口变高频，可在 `StpInterfaceImpl` 里自己加权限缓存。

### 一句话记忆

> **`setAuth` 里的 match 链按代码顺序立即执行：先通用登录校验（`/**` + notMatch 排除）、再特定路径权限校验；`checkPermission` 内部隐式调用容器里唯一的 `StpInterface` 实现（StpInterfaceImpl），从 Redis 实时拉权限列表做判断，权限数据不是凭空来的。**

## 问题十二：项目中为什么频繁进行 JSON 序列化/反序列化？哪些场景需要 JSON？

### 结论：频繁序列化的根源是"微服务把边界变多了"

**Java 对象是 JVM 内存里的东西，而网络传输、磁盘/缓存/消息存储介质只认字节**。只要数据要跨过"进程边界"（HTTP、Feign、Redis、RocketMQ、ZooKeeper、日志文件），就必须在边界处把对象"翻译"成字节（序列化），对端再还原（反序列化）。

单体架构时一个 JVM 内部传对象引用，几乎不涉及序列化；项目拆成网关 + auth/user/note/count/user-relation/kv 等十来个服务后，**每一次服务间交互、每一次缓存读写、每一条 MQ 消息都在过序列化**，所以显得"频繁"。这不是重复劳动，而是分布式系统的必然开销。

### 项目中使用 JSON 的场景一览

| 场景 | 为什么需要 JSON | 项目真实位置 |
|------|----------------|-------------|
| **HTTP 接口（前后端交互）** | REST 接口协议标准，请求/响应体都是 JSON | 各服务 `Controller`；网关 `GlobalExceptionHandler` 用 `objectMapper.writeValueAsBytes(result)` 把 `Response` 转 JSON 写入响应体 |
| **Feign 服务间同步调用** | 通过 HTTP 传输 DTO，调用方/提供方各自序列化、反序列化 | `UserFeignApi`、`KeyValueFeignApi`、`FileFeignApi` 等 |
| **Redis 缓存** | Redis 只存字符串/字节，Java 对象必须先转成 JSON 字符串 | 用户角色：`JsonUtils.toJsonString(roles)`（[UserServiceImpl.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/service/impl/UserServiceImpl.java#L148)）；角色权限（[PushRolePermissions2RedisRunner.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/runner/PushRolePermissions2RedisRunner.java#L127)）；用户信息缓存 `parseObject(userInfoRedisValue, FindUserByIdRspDTO.class)`；笔记详情缓存 `parseObject(noteDetailJson, FindNoteDetailRspVO.class)`（[NoteServiceImpl.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L269)） |
| **RocketMQ 消息** | 消息体是字节流，生产端 `MessageBuilder.withPayload(JsonUtils.toJsonString(dto))` 发 JSON 字符串，消费端 `parseObject(body, XxxDTO.class)` 还原 | 点赞/收藏/关注/笔记发布等：如 [RelationServiceImpl.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user-relation/xiaohashu-user-relation-biz/src/main/java/com/quanxiaoha/xiaohashu/user/relation/biz/service/impl/RelationServiceImpl.java#L151)、[CountNoteLikeConsumer.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-count/xiaohashu-count-biz/src/main/java/com/quanxiaoha/xiaohashu/count/biz/consumer/CountNoteLikeConsumer.java#L72) |
| **日志输出** | 对象默认 `toString` 不可读，转 JSON 便于排查问题 | `log.info("...{}", JsonUtils.toJsonString(userDO))`；操作日志切面 [ApiOperationLogAspect.java](file:///d:/java/xiaohashu/xiaoha-framework/xiaoha-spring-boot-starter-biz-operationlog/src/main/java/com/quanxiaoha/framework/biz/operationlog/aspect/ApiOperationLogAspect.java#L62) 记录入参/结果 |
| **ZooKeeper 节点数据** | ZK 节点存储文本，临时节点保存雪花算法 endpoint 信息 | [SnowflakeZookeeperHolder.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-distributed-id-generator/xiaohashu-distributed-id-generator-biz/src/main/java/com/quanxiaoha/xiaohashu/distributed/id/generator/biz/core/snowflake/SnowflakeZookeeperHolder.java#L173-L179) |

### 为什么统一选 JSON（而不是 Java 原生序列化 / 其他格式）

1. **可读性**：Redis、MQ 控制台里直接看到明文 JSON，排查数据对不上、乱码问题效率高；
2. **跨语言/跨实现**：网关是响应式 WebFlux、业务是 MVC，各服务共用一套 DTO 和 Jackson，JSON 让"谁生产谁消费"解耦，Java 原生序列化（Serializable）强依赖类定义且不跨语言；
3. **与 Web 生态天然一致**：HTTP/Feign 本来就传 JSON，缓存和 MQ 也用同一格式，全链路统一，无需每种介质各来一套；
4. **配合项目统一 ObjectMapper**：`xiaoha-spring-boot-starter-jackson` 的 `JacksonAutoConfiguration` 提供全局唯一 ObjectMapper（时间格式统一、忽略未知属性），`JsonUtils` 再收敛样板代码，全项目序列化行为一致。

### 一句话记忆

> **序列化是"跨进程边界"的入场券：微服务把边界拆多了，JSON 就变频繁了。JSON 的四大用武之地 = HTTP/Feign（协议标准）、Redis（只能存字节）、RocketMQ（消息体是字节流）、日志（可读排错）；选 JSON 而非 Java 序列化，是为了可读、跨实现、全链路统一（统一 ObjectMapper + JsonUtils）。**

## 问题十三：项目里幂等去重怎么做的？

### 结论：分四层做，核心是"DB 唯一索引 + upsert"兜底

项目没有做"MQ 消费幂等表"之类的专门组件，而是**在不同环节用不同手段**各司其职，最终落库兜底靠数据库唯一索引。

| 手段 | 用在哪儿 | 原理 | 项目位置 |
|------|---------|------|---------|
| **① DB 联合唯一索引 + insertOrUpdate（upsert）** | **MQ 消费落库**（最核心） | 表上有唯一索引，重复消息重放时 `ON DUPLICATE KEY UPDATE` 只更新不新增，天然幂等 | 点赞/收藏：`t_note_like`、`t_note_collection`（user_id + note_id 联合唯一），[LikeUnlikeNoteConsumer.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/consumer/LikeUnlikeNoteConsumer.java#L50) 注释"幂等性: 通过联合唯一索引保证"，XML 见 [NoteLikeDOMapper.xml](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/resources/mapper/NoteLikeDOMapper.xml#L107-L112)；关注/粉丝表同理；count 落库 `t_user_count`/`t_note_count` 用 `insertOrUpdate`（[UserCountDOMapper.xml](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-count/xiaohashu-count-biz/src/main/resources/mapper/UserCountDOMapper.xml#L117-L121)） |
| **② 双 Bloom 过滤器** | **data-align 日增量去重** | 先 `BF.EXISTS` 判重 → 不存在才落分片临时表 → **落库成功后才 `BF.ADD` 登记**（先落库后登记，幂等防漏）；临时表自身还有 `uk_note_id`/`uk_user_id` 唯一索引双保险 | [TodayNoteLikeIncrementData2DBConsumer.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/java/com/quanxiaoha/xiaohashu/data/align/consumer/TodayNoteLikeIncrementData2DBConsumer.java#L84-L101) |
| **③ Redis setIfAbsent 分布式标志锁** | **多实例启动只同步一次** | `setIfAbsent(key, "1", 1, DAYS)` 原子抢锁，抢到才执行，防止每个实例都重复预热权限 | [PushRolePermissions2RedisRunner.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/runner/PushRolePermissions2RedisRunner.java#L65) |
| **④ Lua 脚本原子判重** | **关注/取关前置校验** | `follow_check_and_add.lua` 在 Redis ZSET 里判断"是否已关注"，已关注直接抛 `ALREADY_FOLLOWED`，判重 + 添加原子完成 | [RelationServiceImpl.follow](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user-relation/xiaohashu-user-relation-biz/src/main/java/com/quanxiaoha/xiaohashu/user/relation/biz/service/impl/RelationServiceImpl.java#L55-L163) |

### 关键设计点

1. **MQ 重复消费的最终防线是唯一索引**：点赞消息即使被 RocketMQ 重复投递，落到 `t_note_like` 时 `(user_id, note_id)` 唯一索引拦住重复行，`insertOrUpdate` 只覆盖 `status`/`create_time`，不会产生第二条脏数据。
2. **data-align 的"双保险"**：Bloom 挡在 DB 前面减少写入量（同一对象当天只记一次），即使 Bloom 判重因并发漏判，临时表唯一索引（`uk_note_id`/`uk_user_id`）也会兜住重复插入。
3. **count 服务允许短暂不精确**：`ON DUPLICATE KEY UPDATE xxx_total = xxx_total + (#{count})` 是**累加**语义，极端情况下 MQ 重复投递可能多加一次；项目不追求这里强一致，**最终由次日 data-align 从源表重算对齐修正**——这也是"最终一致"的体现。
4. **为什么不用专门的消费幂等表**：对点赞/收藏这类高频操作，维护一张"消息 ID 去重表"会多一次 DB 读 + 一条记录，成本和复杂度更高；用业务表自身唯一索引做幂等，零额外存储、零额外延迟。

### 一句话记忆

> **幂等分层做，DB 兜底：① 消费落库靠"唯一索引 + insertOrUpdate（upsert）"防重复行（点赞/收藏/关注/计数）② data-align 靠双 Bloom 先判重后落库、成功才登记（+ 临时表唯一索引双保险）③ 启动预热用 Redis setIfAbsent 分布式锁只跑一次 ④ 关注前置用 Lua 原子判重。MQ 重复不可怕，唯一索引是最终防线。**

## 问题十四：Leaf 号段表（leaf_alloc）的 max_id / step 代表什么？

### 结论：这是美团 Leaf **号段模式**的号段表，一行一个业务标签（biz_tag）

表里两行数据（用户贴的）：

| biz_tag | max_id | step | 说明 |
|---------|--------|------|------|
| `leaf-segment-user-id` | 6100 | 2000 | 用户 ID |
| `leaf-segment-xiaohashu-id` | 16100 | 2000 | 工大社区 ID |

| 字段 | 含义 |
|------|------|
| `max_id` | 该 tag **当前已从库里划走的号段上界**（已分配到的最大 ID） |
| `step` | **每次批量取号段的大小**（一次从 DB 划走 2000 个连续 ID） |
| `update_time` | **最近一次取号段**（执行 `max_id += step`）的时间 |

### 号段模式工作原理（结合日志对照）

服务每次要 ID 时，不是一条条去 DB 生成，而是**一次批量划一段**：

```
UPDATE leaf_alloc SET max_id = max_id + step WHERE biz_tag = ?
```

拿到 `[旧max_id + 1, 新max_id]` 这一整段连续 ID 缓存在**内存**里发号；内存号段快用完时再去 DB 划下一段（Leaf 还带**双缓冲**：两个 segment，一个在用、另一个提前预取，切换无阻塞）。

对照项目日志（2026-08-11 22:00:20，与表里 `update_time` 完全吻合）：

```
Init buffer. Update leafkey leaf-segment-user-id     Segment(value:4100, max:6100, step:2000)
Init buffer. Update leafkey leaf-segment-xiaohashu-id Segment(value:14100, max:16100, step:2000)
```

说明那一刻两个 tag 各自划走了一段号段：

- `leaf-segment-user-id`（用户 ID）：划走 `4101 ~ 6100`（2000 个），DB 的 `max_id` 从 4100 → **6100**；这段发完后再取会把 `max_id` 推到 **8100**；
- `leaf-segment-xiaohashu-id`（工大社区 ID）：划走 `14101 ~ 16100`（2000 个），DB 的 `max_id` 从 14100 → **16100**；这段发完后再取推到 **18100**。

两个 tag **相互独立、各自推进**，保证同一 tag 内部 ID 全局唯一、不重复；`step` 越大，DB 访问越少、吞吐越高（一次性缓存 2000 个在内存发）。

### 追问一：max_id 不够了怎么办？

**max_id 只是"游标"，永远不会不够——不够了就再划一段。** 号段用完后，服务自动再执行：

```sql
UPDATE leaf_alloc SET max_id = max_id + step WHERE biz_tag = ?
```

- 比如用户 ID 号段 `4101~6100` 发完，再取号时 `max_id` 从 6100 推到 8100，拿到 `6101~8100` 接着发，单调递增无限推进；
- **真正上限是 BIGINT**（约 9.2×10¹⁸），按每秒百万级发号也要几十万年才耗尽，实际不可能用完；
- **多实例并发取号不重叠**：多个实例同时划号段时，靠这条 `UPDATE ... WHERE biz_tag = ?` 的**数据库行锁**串行化，同一时刻只有一个实例成功推进 `max_id`，其它实例拿到的是下一段区间，绝无重叠；
- 这正是号段模式的优势：把"单条生成 ID"变成"一次划 2000 条缓存内存"，DB 访问频率降 2000 倍。

### 追问二：工大社区 ID 取到 6100 以下，不就和用户 ID 重复了吗？

**不会，因为"数值相同 ≠ 冲突"。**

1. **两个 tag 是独立游标，各自单调递增、永不交叉**：`leaf-segment-user-id` 和 `leaf-segment-xiaohashu-id` 虽然都从 1 开始，但各自独立推进、`max_id` 互不影响（当前工大社区 ID 已划到 16100，只会发 16100 以上的号），两个序列各发各的；
2. **就算数值重叠也不叫重复**：唯一性的含义是"**同一业务标签内部**不能重复"（不能有两个用户 ID 都是 5000）。用户 ID 存在 `t_user.id` 列、工大社区 ID 存在 `t_user.xiaohashu_id` 列，**不在同一个唯一约束里、无共享唯一索引**，两个字段数值相同完全合法——就像两个班学生学号都从 1 排，不冲突；
3. **Leaf 按 `biz_tag` 隔离的意义**：每个业务一个独立号段空间，只需保证"本业务内唯一"，不必全局唯一，把 ID 空间规模要求降到最小；
4. **澄清**：**笔记 ID** 不走号段，走 Leaf **雪花模式**（`getSnowflakeId`），是另一套机制，更不存在与用户 ID 冲突。

### 一句话记忆

> **`leaf_alloc` 一行 = 一个 ID 业务 + 当前划号上界（max_id）+ 每次划号长度（step）。`UPDATE max_id = max_id + step` 划走一段连续 ID 缓存到内存发号，用完再划；update_time 就是最近一次划号时间。表里 user-id 已划到 6100、xiaohashu-id 已划到 16100，各自步长 2000。**

## 问题十五：工大社区号和用户 ID 有什么区别？KV 为什么用 UUID 关联？

### 结论一：工大社区号 = 对外展示号，用户 ID = 内部唯一身份

两者都是 Leaf **号段模式**生成的数字，但角色完全不同（注册代码见 [UserServiceImpl.register](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/service/impl/UserServiceImpl.java#L109-L121)，一次注册同时生成两个号段 ID）：

| | 用户 ID（`userId`） | 工大社区号（`xiaohashuId`） |
|--|--------------------|--------------------------|
| 字段 | `t_user.id` | `t_user.xiaohashu_id` |
| 类型 | `BIGINT` / Long | `VARCHAR` / String（内容是数字串） |
| 生成 | Leaf 号段 `leaf-segment-user-id` | Leaf 号段 `leaf-segment-xiaohashu-id`（两个 tag 独立） |
| 角色 | **内部唯一身份标识**：主键、Redis key、Sa-Token loginId、关联查询都用它 | **对外展示号**（类似微信号/小红书号），只用于展示和用户自定义 |
| 是否可变 | 不可变（身份标识） | **用户可改**（`updateUserInfo` 里 `checkXiaohashuId` 校验后更新） |
| 附加用途 | 系统内部全链路使用 | 默认昵称"小红薯{xiaohashuId}" |

一句话：**userId 是系统内部给用户上的"身份证号"，工大社区号是用户对外展示的"微信号"**——都能唯一标识用户，但一个内部不可变、一个对外可自定义。

### 结论二：笔记 ID 用雪花 Long（MySQL），KV 内容引用用 UUID（Cassandra）

同一条笔记是"**元数据 + 大文本分离存储**"的混合方案（详见 [ID使用方式总结.md](file:///d:/java/xiaohashu/xiaohashu/docs/01-项目架构/ID使用方式总结.md)）：

```
t_note.id = Leaf 雪花 Long ID          → MySQL（标题/图片/作者/话题…）
t_note.content_uuid = UUID.randomUUID() → MySQL 只存"引用"
note_content.id = 同一个 UUID          → Cassandra（大文本正文）
```

**为什么 MySQL 用 Long 雪花、Cassandra 却用 UUID？**

| 维度 | MySQL（`t_note.id` 雪花 Long） | Cassandra（`note_content.id` UUID） |
|------|-------------------------------|--------------------------------------|
| 场景 | 元数据：需要**关联查询、分页、排序、对外展示** | 大文本：只**按 key 精确存取**，无排序需求 |
| 存储特性 | 趋势递增 Long 命中**聚簇索引**，插入追加末尾、页分裂少 | **随机 UUID 本地生成零协调**，Cassandra 无中心分配器，省掉"先取 ID 再写入"的 RPC |
| 写入分布 | 适合有序 | 随机散列到全集群各分区，**避免递增 ID 造成写入热点** |
| 安全性 | 对外可见 | `content_uuid` 随机不可猜测，**防恶意批量抓取正文** |

关键点：
1. **UUID 由 note 服务本地 `UUID.randomUUID()` 生成**（[NoteServiceImpl](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L113)），生成后先存 Cassandra 正文，再把同一个 UUID 写进 MySQL `content_uuid` 引用——kv 服务只做纯 KV 存取，不负责生成主键；
2. 若正文也用雪花 ID：发布要先 RPC 取 ID 才能写正文，多一次远程调用；且递增 ID 写入 Cassandra 会集中热点分区；
3. 所以是**两套 ID 各取所长**：Long 管"关系/排序"，UUID 管"内容引用/散列/防猜测"。

### 追问一：为什么工大社区号和用户 ID 不用同一个值？

**因为两者语义与生命周期不同，共用一个值会互相绑架。**

1. **可变性冲突（最核心）**：userId 是内部身份标识，**不可变**（改动会破坏所有关联数据、Redis key、Sa-Token token）；工大社区号是**对外展示号，允许用户自定义修改**（`updateUserInfo` 可改）。两者若共用，用户改工大社区号 = 改内部主键，整个系统的关联/缓存/鉴权全乱；
2. **内部身份与对外展示解耦**：内部 ID 不应暴露、不受用户控制；对外号要可个性化（甚至未来支持用户自定义成字母数字混合，像小红书号一样），分开才能各自演进；
3. **安全**：对外号与内部主键独立，外部无法通过展示号反推/遍历内部用户；
4. 目前两者"恰好"都是号段数字，只是**格式相似**，本质是**两条独立序列、两种独立语义**——就像"身份证号（内部）"和"手机号（对外展示、可改）"本来就不一样。

### 追问二：雪花 Long 也很长，存 MySQL 不也和 UUID 一样有"不易存储"的缺点吗？

**没有——"长度"不是问题，"无序"才是。**

| 对比项 | 雪花 Long（BIGINT） | UUID |
|--------|--------------------|------|
| 体积 | **8 字节定长**，数值再大也是 8 字节 | **16 字节**（或 32 字符字符串），是 Long 的 2 倍 |
| 有序性 | **趋势递增**（高位时间戳），插入基本追加索引末尾 | **随机无序**，插入导致 B+ 树随机页分裂、碎片化、写放大 |
| MySQL 支持 | BIGINT 原生高效类型，19 位数字毫无压力 | 做主键还得转二进制或用字符串，存储与比较都更重 |
| 范围/排序 | 天然支持 | 不支持 |

关键理解：**Long 长的是"数值大小"，UUID 贵的是"无序 + 体积大 2 倍"**。BIGINT 无论存 1 还是存 19 位数字，都是固定 8 字节；雪花 ID 数字虽大但**趋势递增**，InnoDB 聚簇索引照样追加写入、页分裂少——这正是"数字型趋势递增"选型的核心原因（见 [ID使用方式总结.md](file:///d:/java/xiaohashu/xiaohashu/docs/01-项目架构/ID使用方式总结.md#L31-L33)）。

### 追问三：工大社区号支持用户自定义格式的话，不就会产生重复吗？

**会——这正是"用户可自定义账号"系统的通病（微信号、小红书号、抖音号都一样）。** 关键看"谁生成、怎么保唯一"：

| 生成方式 | 唯一性怎么保证 | 会不会重复 |
|---------|---------------|-----------|
| **系统号段生成**（本项目现状，注册时 `getXiaohashuId()`） | Leaf 号段发号器**单调递增，天然不重复**，无需查重 | 不会 |
| **用户自定义**（未来开放） | 需**两层保障**：① 业务层查重——修改前 `selectByXiaohashuId` 查是否被占用，占用则提示换一个；② DB 层兜底——`t_user.xiaohashu_id` 加**唯一索引**，并发下两人同时改成同一个号，靠唯一索引 + 捕获 `DuplicateKeyException` 拦截（与项目幂等去重"唯一索引兜底"同一套路） | 不加保障就会 |

**本项目现状观察点**：注册时工大社区号由 Leaf 号段生成（天然唯一）；[UserServiceImpl.updateUserInfo](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/service/impl/UserServiceImpl.java#L194-L197) 用户修改时 `checkXiaohashuId` **目前只做格式校验**（长度 + 数字/字母/下划线正则），**暂无查重、暂无唯一索引**——若真要开放"完全自由自定义"，需要补这两层保障（可视为一个待办风险点）。

一句话：**系统生成的号靠"发号器"保唯一，用户自定义的号靠"查重 + 唯一索引"保唯一**——两条路径手段不同、缺一不可。

### 一句话记忆

> **userId = 内部身份证（不可变、全链路用），工大社区号 = 对外微信号（可自定义），都是 Leaf 号段独立生成；MySQL 管"结构"用雪花 Long（关联/排序），Cassandra 管"正文"用 UUID（本地生成、散列均衡、防批量抓取），两者用 `content_uuid` 关联。**

## 问题十六：Feign 接口只有方法名，怎么配对到 biz 的 Controller？

### 结论：靠"服务名 + URL 路径"配对，方法名根本不参与匹配

以 [UserFeignApi.registerUser](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-api/src/main/java/com/quanxiaoha/xiaohashu/user/api/UserFeignApi.java#L30-L31) 为例，配对分三层：

**① 服务名配对（找哪台机器）**

```java
@FeignClient(name = ApiConstants.SERVICE_NAME)   // SERVICE_NAME = "xiaohashu-user"
```

[ApiConstants.java](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-api/src/main/java/com/quanxiaoha/xiaohashu/user/constant/ApiConstants.java#L14) 里的服务名 `"xiaohashu-user"` 与 **user-biz 在 Nacos 注册的服务名一致**——调用时 Feign 拿着这个名字去注册中心拿到实例地址（IP + 端口）。

**② 路径配对（核心，真正的契约）**

```java
// Feign 接口（调用方）
@PostMapping(value = PREFIX + "/register")   // PREFIX = "/user" → POST /user/register

// user-biz Controller（提供方）
@RequestMapping("/user")                      // 类级前缀
@PostMapping("/register")                    // 方法级 → 完整路径 /user/register
```

两边拼出的完整 URL **完全一致**（`POST /user/register`），HTTP 请求发到 user-biz 后由 Spring MVC 路由到对应 Controller 方法——**这才是真正"配对"的依据**。方法名不同都没关系：Feign 方法叫 `registerUser`，Controller 方法叫 `register`，照样配对成功。

**③ DTO 类型配对（请求/响应结构一致）**

`RegisterUserReqDTO`、`Response<Long>` 都定义在**共享的 api 模块**（`xiaohashu-user-api`），调用方和提供方引用的是**同一个类**——序列化/反序列化时字段天然一致，不会出现字段对不上。

### 机制本质：Feign 动态代理

Spring Cloud OpenFeign 启动时为每个 `@FeignClient` 接口生成**动态代理对象**：

```
调用 userFeignApi.registerUser(dto)
  → 代理拦截方法调用
  → 解析方法上的 @PostMapping 拼出完整 URL（服务名→Nacos 实例地址 + /user/register）
  → 参数 dto 序列化成 JSON body，用 HTTP POST 发出去
  → 收到响应体反序列化回 Response<Long> 返回给调用方
```

所以**方法名只是调用方代码里的"本地别名"**，HTTP 协议根本不认识 Java 方法名；Feign 的远程调用契约 = **服务名 + HTTP 方法 + 路径 + DTO**。

> 附带：网关鉴权通过后把 `userId` 写进请求头，Feign 出站时由自研 biz-context 的 `FeignRequestInterceptor` 把 `userId` 透传给下游（见问题五）。

### 一句话记忆

> **Feign 配对不靠方法名，靠"服务名（Nacos 定位机器）+ URL 路径（与 Controller 的 @RequestMapping/@PostMapping 完全一致）+ 共享 DTO（字段一致）"；Feign 动态代理把方法调用翻译成 HTTP 请求，方法名只是调用方的本地别名。**

## 问题十七：Spring Cloud Alibaba 动态配置为什么是重建 Bean，而不是直接改值？

### 结论：直接"改字段值"实现不了可靠的刷新，重建 Bean 是唯一通用的方案

（完整使用步骤见 [Nacos配置动态Bean指南.md](file:///d:/java/xiaohashu/xiaohashu/docs/02-开发指南/Nacos配置动态Bean指南.md)。这里只回答"为什么"。）

**① `@Value` 是"实例化时一次求值"，改字段 ≠ 改所有引用**

```java
@Value("${mq-consumer.rate-limit}") private double rateLimit; // 创建 Bean 时把值读进来
```

配置值在 Bean 创建那一刻就被"固化"进字段，之后 Nacos 改配置，字段不会自己变。更关键的是：**值可能被复制走了**——注入到别的地方、传进构造器、存进局部变量。直接改字段，那些已经"复制出去"的值根本不会被更新，Spring 也无法追踪"这个值被用到了哪里"。重建 Bean 则能让**所有注入点（字段、构造器、方法参数）都拿到新实例**。

**② Bean 有完整生命周期，只改值无法重新执行**

Bean 创建时还要做依赖注入、`@PostConstruct` 初始化、AOP 代理包装等。配置变了往往需要**重新走一遍初始化逻辑**（比如用新配置重建连接池、重建客户端），只改字段值这些都不会发生，Bean 状态会"半新半旧"。重建 Bean = 完整重走生命周期，状态自洽。

**③ 有些对象"出厂定死"，根本没法原地改值**

项目里最典型的是 [FollowUnfollowMqConsumerRateLimitConfig](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user-relation/xiaohashu-user-relation-biz/src/main/java/com/quanxiaoha/xiaohashu/user/relation/biz/config/FollowUnfollowMqConsumerRateLimitConfig.java) 的 **Guava `RateLimiter`（令牌桶）**——速率在构造时定死，想改速率只能"换一个新桶"，不能把旧桶的孔改大。连接池、缓存客户端同理。这类对象只能**重建**。

**④ `@RefreshScope` 的实现方式：自定义"作用域"**

`@RefreshScope` 本质是一个 Spring **自定义 Scope**：刷新时把缓存里的旧 Bean 实例销毁，下次 `getBean` 时按最新配置重新实例化。业务代码里注入的始终是**同一个代理（替身）**，Spring 悄悄把幕后对象换了——所以业务代码**一行不用改**，统一生效。这是比"每个字段手动监听更新"更声明式、更可靠的机制。

**⑤ 不是没有"直接改值"的方案，但适用面窄**

Nacos 原生的 `@NacosValue(autoRefreshed = true)` 就是直接改字段值、不重建 Bean（方案 B）。它简单，但**无法处理 ①②③ 的问题**（值被复制走、生命周期、状态固化对象），且需要额外依赖 `nacos-config-spring-boot-starter`。项目统一用方案 A（`@Value` + `@RefreshScope`）正是因为通用、可靠。

### 刷新链路（为什么能自动重建）

```
Nacos 控制台改配置并发布
  → Nacos Config 客户端收到变更（refresh-enabled: true）
  → 发布 RefreshEvent
  → RefreshScope.refreshAll() 销毁 @RefreshScope 标记的旧 Bean
  → 下次调用时重新实例化（重新解析 @Value / @ConfigurationProperties，用新值）
```

### 一句话记忆

> **重建 Bean 是"通用且可靠"的刷新方式：@Value 只求值一次且值会被复制走、Bean 生命周期要重走、令牌桶等对象状态出厂定死无法原地改值——只有重建才能让所有引用点拿到一致的新实例；@RefreshScope = 自定义作用域，销毁旧 Bean、按新配置重建，业务代码无感知。**

## 问题十八：@Transactional 和编程式事务的区别？

### 结论：声明式 = 整个方法一个事务；编程式 = 手动圈定事务边界、返回值驱动后续流程

项目两种都用了，先看真实位置：

| 方式 | 项目真实位置 | 场景 |
|------|-------------|------|
| **`@Transactional(rollbackFor = Exception.class)`** | [UserServiceImpl.register](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/service/impl/UserServiceImpl.java#L94-L96)（注册：插用户+角色）、[NoteServiceImpl.updateNote](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L390)（更新笔记，KV 变更失败需回滚）、[PushRolePermissions2RedisRunner](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/runner/PushRolePermissions2RedisRunner.java#L38) | **纯 DB 操作**、整个方法都是写库 |
| **编程式 `transactionTemplate.execute(...)`** | [FollowUnfollowConsumer](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user-relation/xiaohashu-user-relation-biz/src/main/java/com/quanxiaoha/xiaohashu/user/relation/biz/consumer/FollowUnfollowConsumer.java#L104-L128)（关注：插关注表+粉丝表）、[CountNoteLike2DBConsumer](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-count/xiaohashu-count-biz/src/main/java/com/quanxiaoha/xiaohashu/count/biz/consumer/CountNoteLike2DBConsumer.java#L64) / CountNoteCollect2DBConsumer（计数落库） | **MQ 消费者**：DB 写 + 事务成功后还要做 Redis/MQ 副作用 |

### 两种方式对比

| 维度 | `@Transactional`（声明式） | `TransactionTemplate`（编程式） |
|------|--------------------------|-------------------------------|
| 原理 | AOP 代理，方法进入自动开事务、异常自动回滚 | 手动 `execute(回调)`，事务边界 = 回调代码块 |
| 事务粒度 | **整个方法**一个事务（无法只包一部分） | **可精确圈定**：大方法里只把 DB 写包进事务 |
| 回滚控制 | 抛异常自动回滚（`rollbackFor` 指定异常类型） | 手动 `status.setRollbackOnly()` + 返回 false / 抛异常 |
| 事务内能否做"副作用" | 方法内一切都在事务里（发 MQ、写 Redis 也在事务里，不合适） | **事务里只做 DB 写，事务成功后再做 Redis / MQ** |
| 同类自调用 | **失效**：同类内方法互调不走代理，`@Transactional` 不生效 | 无此问题 |
| 适用 | 简单、整个方法都是 DB 操作 | MQ 消费、"先落库成功再发消息/更新缓存" |

### 为什么 MQ 消费者用编程式事务（关键设计点）

以 [FollowUnfollowConsumer](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user-relation/xiaohashu-user-relation-biz/src/main/java/com/quanxiaoha/xiaohashu/user/relation/biz/consumer/FollowUnfollowConsumer.java#L103-L132) 为例，落库成功后还要"更新 Redis ZSET + 发 MQ 通知计数"：

```java
boolean isSuccess = Boolean.TRUE.equals(transactionTemplate.execute(status -> {
    try {
        followingDOMapper.insert(...);  // 关注表
        fansDOMapper.insert(...);       // 粉丝表
        return true;
    } catch (Exception ex) {
        status.setRollbackOnly();       // 标记回滚
        return false;
    }
}));
// 事务成功后才做"副作用"
if (isSuccess) {
    // ① Lua 更新被关注者的粉丝 ZSET
    // ② 发 MQ 通知计数服务
}
```

1. **事务与副作用分离**：如果整个方法标 `@Transactional`，发 MQ、写 Redis 都在事务里——事务还没提交，消息就发出去了/缓存就更新了；一旦后面回滚，下游已按"已关注"处理，造成不一致。编程式事务把**两条 insert 圈在事务里，成功后才做副作用**；
2. **返回值驱动流程**：`execute` 返回 `true/false` 直接决定"是否继续更新 Redis、发 MQ"，失败时 `setRollbackOnly()` + return false，外层直接 return，**零副作用**；
3. **避免事务期间做网络 IO**：Redis/MQ 是网络调用，放在 DB 事务里会拉长锁持有时间；移出事务后事务极短。

### 一句话记忆

> **`@Transactional` = AOP 代理，整个方法一个事务、异常自动回滚，适合"纯 DB 操作"（注册、更新笔记）；编程式 `TransactionTemplate` = 手动圈事务 + 返回值驱动，适合"DB 写 + 事务成功后才做 Redis/MQ"的消费场景——先落库成功再发消息，失败零副作用，且无自调用失效问题。**

## 一句话记忆总结

1. **RPC vs MQ**：现在就要 → Feign（同步拿结果）；以后再说 → MQ（异步解耦/削峰）。
2. **AutoConfiguration.imports**：Starter 的"自动配置类注册清单"，一行一个 `@AutoConfiguration` 全限定类名，是"引入即生效"的关键。
3. **common 不用清单**：它是纯工具 jar，没有需要自动装配的 Bean。
4. **GlobalConstants.USER_ID**：全系统 userId 的统一键名，串起"网关写 header → 过滤器读 header → ThreadLocal → Feign 透传"整条身份链路。
5. **枚举 = 业务语义 + 存储值**：枚举名给人看（YES/NO），value 给数据库用（true/false/0/1），解耦后可读、可扩展、全项目统一。
6. **BizException 构造器 + 接口参数**：方法名=类名、无返回类型、new 调用 → 是构造器；参数是 `BaseExceptionInterface` 接口，任何实现它的错误码枚举都能传入（多态/面向接口编程），`BizException` 自身不需要实现该接口。
7. **Response 三个 fail 重载**：同一套"填错误信息"逻辑 + 三种取值来源（字符串 / 异常对象 / 错误码枚举），用重载让调用方"手头有什么就传什么"。
8. **JsonUtils**：全局共享一个配置好的 ObjectMapper（忽略未知属性/空 Bean + JavaTimeModule），4 个静态方法收敛样板代码，`init()` 与 Spring 序列化配置保持一致。
9. **@Bean 返回什么**：取决于"谁消费它"——框架按类型从容器收集（Feign 拦截器）→ 返回本身；组件要进 Servlet 等外部容器且需配置（Filter）→ 返回注册器包装（FilterRegistrationBean）。
10. **SaTokenConfigure 双 match**：`setAuth` 里的 match 链按代码顺序立即执行（先 `/**` 通用登录校验 + notMatch 排除，再 `/auth/logout` 特定权限校验）；`checkPermission` 内部隐式调用容器里唯一的 `StpInterface` 实现 `StpInterfaceImpl.getPermissionList` 从 Redis 实时取权限，Sa-Token 默认不缓存。
11. **频繁 JSON 序列化**：根源是微服务把进程边界拆多了——HTTP/Feign、Redis、RocketMQ、日志、ZK 每过一道边界就序列化一次；选 JSON 是为了可读、跨实现、全链路统一（统一 ObjectMapper + JsonUtils）。
12. **幂等去重四层**：消费落库靠"唯一索引 + insertOrUpdate（upsert）"；data-align 靠双 Bloom 先判重后落库、成功才登记（+ 唯一索引双保险）；启动预热用 setIfAbsent 分布式锁；关注前置用 Lua 原子判重——MQ 重复不可怕，唯一索引是最终防线。
13. **Leaf 号段表**：`leaf_alloc` 一行 = 一个 ID 业务 + max_id（已划号上界）+ step（每次划号长度）；`UPDATE max_id = max_id + step` 划走一段连续 ID 缓存内存发号，用完再划（双缓冲预取），update_time 即最近划号时间。
14. **userId vs 工大社区号 / Long vs UUID**：userId 是内部身份证（不可变），工大社区号是对外微信号（可自定义），两者 Leaf 号段独立生成；MySQL 管"结构"用雪花 Long（关联/排序），Cassandra 管"正文"用 UUID（本地生成、散列均衡、防批量抓取），用 `content_uuid` 关联。
15. **Feign 配对机制**：不靠方法名——靠"服务名（Nacos 定位机器）+ URL 路径（与 Controller 的 @RequestMapping/@PostMapping 一致）+ 共享 DTO（字段一致）"；Feign 动态代理把方法调用翻译成 HTTP 请求，方法名只是本地别名。
16. **动态配置重建 Bean**：@Value 只求值一次且值会被复制走、Bean 生命周期要重走、令牌桶等对象状态出厂定死无法原地改值——只能靠 @RefreshScope 销毁旧 Bean、按新配置重建，让所有引用点拿到一致新实例，业务代码无感知。
17. **声明式 vs 编程式事务**：@Transactional = AOP 代理、整个方法一个事务、异常自动回滚，适合纯 DB 操作；编程式 TransactionTemplate = 手动圈事务 + 返回值驱动，适合"DB 写 + 事务成功后才做 Redis/MQ"的消费场景（先落库成功再发消息，失败零副作用）。
