## 1. 延时消息 + 延迟双删策略：保证 Redis 缓存一致性

### 1.1 问题背景：什么是双写一致性

**双写一致性**：在数据更新时，确保多个存储系统（如数据库和缓存）中的数据保持一致的状态，避免脏读。

本项目相关场景（结合现有实现）：

- 笔记详情查询链路：**Caffeine（本地缓存）→ Redis（二级缓存）→ MySQL**；
- 更新笔记时当前处理顺序（[NoteServiceImpl.updateNote](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L409-L421)）：
  1. 更新数据库 `t_note`
  2. 删除 Redis 缓存
  3. 广播 MQ 消息删除各实例本地缓存
- **隐患**：缓存只删一次，若删除后又有并发读把旧值回填进缓存，Redis 里的脏数据会一直存在，直到 TTL 过期（本项目缓存 TTL 为 1~2 天）。

### 1.2 为什么会不一致（典型脏读窗口）

| 场景 | 过程 | 后果 |
|------|------|------|
| 先删缓存、后更库 | A 删缓存 → B 读到 DB 旧值并回填缓存 → A 才更新 DB | 缓存长期为旧值（A 更新后缓存不会再失效） |
| 主从延迟 | A 更新主库 → A 删缓存 → B 命中未完成同步的从库旧值并回填 | 缓存为旧值，直到 TTL 过期 |
| 删除后并发回填 | A 更新 DB → A 删缓存 → B 在删除瞬间把 DB 新值/旧值回填 | 若回填的是旧值则短暂脏读 |

本项目现状是"**先更库、后删缓存**"，主要风险窗口是**主从延迟回填**与**删除后并发回填**。

### 1.3 方案原理：延迟双删（Delayed Double Deletion）

> **延迟双删**：一种用于解决数据库与缓存双写场景下数据不一致问题的优化方案。其核心思想是通过**两次删除缓存**并结合**延迟时间**，尽可能减少因并发操作或主从同步延迟导致的脏数据残留问题。

核心流程：

```text
更新操作（业务线程）：
  ① 第一次删除缓存（Redis + 本地）
  ② 更新数据库
  ③ 发送一条 RocketMQ 延时消息（延迟 T 秒）

T 秒后（MQ 消费者线程）：
  ④ 收到消息 → 第二次删除缓存
```

**为什么第二次要延迟删除**：第一次删除后到数据库更新完成、主从同步完成的这段窗口内，可能有读请求把旧值回填进缓存；延迟 T 秒后（此时窗口已过）再删一次，就能把这些脏数据清掉，保证最终一致。

### 1.4 用 RocketMQ 延时消息落地（参考实现，项目当前未落地）

**为什么用延时消息而不是 `Thread.sleep`**：
- 不阻塞业务线程；
- 消息持久化，可靠、失败可重试；
- 天然支持跨实例（各节点都能收到，连本地缓存一起删）。

**RocketMQ 延时机制**：broker 内置预设延时级别（`messageDelayLevel`，共 18 档）：

```text
1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
（level 1~18，即 1s=level1、5s=level2、10s=level3 ...）
```

**生产者**（更新笔记后发送延时消息，10s 后再删一次缓存）：

```java
// ① 第一次删除缓存（照旧）
redisTemplate.delete(RedisKeyConstants.buildNoteDetailKey(noteId));

// ② 更新数据库 ...

// ③ 发送延时消息：delayLevel=3 对应 10s 后再消费
Message<String> message = MessageBuilder
        .withPayload(String.valueOf(noteId))
        .setHeader(RocketMQHeaders.DELAY, 3)   // 延时级别，不是秒数
        .build();
rocketMQTemplate.syncSend(MQConstants.TOPIC_DELAY_DELETE_NOTE_CACHE, message);
```

**消费者**（延时到点后第二次删除缓存）：

```java
@RocketMQMessageListener(consumerGroup = "xiaohashu_delay_group",
        topic = MQConstants.TOPIC_DELAY_DELETE_NOTE_CACHE)
public class DelayDeleteNoteCacheConsumer implements RocketMQListener<String> {

    @Resource
    private RedisTemplate<String, String> redisTemplate;

    @Override
    public void onMessage(String body) {
        Long noteId = Long.valueOf(body);
        // 第二次删除缓存（幂等，多删无害）
        redisTemplate.delete(RedisKeyConstants.buildNoteDetailKey(noteId));
        // 本地缓存也删（广播场景所有实例都会执行）
        NoteServiceImpl.LOCAL_CACHE.invalidate(noteId);
        log.info("## 延迟双删：第二次删除缓存成功, noteId: {}", noteId);
    }
}
```

> 说明：延时级别只能取 broker 预设档位，不能随意指定秒数；`RocketMQHeaders.DELAY` 是 rocketmq-spring 设置延时级别的标准方式（本项目 `rocketmq-spring-boot-starter` 2.2.3）。

### 1.5 与本项目现状的关联与演进建议

**当前实现**（[NoteServiceImpl.java:409-421](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L409-L421)）：

```java
noteDOMapper.updateByPrimaryKey(noteDO);           // 1. 更新 DB
redisTemplate.delete(noteDetailRedisKey);          // 2. 删 Redis（仅一次）
rocketMQTemplate.syncSend(TOPIC_DELETE_NOTE_LOCAL_CACHE, noteId); // 3. 广播删本地缓存
```

**演进建议**：把"删缓存"升级为延迟双删——

1. 保持现有的"更新 DB + 立即删缓存 + 广播删本地缓存"不变（作为第一次删除）；
2. 更新完成后**追加发送一条延时消息**（如 10s 档）；
3. 新增延时消费者，到点后**再删一次 Redis + 本地缓存**。

改造量小：复用现有 MQ 通道与 Topic 机制，新增一个 Topic + 一个消费者即可。

### 1.6 注意点

1. **延迟时间要大于"最慢读回填 + 主从同步"耗时**：本地单机 MySQL 用 10s 档足够；生产环境需按实际主从延迟评估，一般 1~2 档（1s~10s）即可。
2. **延时级别是预设档位**，只能选 `1s/5s/10s/30s/1m...`，不能精确指定任意秒数；若要更细粒度可自己用 Redis `DELAY QUEUE` + 定时任务实现。
3. **删除操作必须幂等**（多删无害），避免重复消费造成问题。
4. **消息可靠性**：RocketMQ 消息持久化，消费者失败会自动重试；极端情况下消息丢失也只是缓存多脏一段时间，不影响正确性（最终 TTL 兜底）。
5. **更严格的方案**（本项目暂不需要）：更新时带**版本号/时间戳**，写缓存时比对版本；或用**分布式锁**串行化读写。

### 1.7 小结

双写一致性的核心矛盾是"删缓存"与"并发读回填"的竞态；**延迟双删**用"第一次删 + 延时消息第二次删"把这个竞态窗口内的脏数据再清一次。本项目借助已有 RocketMQ 基础设施，实现成本低，是当前更新流程下保证缓存一致性的推荐方案。

## 2. Redis 缓存穿透（Cache Penetration）

### 2.1 什么是缓存穿透

**缓存穿透**：查询的数据**在缓存和数据库中都不存在**，导致每次请求都直接打到数据库。由于缓存中没有"未命中"的记录，所有这类请求都会穿透缓存访问 DB，恶意攻击或大量无效 ID 请求可拖垮数据库。

与击穿/雪崩的区别：穿透查的是"**不存在的数据**"；击穿/雪崩查的是"存在但缓存失效"的数据。

### 2.2 常见解决方案

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| **缓存空值（null 占位）** | 查不到的数据也写进缓存，TTL 设短（如 1~2 分钟） | 实现简单；短暂占用内存、空值 TTL 窗口内若数据被创建会读不到 |
| **布隆过滤器（Bloom Filter）** | 请求前先用过滤器判断 ID 是否存在，不存在直接拦截 | 内存占用极小；有误判率，需要维护过滤器与数据同步 |
| **参数合法性校验** | 接口层先校验 ID 是否合法（如 `@PhoneNumber`、`@NotNull`、范围校验） | 拦掉大部分明显非法请求；无法拦"合法但不存在"的 ID |
| **接口限流/降级** | 对高频异常请求限流 | 兜底手段 |

### 2.3 本项目实现：缓存空值

在**查库后判空**的分支里，把 `"null"` 占位异步写入 Redis，TTL 为 **60 + 随机 60 秒（1~2 分钟）**：

- 用户服务 [UserServiceImpl.java:322-329](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/service/impl/UserServiceImpl.java#L322-L329)：

```java
if (Objects.isNull(userDO)) {
    threadPoolTaskExecutor.execute(() -> {
        // 防止缓存穿透，将空数据存入 Redis 缓存 (过期时间不宜设置过长)
        // 保底1分钟 + 随机秒数
        long expireSeconds = 60 + RandomUtil.randomInt(60);
        redisTemplate.opsForValue().set(userInfoRedisKey, "null", expireSeconds, TimeUnit.SECONDS);
    });
    throw new BizException(ResponseCodeEnum.USER_NOT_FOUND);
}
```

- 笔记服务 [NoteServiceImpl.java:242-249](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L242-L249) 同理（`noteDetailRedisKey` 写 `"null"`）。

**读侧判断**：下次查询时 Redis 命中 `"null"`，`JsonUtils.parseObject("null", ...)` 解析出 null 对象直接返回空数据，不再打数据库。

### 2.4 注意点

- 空值 TTL 不宜过长（本项目 1~2 分钟），否则数据"从无到有"后用户会短暂查不到；
- 占位 key 量大的场景可再叠加**布隆过滤器**（本项目 ID 为分布式 Long，可选做）；
- 写入放在异步线程（`execute`），不阻塞主线程。

## 3. Redis 缓存击穿（Cache Breakdown）

### 3.1 什么是缓存击穿

**缓存击穿**：某个**热点 key** 在过期的一瞬间，大量并发请求同时打到数据库，导致 DB 压力瞬间飙升（区别于雪崩的是"**单个热点 key**"）。

### 3.2 常见解决方案

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| **互斥锁（setnx 重建）** | 缓存 miss 时先 `setIfAbsent` 抢锁，抢到者查库回填，其余等待 | 实现简单、保证只有一次查库；有锁等待开销、可能阻塞 |
| **逻辑过期** | 缓存不设物理过期，值里带过期时间，异步线程发现过期后重建 | 无阻塞、读旧值；实现较复杂，短暂读到旧数据 |
| **永不过期 + 后台定时刷新** | 热点数据后台任务定时更新缓存 | 数据总有值；实现成本高 |
| **本地缓存兜底** | 第一级加 Caffeine 等本地缓存，Redis miss 时本地缓存仍可命中 | 单实例内防击穿有效；多实例场景仍需配合其他方案 |

### 3.3 本项目现状与演进建议

**现状**：未使用互斥锁/逻辑过期，靠 **Caffeine 本地缓存作为第一级**缓解击穿——笔记/用户详情查询链路都是 `Caffeine → Redis → DB`（[NoteServiceImpl.java:213-237](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L213-L237)），单实例内热点 key 过期瞬间由本地缓存兜住，不会直接打到 DB。

**局限**：多实例部署时，各实例本地缓存过期时刻不同，仍可能同时 miss 到 DB；若未来出现强热点数据，可引入**互斥锁**重建缓存：

```java
// 参考实现：缓存 miss 时用 setIfAbsent 抢锁，抢到者查库回填
Boolean lock = redisTemplate.opsForValue().setIfAbsent(lockKey, "1", 3, TimeUnit.SECONDS);
if (Boolean.TRUE.equals(lock)) {
    try {
        // 查库并回填缓存
    } finally {
        redisTemplate.delete(lockKey);
    }
} else {
    // 未抢到锁，短暂等待后重查缓存
}
```

## 4. Redis 缓存雪崩（Cache Avalanche）

### 4.1 什么是缓存雪崩

**缓存雪崩**：**大量缓存 key 在同一时间集中过期**，或 **Redis 实例宕机**，导致海量请求瞬间打到数据库，引发 DB 压力骤增甚至宕机。

### 4.2 常见解决方案

| 方案 | 原理 |
|------|------|
| **TTL 随机打散** | 设置过期时间时加随机值，避免同一批 key 同时失效 |
| **多级缓存** | 加本地缓存（Caffeine）作为第一级，Redis 失效时本地兜底 |
| **Redis 高可用** | 主从 + 哨兵 / Cluster，避免单点宕机 |
| **熔断/限流/降级** | Redis 不可用时快速失败或走兜底数据，保护 DB |

### 4.3 本项目实现

**① TTL 随机打散**：用户/笔记详情的 Redis 缓存过期时间为 **保底 1 天 + 随机 0~1 天秒数**，让各 key 的失效时间分散开：

- [UserServiceImpl.java:339-345](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-user/xiaohashu-user-biz/src/main/java/com/quanxiaoha/xiaohashu/user/biz/service/impl/UserServiceImpl.java#L339-L345)：

```java
// 过期时间（保底1天 + 随机秒数，将缓存过期时间打散，防止同一时间大量缓存失效，导致数据库压力太大）
long expireSeconds = 60*60*24 + RandomUtil.randomInt(60*60*24);
redisTemplate.opsForValue()
        .set(userInfoRedisKey, JsonUtils.toJsonString(findUserByIdRspDTO), expireSeconds, TimeUnit.SECONDS);
```

- [NoteServiceImpl.java:310-312](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-note/xiaohashu-note-biz/src/main/java/com/quanxiaoha/xiaohashu/note/biz/service/impl/NoteServiceImpl.java#L310-L312) 同理（`保底1天 + 随机秒数`）。

**② 多级缓存**：Caffeine 本地缓存（1 小时 TTL）作为第一级，Redis 整体失效/宕机时单实例内仍可命中本地缓存，进一步削峰。

### 4.4 注意点

- Redis 宕机场景当前**未做熔断/限流/降级**，若 Redis 不可用请求会全部打到 DB；生产环境需补充（如 `redisTemplate` 调用失败快速失败 + 本地缓存兜底）；
- 空值占位缓存（1~2 分钟）与正常缓存（1~2 天）的随机打散已同时覆盖，避免空值 key 集中过期。

## 5. 数据对齐日增量落库：同发布者多篇笔记导致唯一索引冲突回滚

### 5.1 问题背景

data-align 服务负责把当天发生变更的点赞、收藏等增量数据落库到**按日期 + 分片**的临时表，供次日对齐任务重算计数。落库时每个变更事件会写两张表：

| 表 | 字段 | 去重维度 | 用途 |
|----|------|----------|------|
| `t_data_align_note_like_count_temp_日期_分片` | `note_id`（`uk_note_id`） | 按笔记 | 今天哪些笔记被点赞，重算每篇笔记的点赞总数 |
| `t_data_align_user_like_count_temp_日期_分片` | `user_id`（= 笔记发布者 ID，`uk_user_id`） | 按发布者 | 今天哪些作者的笔记被点赞，重算作者的"笔记被点赞总数" |

**现象**：用户点赞了**同一位发布者的第 2 篇笔记**时，整个事务回滚，第 2 篇笔记的 ID 没有落库成功；而第 1 篇正常。

### 5.2 根因分析

1. **单一事务耦合两次写入**：消费者在同一个 `transactionTemplate` 里连续 insert 两张表（[TodayNoteLikeIncrementData2DBConsumer.java:90-104](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/java/com/quanxiaoha/xiaohashu/data/align/consumer/TodayNoteLikeIncrementData2DBConsumer.java#L90-L104)），先写笔记表、再写用户表。
2. **去重只覆盖笔记维度**：布隆过滤器只按 `noteId` 校验（[bloom_today_note_like_check.lua](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/resources/lua/bloom_today_note_like_check.lua)），无法拦截"发布者已存在"的情况。
3. **同发布者第 2 篇笔记必然冲突**：
   - 笔记表 insert 新 `noteId` → 成功（`uk_note_id` 不冲突）；
   - 用户表 insert 发布者 ID → 撞 `uk_user_id`（发布者当天第 1 次已写入，见 [CreateTableMapper.xml:40-47](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/resources/mapper/CreateTableMapper.xml#L40-L47)）→ 抛 `DuplicateKeyException`；
   - 事务整体回滚 → **笔记表的有效写入也被回滚**。

这是**确定性 bug**："同发布者多篇笔记被点赞"是正常业务数据，不是脏数据，因此第 2 次用户表 insert 必然失败，并非并发竞态。

### 5.3 附带影响

- **数据静默丢失**：异常在事务内被 `catch` 吞掉，消费方法不抛异常 → MQ 认为消费成功、**不会重试**；
- **当天持续失败**：布隆过滤器未加入该 noteId，后续任何人点赞这篇笔记都会重走"笔记表成功 + 用户表冲突 → 回滚"的路径，当天救不回来；
- **同类代码**：收藏消费者 [TodayNoteCollectIncrementData2DBConsumer.java:91-105](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/java/com/quanxiaoha/xiaohashu/data/align/consumer/TodayNoteCollectIncrementData2DBConsumer.java#L91-L105) 结构相同，存在同样问题。

### 5.4 解决方案：双布隆过滤器

> ✅ **已实施（2026-08-12）**：点赞、收藏消费者均已改造为双 Bloom（[TodayNoteLikeIncrementData2DBConsumer.java:66-125](file:///d:/java/xiaohashu/xiaohashu/xiaohashu-data-align/src/main/java/com/quanxiaoha/xiaohashu/data/align/consumer/TodayNoteLikeIncrementData2DBConsumer.java#L66-L125)），笔记 ID 与发布者 ID 各自独立校验、独立落库、互不影响。

**思路**：分别对**笔记 ID** 与**笔记发布者 ID** 做"落库前校验 + 落库后登记"，两张表各自独立幂等、互不拖累，从源头避免唯一索引冲突。

| 布隆过滤器 | 校验维度 | 对应表 | 职责 |
|-----------|----------|--------|------|
| Bloom A（沿用/改造） | `noteId` | 笔记维度表 | 未落库才 insert，成功后登记 |
| Bloom B（新增） | `noteCreatorId` | 发布者维度表 | 未落库才 insert，成功后登记 |

**核心流程**：

```text
1. 分别校验两个 Bloom：
   - noteId 未登记 → insert 笔记表 → 成功后再加入 Bloom A
   - noteCreatorId 未登记 → insert 用户表 → 成功后再加入 Bloom B
2. 两个写入相互独立（不再绑定在同一个事务里）
3. 任一维度已登记 → 直接跳过对应表的 insert（幂等）
```

### 5.5 落地要点 / 注意点

1. **Bloom 粒度与临时表一致**：均以"日期"为 key 维度（每日一张临时表、每日一个 Bloom），过期时间与现有脚本一致（当天 20 小时）。
2. **唯一索引保留，作为并发兜底**：两个并发消息可能同时判断"未落库"并 insert 同一 `note_id`/`user_id`，此时仍会撞唯一索引 → 需捕获 `DuplicateKeyException` 并忽略（视为已落库），不能回滚另一张表的写入。
3. **先落库、后登记**：只有 insert 成功后才写入 Bloom，保证"已登记 = 已落库"，避免落库失败却登记导致数据漏对齐。
4. **布隆过滤器误判**：误判"已存在"时该条增量会跳过落库（极端情况下该维度少对齐一次），属于可接受的误差；误判方向只可能"误判已存在"，不会漏判已存在的数据。
5. **收藏（Collect）消费者同步改造**：点赞、收藏消费者均已落地双 Bloom（2026-08-12），并修正了 `BF.ADD` 的登记时机——只在 insert 成功后才写入布隆过滤器，保证"已登记 = 已落库"。

### 5.6 落地总结（2026-08-12）

- **双 Bloom 已实施**：点赞 / 收藏消费者按"笔记 ID + 发布者 ID"各用一个布隆过滤器，各自独立判断、独立落库，同一发布者的多篇笔记不再互相影响；
- **移除了单事务耦合**：两张临时表的写入不再绑定在同一事务里，insert 冲突（如并发重复）被 `catch` 吞掉并只影响自身维度，另一张表不受牵连；
- **先落库、后登记**：`BF.ADD` 移到 insert 成功之后执行，避免"落库失败却登记"导致当天数据漏对齐；
- **唯一索引保留作并发兜底**：两个并发消息同时判断"未落库"时，唯一索引拦截重复写入（DuplicateKeyException 被捕获忽略）；
- **数据对齐任务补齐**：7 类计数（关注 / 粉丝 / 笔记点赞 / 笔记收藏 / 用户获赞 / 用户获收藏 / 笔记发布）均有分片广播对齐任务，次日从源表重算回写计数表与 Redis。
